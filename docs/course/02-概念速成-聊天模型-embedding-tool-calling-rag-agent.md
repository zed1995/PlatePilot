## 2.1 坏 case 开场：术语墙

第一次读 LLM 应用代码的人，通常会在十分钟内被这串词砸晕：
token、chat completion、system prompt、embedding、向量相似度、function calling、
RAG、ReAct、Agent、workflow……然后它们还经常出现在同一句话里。

本章只做一件事：把这五个概念讲到**核心思想 + 它在真实项目里对应什么**。
不推导公式，不考历史，目标是让你下一章读 for 循环时没有生词。

先给一张全景图，后面逐条展开：

| 概念 | 一句话 | 在 PlatePilot 里对应什么 |
|---|---|---|
| Chat Completion | 「一串消息进去，一条消息出来」的无状态调用 | 聊天模型端口 |
| Embedding | 把文本变成可比较距离的向量 | 独立的 embedding 模型端口，本地 Qwen |
| Tool Calling | 模型输出「想调谁、参数是什么」，由你的代码执行 | 三个工具 DTO + 六个确定性工具 |
| RAG | 先检索证据、再让模型只基于证据回答的闭环 | 第二篇整个检索链路（第 5–10 章） |
| Agent | 模型在循环里自己决定下一步做什么，直到任务结束 | 第 3 章的 for 循环 → 第三篇的 Eino 图 |

## 2.2 Chat Completion：四个角色的消息对话

模型接口的心智模型极其朴素：**HTTP 无状态调用**。你发一串消息过去，服务端
返回一条 assistant 消息和它为什么停下来（`finish_reason`）。模型不记得任何
上一次调用——所谓「多轮对话」，就是你每次把完整历史重新发一遍。

### token

模型不按字或词处理文本，而是按 **token**（子词单元）。你只需要知道三件事：

1. 输入和输出都按 token 计费、计量；
2. 模型有**上下文窗口**（本项目默认按 32,768 token 配置），历史、证据、系统
   指令共用这一个预算；
3. 因此「往 prompt 里塞多少东西」是一个需要算账的工程决策，不是免费的。

### 四类消息角色

一次对话里的消息只有四种角色，理解这张表就够了：

| 角色 | 谁写的 | 关键细节 |
|---|---|---|
| `system` | 你 | 本轮所有规则的载体：人设、边界、凭据使用规范 |
| `user` | 用户 | 用户输入，中英文皆可 |
| `assistant` | 模型 | 普通回答；调工具时正文往往为空，调用请求放在附加的 `tool_calls` 里 |
| `tool` | 你的代码 | 工具执行结果；必须带调用 ID 指回是哪次调用，错配在协议层就是非法请求 |

`finish_reason` 说明模型为何停下：`stop`（答完了）、`length`（被截断）、
`tool_calls`（停下是为了等你执行工具）、`content_filter`（被内容策略拦下）。
Agent 循环靠它判断「该继续转还是该收工」。

### 一个最小请求的形状

```json
{
  "model": "<model-id>",
  "messages": [
    {"role": "system", "content": "你是餐厅顾问，只基于提供的证据回答。"},
    {"role": "user",   "content": "曼哈顿安静的意大利菜？"}
  ],
  "temperature": 0,
  "stream": false
}
```

注意模型名、服务地址、密钥都是**配置**：今天绝大多数模型服务都讲同一套
`/chat/completions` 协议（OpenAI 本家、OpenRouter、vLLM、Ollama 兼容路由），
换供应商是换配置而不是换代码。怎么把这件事做成工程结构，是第 4 章的主题。

## 2.3 Embedding：让文字有了「距离」

**核心思想：分布式表示。** embedding 模型把任意长度的文本映射成一个固定宽度的
浮点向量（本项目是 **1024 维**，模型 `qwen3-embedding:0.6b`，跑在本地 Ollama
上）。这个向量空间被训练成：**语义相近的文本，向量距离也近**。

于是「这条评论和用户问题相不相关」这个语言问题，就变成了一个几何问题——算两个
向量的夹角。最常用的度量是 **cosine 相似度**：方向一致取 1，正交取 0，相反取
-1。向量数据库里的 `<=>` 运算符就是 cosine 距离（第 7 章会大量见到）。

```text
"安静适合约会的餐厅"      ──embedding──→ [0.02, -0.13, …, 0.31]  (1024 维)
"intimate, quiet vibe…"  ──embedding──→ [0.01, -0.11, …, 0.28]  距离近 → 相关
"pizza slice $2"         ──embedding──→ [0.40,  0.22, …,-0.05]  距离远
```

不需要线性代数也能建立的两个直觉：

1. 它匹配的是**语义**不是字面——「安静」和英文评论里的 "quiet / intimate /
   low noise" 可以靠得很近，这是关键词匹配做不到的；
2. 它是**近似**的、会犯错——精确店名、行政区这种硬约束交给它必然翻车，
   所以第 8 章要多路召回。

任何 embedding 能力，抽象出来都长这样（教学示意，不是仓库源码）：

```go
type Embedder interface {
    Dimensions() int
    Embed(texts []string) ([][]float32, error) // 文档和查询走同一条路径
}
```

这四行里有两个设计决策，后面会变成大文章：

- **文档和查询必须走同一条计算路径。** 如果入库向量和查询向量由不同代码算出
  （预处理、截断、前缀有任何差异），所有检索分数都会带着系统偏差，且极难排查。
- **批量调用。** 向量化是批量重活，一次请求传一个文本数组；为每篇文档发一个
  请求，等于付 N 倍分词和网络成本（第 6 章）。

### 为什么 embedding 走本地，chat 走远端

聊天模型要强（规划、表达、遵循工具协议），用远端的大模型；embedding 用本地
Qwen：语料以英文评论为主、查询以中文为主，需要一个中英文都稳的模型；3,000 家
餐厅的离线向量化是批量重活，本地免费、可重复跑；在线检索每轮只 embed 一个短
查询，本地也扛得住。这不是教条——模型可替换是第 4 章端口抽象的直接回报。

## 2.4 Tool Calling：模型「点菜」，你的代码「做菜」

新手最常见的误解：以为模型能调用你的函数。**不能。** 模型能做的只有一件事：
输出一段结构化 JSON，说「我想调用名为 X 的工具，参数是 {...}」。真正执行的
永远是你的程序，执行完再把结果作为 tool 消息喂回去。

整件事只需要三个对象，记住它们的方向就够了：

| 对象 | 谁 → 谁 | 装什么 |
|---|---|---|
| 工具说明书 | 你 → 模型 | 工具名、一句自然语言描述、参数的 JSON Schema、是否只读 |
| 调用请求 | 模型 → 你 | 调用 ID、工具名、模型生成的参数 JSON |
| 调用结果 | 你 → 模型 | 对应调用 ID、成功/失败状态、结果文本或错误解释 |

三个要点：

1. **说明书的描述字段是模型选工具的唯一依据。** 名字和 Schema 定义形状，
   「什么时候该用它」写在描述里。第 14 章的六个工具，Schema 从强类型声明
   自动生成，而不是手写 JSON。
2. **模型给的参数不可信。** 少字段、类型错、编一个不存在的行政区、引用一个
   本轮没有的证据 ID——都可能发生。校验、超时、错误转换是工具注册表的职责
   （第 14 章），不是模型的自觉。这就是开篇词说的**校验闭环**。
3. **「只读」不是装饰。** PlatePilot 用它区分读工具与写工具：同一轮多个只读
   调用可以并发（最多 3 个），写工具一旦出现立即截停本轮、转人工确认
   （第 18 章）。

另外，工具能力是**可选**的：不是每个模型都支持。对一个没声明工具能力的模型
发工具请求，正确做法是在本地直接拒绝、不发那次 HTTP 调用——否则真实失败形态
会是「你在等一个结构化调用，它还你一段散文」，极难排查。

## 2.5 RAG：不是「检索一下塞进 prompt」，是一个闭环

RAG（Retrieval-Augmented Generation，检索增强生成）的最小闭环有四步：

```text
用户问题
  ① 召回（retrieve）：从语料里找回可能相关的证据
  ② 组装（assemble）：按预算拼成上下文，带来源标识
  ③ 生成（generate）：模型只基于证据回答，观点句挂引用
  ④ 引用校验（verify）：代码核对引用 ID 是否真实、是否本轮拥有 ──不合格回到 ③
```

只做前三步的「RAG」是教程版本；第 ④ 步才是产品与 demo 的分界。没有它，你无法
回答用户那句终极追问：「你凭什么这么说？」

对照第 1 章的坏 case，你现在能看懂 RAG 治幻觉是有条件的：

- 召回错了，证据里没有真东西，模型照样编 → 第 8、10 章解决「召得准」；
- 证据超预算被腰斩成半句引用 → 第 9 章的「整块丢弃」解决；
- 模型引用了它没拿到的 ID → 第 16 章的引用闭包解决。

RAG 不是某个库，它是一条**链路纪律**。第二篇（第 5–10 章）整条都在实现它。

## 2.6 ReAct 与 Agent：控制权在谁手里

**ReAct**（Reason + Act）是一种朴素的交互模式：模型先给一点推理，再选一个
动作（调工具），看到结果后继续推理、再选动作……直到给出最终答案。你下一章
要写的 for 循环就是 ReAct，没有任何神秘成分：

```text
thought（我需要先搜餐厅）→ action（search_restaurants(...)）
→ observation（工具结果）→ thought（还需要证据）→ action(evidence(...))
→ observation → final answer（不再请求工具）
```

那「Agent」和「固定 workflow」的区别到底是什么？一句话：

> **下一步做什么的控制权，在模型手里还是在代码手里。**

- **workflow**：代码把路径写死（A 完了必做 B，分支条件是确定性规则）。可预测、
  便宜、好测，但只会处理你预想过的路径。
- **agent**：模型根据中间结果决定调哪个工具、调几次、什么时候停。灵活，但
  不可预测——会停不下来、会调错、会写库。

PlatePilot 的答案是**混合**，这个判断贯穿第三篇，先建立印象：

- 图的骨架是 workflow（ingress → interpret → plan → 工具轮 → answer →
  finalize），停机点、状态、轮次上限都在代码手里；
- 骨架内部给模型留了一个**有界的 ReAct 环**：一个 turn 最多 5 轮工具，同线程
  最多澄清 3 次；写操作根本不在环的可达路径上。

换句话说：**模型控制选择，代码控制边界。** 这是工程上能让 Agent「既灵活又
不会野出去」的核心手法，第 11–13 章会看到它如何从那个 for 循环一步步长成。

## 2.7 一张收束表

| 你在这类代码里看到 | 它其实在说 |
|---|---|
| 消息数组被反复 append 后整体重发 | 在构造对话历史（服务端无状态） |
| role=tool 的消息带着调用 ID | 工具结果回喂，一次 ReAct 往返的后半程 |
| `finish_reason=tool_calls` | 模型没有答完，它在等你执行工具，循环要继续 |
| 查询和文档用同一个 embed 方法 | 保证两侧向量同分布，检索分数才可比较 |
| 请求里出现「工具说明书」 | 模型只获得了选择与声明的能力，执行永远在你这边 |
| 模型给的参数是一段原始 JSON | 一段**等待代码校验**的输入，不是可信数据 |
| 能力位返回 false 还发工具请求 | 应该本地拒绝的无效调用，不该出门 |

## 2.8 取舍与边界

- **概念是协议无关的，类型是项目自有的。** 对话消息、工具调用这些 DTO 放在
  领域层，不带任何厂商字段；厂商的 wire 类型藏在适配器包内部。换协议 = 换
  适配器，领域代码不动（第 4 章）。
- **embedding 不是相似度的银弹。** 它解决语义匹配，不解决精确匹配、硬过滤、
  地理范围；承认它的边界才有了第 8 章的四个通道。
- **Agent 程度是旋钮不是信仰。** 全固定（没脑子）和全放任（不可控）都是失败
  形态；本项目把自由度开在工具选择上，把状态机、写操作、停机条件留在代码侧。
- **结构化输出也只是「合法 JSON」。** 即便用严格 JSON Schema 模式，也保证
  不了业务合法（行政区真实存在吗？证据 ID 本轮有吗？），语义校验永远在代码
  侧（第 15 章）。

## 2.9 课后实验

**跑（全部离线、不需要模型）**

```bash
cd shared && go test ./...        # 全部领域 DTO 与适配器测试，不需要数据库/模型
```

**观察（改配置，看行为变化）**

- 配置了聊天模型（开篇词档位 C）时，在 `.env` 里把 `CHAT_SUPPORTS_TOOLS`
  关掉再启动，对照 §2.4 想一想：模型连工具说明书都收不到时会怎么回答？为什么
  这种「不可能成功」的请求要在本地拒绝，而不是发出去等一个 400？
- 用 `make run-chat` 启动后直接打健康检查与检索接口（不需要聊天模型）：
  检索请求能成功、Agent 对话不能——观察「一个服务里不同能力各自可降级」
  是什么形态（第 4、23 章会讲清这个分级）。
