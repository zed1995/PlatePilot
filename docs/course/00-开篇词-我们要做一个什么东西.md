## 0.1 先看三场对话

不铺垫，先看这门课做完之后，你手里的东西能干什么。

**第一场：带引用的推荐。** 用户问：「曼哈顿有没有安静一点、适合约会的意大利菜？」
Agent 不是直接凭印象报菜名，它先调 `search_restaurants` 做四路召回，再调
`restaurant_evidence` 取回可引用的评论证据，最后合成回答。观点句每一句都挂着
`[^id]` 角标，点开就能看到是哪家店的哪条评论说了「安静」「适合约会」；而评分、
价格、菜系这类商家记录事实可以直述，但评分必须带着评论样本量出现。你在接口里能
看到的候选自证长这样（摘自 [README.md](../../README.md) 的实测响应）：

```json
{
  "restaurant_id": 7715,
  "name": "Vezzo",
  "score": 0.682,
  "rating": 4.53,
  "rating_count": 1161,
  "reasons": [
    "满足全部硬条件（菜系=italian、行政区=manhattan）（权重 1.00，贡献 0.500）",
    "评分先验（按评论样本量收缩）（权重 0.20，贡献 0.172）"
  ]
}
```

每个候选都自证「我为什么出现在这里」；`trace.channels` 如实记录每个通道跑没跑、
召回了多少。这不是礼貌，这是产品的第一性原则。

**第二场：同名餐厅澄清。** 纽约叫「Joe's Pizza」的店不止一家。当名称解析出
多个置信度接近的候选，Agent 不会替你猜一个——它把本轮停在 `awaiting_input`，
通过候选卡片让用户选「你说的是哪一家」，下一轮带着选择继续。一个线程最多澄清
3 次，第 4 次必须按明示假设往前走，而不是问第四遍。

**第三场：带确认门的预约。** 用户说「帮我订明天晚上 7 点两人位」，Agent 查
mock 库存、展示最终摘要，然后把本轮停在 `confirmation.required`。注意：
**模型话说得再漂亮，也不会产生任何写库**。预约只能在用户看到摘要后，通过独立的
`POST /v1/conversations/:id/confirm` 发生；确认请求带幂等键，网络重试点两次
确认按钮也只会订出一张订单。

三场对话串起来，就是这门课要带你长出来的东西：一个 **evidence-grounded（有据可依）
的餐厅发现 Agent**。

## 0.2 最硬的一条约束

先把这句话钉在墙上：

> **用户看到的每一个结论，都必须能指回一条真实评论。**

为什么要对一个 demo 下这么狠的约束？因为大模型的默认行为不是「不知道就不说话」。
你不给它餐厅数据，它会一本正经地编出店名、评分和「这家很安静」；你把数据塞进
上下文，它**照样会编**。在系统提示词里写「不要编造」是治不好这个病的——模型无法
验证自己有没有编，它没有「真实世界」这个裁判。

所以「引用闭环」只能是**架构级约束**，不是提示词工程：

```text
用户的问题
  → 确定性检索（数据库算，模型不算）
  → 证据组装（超预算整块丢弃，不许半句引用）
  → 模型只在证据范围内表达
  → 回答出来后代码再校验引用 ID 是否本轮真的拥有   ← 闭包在代码侧
  → 校验不过，整轮重新生成
```

这条约束会一路逼出本课程的全部技术点：流式数据处理、embedding、向量索引、多路
召回融合、证据组装、工具调用、图编排、人工确认门、长期记忆、SSE 流式协议、运行
审计、Agent 评测门禁与性能核算。

还有第二条闭环，方向相反，同样重要：

> **校验闭环**：模型吐出来的每一件结构化产物——工具参数、槽位、它声称引用的
> 证据 ID、digest 里的来源评论 ID——在没被代码校验过之前都不可信。

引用闭环管「给用户看的」，校验闭环管「模型给的」。一进一出，会贯穿很多章。

## 0.3 我们手里有什么数据

一份真实的大数据，不是玩具：

| 数据 | 文件 | 规模 |
|---|---|---|
| Google Local Meta（POI 快照） | `data/raw/google_local/meta-New_York.json.gz` | 272,189 行，270,720 个唯一 `gmap_id` |
| Google Local Review（评论） | `data/raw/google_local/review-New_York.json.gz` | 33,459,761 条，gzip JSONL，2.5 GB |

原始文件是 git-ignored 的外部数据，不随仓库分发。真正入库的是清洗后的一小部分：

- 272,189 行 meta → **36,133 家餐厅**写入（约 13.3%）；
- 33.5M 条评论 → prefilter 后 **4.24M 条可导入（12.7%）**，2.5 GB 砍到 308 MB；
- 最终 demo 语料选 **3,000 家活跃餐厅**，生成 **11,775 份活跃知识文档**。

「33.5M 条里只有 12.7% 能用」不是一个背景数字，它决定了后续的一堆设计：为什么
要本地预过滤、为什么硬过滤必须先于向量召回、为什么检索要分两级。第 1 章和第 5 章
会反复回来找它。

## 0.4 四个项目的代码地图

仓库根目录**没有 `go.mod`，也没有 `package.json`**。它是四个各自独立、可单独
构建部署的项目：

| 目录 | 类型 | 职责 |
|---|---|---|
| [data-pipeline/](../../data-pipeline/) | Go module，批处理 CLI | 离线：流式导入 Meta/Review、清洗、生成知识文档与 embedding、`migrate`；**写内容表**（餐馆 / 评论 / 知识文档） |
| [chat-service/](../../chat-service/) | Go module，常驻服务 | 在线：HTTP + SSE 对话 API、Agent 运行时（Eino 图）、两级检索、只读 `/admin/v1`；**写运行时表**（会话、run 审计、记忆、预约） |
| [shared/](../../shared/) | Go module，库 | 领域 DTO、端口与适配器（chat / embedding / store）、配置、日志、测试夹具 |
| [web/](../../web/) | npm 项目 | Vite + React 18 + TS：只读运维台 + Agent 验证台 |

三条结构事实，读代码时一直要记得：

1. **两个服务都写库，但表集不重叠。** pipeline 写语料，chat-service 写运行时；
   schema 只有 `data-pipeline migrate` 能改，chat-service 启动时只**核对**迁移
   版本，落后就拒绝启动。
2. **两个服务都依赖 `shared/`，且绝不互相 import**；`shared/domain` 连
   `postgres`、`sql` 这类词出现在注释里都会让测试失败。
3. **`web/` 从不直接连库。** 运维台走只读的 `/admin/v1`（默认关、额外限
   loopback），Agent 验证台 `/agent` 走 `/v1` 对话面——它是会写的一方，但写入
   全部经由 chat-service。

依赖方向只有这一张图，而且有测试强制：

```text
chat-service  ─┐
               ├─→ shared
data-pipeline ─┘
```

## 0.5 环境准备

环境要求：**Go 1.26+、Docker、Node 18+、Ollama**（本地 embedding；
安装见 https://ollama.com/download ）。可选 `golangci-lint`。

按你的目标分三档准备，第一档不需要任何 API key、不需要原始语料。

### 档位 A：冒烟（10 分钟，验证骨架能跑）

```bash
cp .env.example .env          # 默认值已够本地启动
make pg-up                    # 自带 pgvector + PostGIS 的 Postgres，:55432
make migrate                  # 应用全部 SQL 迁移（= make -C data-pipeline migrate）
make run-chat                 # chat-service，:8080
curl -s localhost:8080/healthz
# {"status":"ok","version":"dev","request_id":"..."}
```

此时库里没有语料，Agent 在没有 chat provider 时无法启动（M4 起模型是主路径），
但服务骨架、schema 校验、健康检查都可以验证。

### 档位 B：语料与检索（需要原始数据 + 本地 embedding）

```bash
make ollama-up                # 起 ollama serve 并 pull qwen3-embedding:0.6b（1024 维）
# 1) 把两个 gzip 文件放到 data/raw/google_local/（见 .env 的 PIPELINE_DATA_DIR）
# 2) 下载行政区边界几何（checksum 钉在代码里），命令见 data/boundaries/README.md
make import-sample            # meta(2万) → review(20万) → stats → score 的小样
# 全量则先 prefilter 再 import（第 5 章详述）：
#   bin/data-pipeline prefilter
#   bin/data-pipeline import --stage=all
bin/data-pipeline build-documents
bin/data-pipeline embed
make -C chat-service eval-retrieval   # 86 个检索 case 的指标门禁
```

走通后可以直接打检索接口（不需要 chat key）：

```bash
curl -s localhost:8080/v1/restaurants/search \
  -H 'content-type: application/json' \
  -d '{"filter":{"cuisines":["italian"],"borough":"manhattan"},"text":"pizza"}' | jq
```

### 档位 C：对话 Agent + 浏览器验证台

在 `.env` 里填一组 **OpenAI 兼容**的聊天模型配置（OpenRouter、vLLM、Ollama 兼容
路由均可，适配器只认 `/chat/completions` 协议）：

```bash
# CHAT_PROVIDER=openai_compatible
# CHAT_BASE_URL=https://openrouter.ai/api/v1
# CHAT_API_KEY=<secret>      # 永远只走配置，打印经 Redacted() 脱敏
# CHAT_MODEL=<支持 function calling 的模型>
# CHAT_SUPPORTS_TOOLS=true
make run-chat-admin          # 后端，同时挂载 loopback-only 的 /admin/v1
make web-install && make web-dev   # Vite（默认 5173），/v1 与 /admin 代理到 :8080
# 或者一条命令：make dev（后端 admin + Vite 一起起，Ctrl-C 一起停）
```

浏览器里 `/agent` 是 Agent 验证台（走 `/v1`，会写），其余页面是只读运维台
（走 `/admin/v1`）。

> 配置的加载顺序：`make run*` 先读项目自己的 `.env`，读不到回退根 `.env`。
> 所有新配置必须走各项目的 `config.Load() + Validate()`，密钥打印时经
> `Redacted()` 脱敏。

## 0.6 这门课怎么讲

不按技术点的教科书顺序，而是按**一个 Agent 长出来的真实顺序**讲：先写一个最丑但
能跑的 for 循环，再带它一次次撞墙，每面墙对应一个真实技术与一次真实取舍。

```text
一个 40 行的 for 循环 Agent
  → 它不知道餐厅数据，就一本正经地编  → 撞上第一面墙：模型幻觉
  → 给了数据它还会编（prompt 治不好）  → 数据工程 + RAG + 向量检索（第二篇）
  → 单通道检索频频翻车                → 多路召回 + 融合 + 证据闭环
  → 循环里长出状态/追问/写操作         → 手写循环失控 → Eino 图编排（第三篇）
  → 工具写死、模型不听话              → 工具注册表 + 槽位抽取 + HITL 确认门
  → "看起来能用"但无法证明对          → 审计 + SSE + 评测门禁 + 性能与韧性（第四篇）
```

### 每章的固定结构

1. **坏 case / 真实需求开场**——一个不解决就过不去的问题；
2. **概念与原理（正文主体）**——这一类问题该怎么想、怎么解，配图配表，
   **不看仓库代码也应当读得懂**，不推导公式；
3. **承载思路的最小示例**——文档内 10–40 行教学片段，只为说明思路，不是仓库源码的搬运；
4. **取舍与边界**——为什么这么做、什么情况下要重新考虑；
5. **课后实验**——只有两类动作：**跑现成命令**（`curl`、`make eval-*`、`EXPLAIN`）、
   **改环境变量观察行为**；
6. **参考代码与目录**——本章涉及的真实文件、函数与实测数字集中在章末，想深入实现再按图索骥。

项目代码在课程里的角色是**证据**，不是教材正文：每讲完一段通用思路，用 PlatePilot 的
真实取舍、实测数字或事故佐证「它在真实系统里如何落地」；知识点本身不依赖读代码。
开篇词与收官章不套这个结构。

受众设定：有任意语言工程经验、没做过 LLM 应用的工程师。不教语言语法——Go 的
接口、并发只作为架构思想出现。

教学顺序不照抄里程碑，但对应关系给你，方便回查任务文档（`docs/platepilot-m*-task-document.md`）：

## 0.7 开始之前的三句话

1. **一切结论以仓库现状为准。** 本课程的数字、路径、行为都来自当前仓库的 README、
   docs、代码、迁移和测试；项目演进、文档过时之时，相信代码并修订文档。
2. **默认离线可跑。** `make test` 不需要数据库、不需要模型、不花钱；需要真库的
   测试在没库时「响亮地 skip」而不是静默通过——「一片绿但什么都没断言」是这套
   代码最警惕的状态。
3. **别跳第 3 章。** 哪怕你已经用过 LangChain/Eino，也请亲手读一遍那个 40 行
   循环和它的七个问题——后面二十三章里每一个「为什么这么设计」，答案都埋在
   这七个问题里。

下一章，我们先把「到底在解决什么问题」讲透：那份 2.5 GB 的数据长什么样、为什么
只有 12.7% 能用，以及「模型会编」这件事为什么是一切设计的起点。
