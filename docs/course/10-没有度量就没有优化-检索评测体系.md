## 10.1 坏 case 开场：你怎么知道它「更好了」？

第 8、9 章把整条检索链路搭齐了：四通道召回、融合、池内重排、证据组装、可溯源引用。
到这里，一个工程师最容易说的一句话是：

> 「我把向量通道的读取深度从 10 加到 100，感觉召回更全了，发布吧。」

这正是一个**真实的改动**。同一份 86 个 case 的评测上，真正动的数字是：

> **返回页里，真正回答了这个问题的餐厅比例，从 0.62 升到了 0.96；86 个 case 中
> 那个返回空结果的 case 也消失了（1 → 0）。**

页 = 10 时，语义通道从三万篇文档里只读 10 篇——它拿到的不是「给融合排序的候选池」，
而是**自己直接命名了答案**；页外的正确餐厅无论被别的通道打多高分，都进不了排名。
读得更深之后，四成「语义沾边、但并不是用户要的那类店」才被挤出前五名。

而最关键的地方在另一个数字：**recall@5 几乎没动，0.857 → 0.843，旧值甚至还略高
一点。** 也就是说，如果手里只有 `recall@5` 这一个指标，这个浅页问题**根本不会被
发现**——它在被盯着的数字上一直「看起来很好」，用户实际读到的页面却是错的。让它
现形的，是当时新加进评测的第二个指标 `semantic_result_relevance`。这次对比在
`vectorOverread` 的代码注释里至今留着（见 [§10.6](#106-参考代码与目录)）。

> **这件事的教训不是「向量越深越好」，而是：只量一个维度，你连改动的好坏都分辨
> 不了；一个你不能分辨好坏的改动，等于不能改。**

还有一种更阴险的情形。曾经有一次评测在 CI 上打出一行：

```
retrieval_recall_at_k = 0.467   (gate >= 0.6)
```

一片红。排查半天，代码一行没动——**只是那台机器重启过，Ollama 没起。**

于是问题来了：**0.467 到底是一次排序退化，还是「语义这一半压根没参与计算」？**
单看这个数字，两者**长得一模一样**。一个把「模型没跑」误报成「排序变差」的指标，
比没有指标更糟：它会把人引向完全错误的方向。

这两件事合起来，就是本章要回答的那个工程上最硬的问题：

> **你怎么知道检索是对的？** 不是「感觉」，不是「随便问两句」，而是**一套可复现、
> 可门禁、能在退化发生的当天就报警的评测体系**。

## 10.2 概念与原理

### 10.2.1 评测集先于指标：86 个 case 覆盖五个查询族

在谈任何指标之前，先要有**被量的东西**。项目里这东西是一个 YAML 文件：
[retrieval_cases.yaml](../../chat-service/internal/retrieval/testdata/retrieval_cases.yaml)，
当前 **86 个 case**（从 25 个一路长到 86），覆盖五个查询族：

| 查询族 | 考什么 | `kind` / 前缀 |
|---|---|---|
| 硬过滤 | 行政区 / 价格 / 菜系 / 最低分被**严格执行**，不许静默放行 | `structured` |
| 店名检索 | 精确店名、残缺店名能不能找到 | `restaurant`（`keyword_` / `partial_`） |
| 软条件 | 「安静、适合约会」这类语义查询，期望店能不能召回 | `restaurant`（`soft_`） |
| 证据主题 | 菜品 / 服务 / 环境 / 性价比 / 等位 / 负面 / 缺失数据 | `evidence`（`evidence_*`） |
| 纪律 | prompt injection、scope 边界、「不知道就拒答」 | `evidence`（`evidence_injection_` / `evidence_scope_` / `evidence_unknown_`） |

文件顶部还有一段 `corpus` 块，**记录这套 fixture 是照着什么语料写出来的**：

```yaml
corpus:
  generated_at: "2026-10-01"
  active_restaurants: 3000
  active_documents: 30198
  evidence_documents: 27198
  embedding_model: "qwen3-embedding:0.6b"
  embedding_dimensions: 1024
  active_by_borough: { manhattan: 2010, brooklyn: 599, staten_island: 353, queens: 31, bronx: 3 }
```

> **为什么要记语料？因为召回是语料的函数。** 同一个「曼哈顿意大利菜」查询，在
> 「曼哈顿有 2010 家店」和「曼哈顿有 3 家店」两种语料上，难度完全不同。评测代码因此
> 会在开跑前把 `generated_at` 和各区店数**打印出来**，并写一句提醒：
> 「如果库的规模和上面这些数字不一致，这次的召回数字和以后的一次不可比。」

这是评测体系的第一条纪律：**分数必须自带语境**，否则一个孤零零的 `0.843` 什么也证明
不了。

### 10.2.2 期望值必须手写，不能从被测系统「录」

拿到一套 case 之后，最省事的做法是**跑一次系统、把结果录下来当标准答案**。项目**明确
拒绝**这么做，理由写得很直白：

> 「A ground truth produced by the system under test makes the metric measure
> self-consistency, which always scores 1.0 and detects nothing.」

**让被测系统给自己出题，等于自己给自己判卷**——它永远考 100 分，也永远发现不了退化。
所以 fixture 里的 `restaurant_ids`（recall 的标准答案）、`exclude_restaurant_ids`
（必须**不出现**的店）、`result_cuisines`（期望页应有的菜系标签）全部是**人工对着抽样行
写出来的**。

其中 `exclude_restaurant_ids` 尤其值得强调：它断言的是**「不该出现的东西没出现」**。
一个把过滤条件应用得**过于宽松**的系统，即使所有正向断言都过，也会栽在这里——
因为「少给了」和「多给了」是两种不同的失败，只测前者测不出来。

### 10.2.3 这里全是规则指标，没有用模型当裁判

现在可以谈指标本身了。业界做语义质量评测，一个很流行的做法是 **LLM-as-judge**：
让一个强模型读「问题 + 答案」，给一个 1–5 分或「是否相关」。它灵活、能评规则写不出的
东西（「这个回答读起来地道吗」），但代价是：**不确定、有成本、不可逐 bit 复现**。

本项目的门禁要求是**可复现**，所以它选了另一条路：**全部指标都是可判定的规则计算**。
最典型的是「语义回答相关性」（`semantic_result_relevance`），它听起来像要一个裁判，
实际上是一个纯数学量：

> **`relevance` = 返回页里、带着「期望菜系标签」的餐厅所占的比例。**
> （`relevantShare`：遍历返回的候选，命中 `result_cuisines` 就计一个，除以页大小。）

这里的取舍很清楚：

- **规则指标**：确定、零成本、能逐字比较两次运行（`reportMetrics` 故意打印**表格**
  而不是一句话，就是为了让人能 diff），代价是**表达力有限**——软指标必须自己拆成
  可判定的形式（「相关」被降维成「有没有某个菜系标签」）。
- **LLM-as-judge**：表达力强，但引入了「裁判今天心情如何」的方差，**不适合当门禁**。

> **门禁要的是「同样的代码 + 同样的语料 ⇒ 同样的分数」。** 一个不能复现的指标，无法
> 回答本章开头那个问题——「这次数字变了，到底是我改坏了，还是环境抖了？」

### 10.2.4 硬指标 vs 软指标：把「缺陷」和「调参结果」分开

`metrics` 结构体把数字分成了**两类，从不合并**：

```go
type metrics struct {
    structuredAccuracy float64   // 硬过滤准确率：必须是 1.0
    recallSum          float64   // 软条件召回：可以 < 1.0，是调参结果
    citationPrecision  float64   // 引用精确率
    groundedPassed     int       // 「整题是否被可核对引用答出」
    crossRestaurantLeak int      // 跨店泄漏：必须恰好 0
    relevanceSum       float64
    vectorRan          int       // 语义通道真跑了几例
    // ...
}
```

原因写在注释里：

> 「A leak is a defect; a recall of 0.5 on a soft condition is a tuning result.
> Printing them in one number would let a good average hide a leak.」

**一次跨店引用泄漏是一条缺陷**（引用把 A 店的话安到 B 店头上，是产品级错误），
而**软条件召回 0.5 是一个调参现状**（可以接受、可以优化）。把两者平均成一个
「综合分」，一个漂亮的平均就会**掩盖一次泄漏**。所以硬指标和软指标永远是**分开列、
分开卡**的。

对应的门禁（Gate C 阈值，全部是**常量**而不是 fixture 里的值）：

| 指标 | 门禁 | 为什么是这个名字的门槛 |
|---|---|---|
| `structured_filter_accuracy` | **恰好 1.0** | 被静默丢弃的硬条件会返回一个「看起来对」的列表——用户明确排除了某家店，却还是看到它，且无从察觉 |
| `retrieval_recall_at_k` | ≥ 0.6 | 软条件召回的下限 |
| `citation_precision` | ≥ 0.7 | 「返回的引用里，有多少是可核对的」的下限 |
| `evidence_grounded_rate` | ≥ 0.95 | 「有多少个可回答的问题，是**整题**由可核对引用答出的」的下限 |
| `cross_restaurant_leak` | **恰好 0** | 一条泄漏就是一次错引用 |
| `semantic_result_relevance` | ≥ 0.6 | 返回页里真正回答问题的比例的下限 |
| `empty_result_rate` | 只报不卡 | 参考项，不作门禁 |

> **阈值为什么写成常量、而不放进 fixture 文件？** 注释说得很清楚：门禁是**里程碑的
> 退出标准**，不是「这份语料的一个属性」。「a fixture that could lower its own bar
> would let a regression pass by editing a file」——如果门槛和被量的数据放在同一个
> 文件里，那么**改一行 YAML 就能把一次退化判成通过**。

### 10.2.5 recall 为什么不够：宽泛语义查询要用 relevance

一个看似显然的问题：「测得准不准，用 recall 不就够了吗？」答案对**窄查询**够，对
**宽泛语义查询**不够。

考虑 `「a pizza place in brooklyn」`（布鲁克林的一家披萨店）。**正确答案有几百家**，
而返回页只有 5 个格子。如果标准答案里手写了 3 个 id，那么只要排序器**更喜欢另外三家
披萨店**，这页就会被打成「错」——尽管它挑的三家**完全正确**。

> 这不是在量「答案对不对」，而是在量「几百个正确答案里，它挑了哪几个」。这个量
> 对用户毫无意义。

所以项目对这类查询换了一个问题：

> **不问「你捞回了哪几家」，而问「你返回的这页，有多大的比例回答了这个问题」。**

这就是 `result_cuisines` + `min_relevant_ratio` 存在的理由，也是
`gateResultRelevance` 注释里那句话的意思：

> 「recall asks whether named restaurants came back, relevance asks whether
> what came back answers the question.」

**每个指标都要有它明确服务的那个问题。** 用错仪器，即使数字在动，也量错了东西。

### 10.2.6 citation precision 与 grounded rate：两条不同的断言

第 9 章末尾把「引用」这件事做成了可核对的。评测里对它有两条独立的度量，**故意不合并**：

- **`citation_precision`（引用精确率）**：返回的**逐条**引用里，有多少条是「可核对」
  的（有来源 `Source`、有观测时间 `SnapshotAt`、且在声明的 scope 内）。它量的是**引用**。
- **`evidence_grounded_rate`（落地率）**：有多少个**可回答的问题**，是**整题**由可核对
  引用答出的。它量的是**问题**。

两者的差别，注释里给了一个精确的例子：

> 「One unsourced sentence beside two good quotes is 0.67 precise and not grounded
> at all.」

——三句引用里两句好、一句**没有来源**：精确率是 0.67（看着还行），但**这个问题**其实
**没有被落地**（有一句无从核对的话混在答案里）。**只有第二条读数会说「这个答案不安全，
不能给用户看」。**

`grounded_rate` 的门槛特别高（0.95），因为注释说这不是抱负而是**契约**：
「grounding is the answer path's contract, not an aspiration — a question it cannot
cite is one it is supposed to decline.」（答不出可核对的引用，它**本该拒答**。）

还有一条容易被忽略的细节：`grounded` 的**分母只算「期望有答案」的问题**
（`MinResults > 0`）。一个断言「这家店没有相关信息」的 case，**不该**被算成「一次未
落地回答」——否则**本该拒答的问题会把这个比率抬高**。

### 10.2.7 一个指标必须能分辨「通道没跑」：`vectorRan / vectorExpected`

回到 10.1 那个 0.467 的故事。解法不是「把门禁调低」，而是**让指标自己说清语义通道
到底跑没跑**：

```go
// vectorExpected 数的是「有 query 可以 embed 的 recall 用例」，
// vectorRan 数的是「语义通道真的跑起来了」的那些。
```

一旦 `vectorRan < vectorExpected`，`assertGates` 会**跳过** recall 和 relevance 两条
语义门禁，并**响亮地**提醒：

- 没设 `PLATEPILOT_REQUIRE_VECTOR`：`t.Skipf`，输出「语义通道有 N 例没跑，两条语义
  门禁因此不成立」——**跳过而不是失败**，因为这是环境缺依赖，不是排序退化；
- 设了 `PLATEPILOT_REQUIRE_VECTOR=1`：**升级为 `t.Errorf`**，门禁真正生效。

> **注释里那段 0.79 vs 0.47 的说明，是这一节的灵魂：**
> 「With the vector channel running, 0.79 is a statement about semantic ranking.
> Without it, the same fixture scores 0.47 — not because the ranking got worse, but
> because half the ranking was never computed. A metric that cannot distinguish
> those two is worse than no metric: the second case reads exactly like a
> regression.」

这里还埋着一个**更隐蔽的 bug**，值得单独讲，因为它是「指标设计」而非「指标数值」的
错误。`vectorExpected` 的分母**不是所有 recall 用例**——因为**店名检索没有 query 可
embed**（比如 `text: "Carmine"`），语义通道**按设计就该跳过**。早期版本把这些
「本就不该跑」的用例也当成「缺席」，于是比率成了 **5/14**，直接触发了「语义通道缺失就
跳门禁」的分支——

> **结果：整套评测静默变绿，而其中 9 个用例的召回根本没被测过。**

**「本该跳过」和「缺席」是两回事。** 把前者误算成后者，会让整个门禁失效，而且失效得
悄无声息。这是本章最值得记住的一条：**评测代码本身也是代码，也会有 bug，而且它的
bug 是「把红变绿」。**

### 10.2.8 覆盖率棘轮：防集合悄悄缩小

指标都对了，还有最后一类风险：**评测集本身悄悄缩水**。

一次重构，有人嫌某个 case「不稳定」删掉了；一次迭代，某个查询族整个被遗落。集合不会
自动腐烂，但会**被人手动缩水**，而且缩水之后**所有指标依然漂亮**——因为难测的 case 没了。

项目用**覆盖率棘轮（ratchet）**挡这个。`TestRetrievalFixtureShape` 在**没有数据库**时
也会跑，它检查 fixture 文件**本身**是否健康：

- 有没有**重复 id**；
- 有没有「**什么都没断言**」的 case（这种 case 只能通过，等于白占位置）；
- `recall_at_k` 设了、但标准答案是空的（指标会**除以零**）；
- 非 evidence 用例有没有搜索词；evidence 用例有没有 `restaurant_ids`；
- `corpus.generated_at` 有没有填（**没日期的分数不可比**）。

再往上一层，是**按族的最小数量**：

```go
const minFixtureCases = 50     // 里程碑要求 50–100 个场景
const minStructuredCases = 30  // 硬过滤族不许缩水

var requiredCoverage = map[string]int{
    "keyword_": 4, "partial_": 3, "soft_": 10,
    "evidence_food_": 3, "evidence_service_": 2, "evidence_ambience_": 2,
    "evidence_value_": 2, "evidence_wait_": 2, "evidence_kid_": 1,
    "evidence_group_": 1, "evidence_complaints_": 2, "evidence_unknown_": 5,
    "evidence_injection_": 2, "evidence_scope_": 1,
}
```

> 这些数字**故意定得比现状低**——注释写得明白：「they are a ratchet against
> silent deletion, not a description of what exists today.」棘轮是**防退**的，
> 不是用来描述当下的。某个族一旦少到线下，评测**直接失败**。

为什么值得为「数量」专门写测试？因为如果没有它，一个保留了 86 个 case、却删光了
**所有 `evidence_complaints_`（负面观点）**和 **`evidence_unknown_`（缺失数据）**的
集合，**照样能通过总数检查**——而答案路径会**正好在最不容易被发现的地方退化**：
**它会开始回答那些它根本没有证据的问题。**

### 10.2.9 离线哲学：宁可「响亮地 skip」，不要「安静地绿」

最后是整套体系的运行姿态。第 1 章立的规矩在这里再次出现，而且更尖锐：

> **「一片绿的套件如果什么都没断言，比一片红更糟。」**

评测需要一个真库、可能还需要一个真 embedding。缺了它们时，**绝不能让它「跑过」**——
因为**对着空结果集跑 fixture，是平凡通过的**：期望的 id 当然没返回（库是空的），
指标要么是 `n/a`，要么是一个**看起来正常**的数字，而它**什么都没测**。

所以缺依赖时它是**显式、响亮的 skip**：

```go
// requireEvalDatabase / assertGates 里的语义门禁都遵循同一姿态：
//   没设 PLATEPILOT_REQUIRE_DB  → Skipped（并打印理由 + 如何开启）
//   设了 PLATEPILOT_REQUIRE_DB=1 → Failed（真门禁）
```

- `PLATEPILOT_REQUIRE_DB=1`：库连不上就 **fail**，而不是 skip；
- `PLATEPILOT_REQUIRE_VECTOR=1`：语义通道没跑就 **fail**，而不是 skip。

而 `make eval-retrieval` 这个 target **默认就把两个开关都打开**——注释解释了为什么：
「this target exists to produce a score」。一次本该产分数的运行，**得分低就是得分低**，
写成「skipped（ok）」是自欺。

## 10.3 承载思路的最小示例

把上面的想法压到最小，一个「可门禁的评测」长这样（示意，非仓库源码）：

```go
// 1) 标准答案是人工写的，不是跑出来的。
type evalCase struct {
    Query         string
    WantIDs       []int64 // recall 的标准答案
    ForbidIDs     []int64 // 必须不出现（漏过滤会被它抓住）
    MinRelevance  float64 // 返回页里相关项的最低比例
}

// 2) 硬指标和软指标分开记，绝不合并成一个平均分。
type scoreboard struct {
    filterFailures int     // 缺陷：必须为 0
    leakCount      int     // 缺陷：必须为 0
    recallSum      float64 // 调参结果：有下限，不要求满分
    recallCases    int
}

func evaluate(svc Service, cases []evalCase) scoreboard {
    var sb scoreboard
    for _, c := range cases {
        page := svc.Search(c.Query, 5)

        // 硬条件：任何一条被漏掉都算缺陷，不允许「平均掉」。
        for _, id := range c.ForbidIDs {
            if pageContains(page, id) { sb.filterFailures++ }
        }
        // 软条件：recall 是分数，不是布尔。
        if len(c.WantIDs) > 0 {
            sb.recallSum += recallAtK(page, c.WantIDs, 5)
            sb.recallCases++
        }
    }
    return sb
}

// 3) 门禁是常量，不是数据里可编辑的值。
func assertGates(t *testing.T, sb scoreboard) {
    if sb.filterFailures > 0 {
        t.Errorf("硬过滤被放松了 %d 次：这是缺陷，不是调参", sb.filterFailures)
    }
    if sb.leakCount > 0 {
        t.Errorf("跨店泄漏 %d 次：引用必须只谈被请求的店", sb.leakCount)
    }
    if sb.recallCases > 0 && sb.recallSum/float64(sb.recallCases) < 0.6 {
        t.Errorf("召回低于下限：先确认语义通道真的跑了，再怀疑排序")
    }
}
```

三行要点，恰好对应三个常见错误：

1. **标准答案手写**（否则在测「自己和自己一致」，永远 1.0）；
2. **硬软分离**（否则一次泄漏会被平均掉）；
3. **门禁写死在代码里**（否则改一行数据就能降标）。

真实实现就是这个骨架长满之后的样子：`loadFixtures` 由它读出 86 个 case，
`runFixtureCase` 逐例累加，`reportMetrics` 打出可 diff 的表格，`assertGates` 卡阈值。

## 10.4 取舍与边界

**① 规则指标赢在可复现，但表达力有限。**
它只能评「可判定」的东西。像「这个回答语气是否得体」「解释是否让人觉得可信」这类
**软质量**，规则写不出来（或者写出来就僵化）。本项目**接受**这个局限，换来的是
**能进 CI 门禁**。要评软质量时，正确做法是**在门禁之外**另起一套 LLM-as-judge 的
离线评估，而不是把它塞进门禁。

**② 分数强绑定语料，跨语料不可比。**
`0.843` 只在「3000 家店、曼哈顿 2010 家」这份 fixture 语料上成立。换一份语料、重新
采样过 fixture，数字就该重新量。所以代码把 `generated_at` 和各区店数**打印出来**并
在语料缺失时**直接报错**——**一个没有语料的分数，是一个无法比较的分数。**

**③ 86 个 case 是地板，不是天花板。**
它覆盖五个族，但**不可能覆盖全部真实查询**。棘轮防的是「缩水」，防不了「**过拟合**
到这套 fixture」——如果每次只对着这 86 个 case 调参，迟早会调出一套「在这 86 个上很
好看」的参数。这是人工评测集的**固有边界**，只能靠**持续补充新场景**缓解。

**④ 只有「注入」这一种对抗用例。**
`evidence_injection_` 考的是第 9 章那条「材料不是指令」的边界。多用户线上产品通常
还有输入侧 moderation、输出侧 PII / 毒性过滤——**那些没有对应的评测族**，因为项目
是本地单用户 demo、语料已脱敏（第 9 章的取舍）。接多用户时，这里要**同时**补护栏
**和**评测用例。

**⑤ `empty_result_rate` 只报不卡。**
「返回空页」在不同查询里含义不同：窄查询查无结果是正常，宽查询返回空页可能是召回
塌了。因为**无法给一个统一阈值**，它的处理方式是**只打印、不作门禁**——一个诚实的
「我拿不准，所以只报给你看」。

**⑥ 评测是函数，不是文件。**
最容易犯的错，是把 fixture 当「数据」、把断言当「脚本」分开维护。但
`TestRetrievalFixtureShape` 恰恰说明：**fixture 文件本身要被测试**（重复 id、空断言、
除零、缺语料）。把评测集当代码来维护，才挡得住「悄悄变绿」。

## 10.5 课后实验

**跑（需要活的库 + 向量通道）**

```bash
make -C .. pg-up && make -C .. migrate
make eval-retrieval      # 已默认设 PLATEPILOT_REQUIRE_DB=1 与 REQUIRE_VECTOR=1
# 输出一张指标表 + 六个门禁；M6-02 用两次运行的表格做逐例对比
```

**体验「响亮地 skip」（不需要库）**

```bash
cd chat-service
go test ./internal/retrieval/ -run TestRetrievalFixtures -count=1 -v
# 库不在 → skip，并打印「A skipped evaluation is not a passing one」
go test ./internal/retrieval/ -run TestRetrievalFixtureShape -count=1 -v
# 形状检查：没有库也会跑，专门验 fixture 文件本身是否健康
```

**把 skip 变成 fail（门禁姿态）**

```bash
PLATEPILOT_REQUIRE_DB=1 go test ./internal/retrieval/ -run TestRetrievalFixtures
# 现在库连不上 = 失败；同理 PLATEPILOT_REQUIRE_VECTOR=1 让「语义通道没跑」= 失败
```

**改 fixture，看棘轮怎么咬人**

- 删掉几个 `evidence_unknown_`（缺失数据）case，让这一族跌破 5 个：
  `TestRetrievalFixtureShape` **立刻失败**。
- 把某个 case 的期望改成空（什么都不断言）：形状测试报「the case asserts nothing」。
- 复制一个 id：报「duplicate fixture id」。

**调参不重编译，对着评测集调**

```bash
# 改根 .env 里的检索开关，再重跑 eval-retrieval，观察哪几个数字在动
RETRIEVAL_TOP_K=5
RETRIEVAL_OVERSAMPLE=2
RETRIEVAL_WEIGHT_VECTOR=1.0
RETRIEVAL_ENABLE_POOL_RESCORE=true
RETRIEVAL_FUSION_METHOD=weighted   # 改成 rrf 再跑一次，对比
```

> 这就是「分数必须可比」的价值：两次运行的表格一 diff，**改动到底动了哪个指标**一目了然。
