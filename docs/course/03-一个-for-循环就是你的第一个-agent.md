## 3.2 四十行：一个能转的 ReAct Agent

```go
// 教学骨架：一个工具调用 Agent 的最小内核。重点看循环结构，忽略 Go 语法。
func runAgent(model ToolCallingModel, query string) (string, error) {
    messages := []Message{
        {Role: "system", Content: "你是餐厅顾问；只能基于工具结果回答，查不到就明说。"},
        {Role: "user", Content: query},
    }
    const maxRounds = 5 // 问题 3：为什么是 5？模型一直调工具怎么办？

    for round := 0; round < maxRounds; round++ {
        // ① 带上完整历史和工具说明书，问一次模型
        resp, err := model.ChatWithTools(messages, searchToolSpec)
        if err != nil {
            return "", err // 问题 6：模型挂了 / 超时 / 乱返回怎么办？
        }
        messages = append(messages, resp.Message) // assistant 消息（可能含工具调用）要进历史

        // ② 模型不再请求工具 = 这就是最终答案，循环退出
        if len(resp.Message.ToolCalls) == 0 {
            return resp.Message.Content, nil
        }

        // ③ 模型请求了工具：由我们的代码执行，模型什么都没有执行
        for _, call := range resp.Message.ToolCalls {
            var args struct{ Text string }
            if err := json.Unmarshal(call.Arguments, &args); err != nil {
                return "", err // 问题 2：参数不合法，除了报错还能怎么办？
            }
            result := fakeSearch(args.Text) // ★ 一切麻烦的源头
            messages = append(messages, Message{
                Role: "tool", Content: result, ToolCallID: call.ID,
            })
        }
        // ④ 回喂后进入下一轮——注意模型服务端无状态，靠 messages 记住一切
    }
    return "", errors.New("exceeded max tool rounds")
}
```

就这些。没有框架，没有图，没有状态机。

### 一次完整的消息序列

一轮「找安静的意大利菜」对话，在线路上长这样：

```text
① system   你是餐厅顾问……
② user     曼哈顿有没有安静一点、适合约会的意大利菜？
        ↓ 问模型（消息历史 + 工具说明书）
③ assistant tool_calls=[{name: search_restaurants, args: {text: "quiet italian manhattan date"}}]
        ↓ 我们的代码执行 fakeSearch
④ tool     （搜索结果）   tool_call_id = ③ 的调用 ID
        ↓ 把①②③④整体重发，再问一次模型
⑤ assistant tool_calls=[{name: search_restaurants, args: { …… }}]   ← 可能继续
⑥ tool     ……
        ↓ 某一轮模型不再请求工具
⑦ assistant content="为你找到……Vezzo，评分 4.53（1161 条评论）……"   ← 循环退出
```

四个不可省略的动作，正是 ReAct 的全部机械结构：

1. **拼 prompt**：系统指令 + 历史消息 + 工具说明书；
2. **调模型**：模型可能返回正文，也可能返回工具调用请求；
3. **执行工具**：你的代码解析参数、跑函数、拿到结果——模型自始至终没有执行
   任何东西；
4. **回喂**：assistant 的调用消息和 tool 结果消息都追加进历史，带着调用 ID
   再问；直到响应里没有工具请求，那段正文就是最终答案。

记住一个反直觉的事实：**模型服务端是无状态的**。第 ② 轮之所以「记得」第 ① 轮，
只是因为你把①到④的消息又完整发了一遍。循环里的消息切片就是这个 Agent 的全部
短期记忆。

### 为什么说这是所有 Agent 框架的内核

无论 Eino、LangGraph 还是别的什么，拆开包装后替你做的都是同一件事：

- 管理这个消息列表（状态传递、裁剪、持久化）；
- 管理循环（停在哪、轮次上限、分支去哪）；
- 管理工具的注册、调用、并发与错误；
- 在节点边界挂上流式与观测回调。

框架没有改变 ReAct 的形状，它只是把循环里那些会缠成毛线团的工程问题变成有
名字的抽象。等你看完 §3.4 的七个问题，再看第 11 章就会明白框架到底在帮你
解决什么。

## 3.3 坏 case 现场：假搜索返回空，模型开始编

现在做本章最重要的一个思想实验。把 `fakeSearch` 写成**永远返回空字符串**
（模拟「检索没查到」，第二篇会告诉你生产环境这有多常见），然后问：

> 曼哈顿中城安静的意大利菜，适合约会的有吗？

你大概率会看到类似这样的输出（**教学示意**，非某次真实抓包；真实表现随模型
不同，但行为模式高度一致）：

```text
assistant（第 3 轮，正文）：
为你推荐 Bella Italia Trattoria，位于曼哈顿中城，评分 4.7，
环境安静浪漫，服务周到，非常适合约会用餐。建议提前预订。
```

一家**不在工具结果里、甚至可能不存在**的店，带着精确到小数点的评分和
「安静浪漫」的体验判断，就这么出来了。更气人的是，它违反了你写在 system
里的那条「查不到就明说」。

### 为什么提示词拦不住

在循环的层面看，有三个具体原因：

1. **模型的优化目标是「给出像答案的续写」，不是「核验事实」。** 空工具结果
   在它看来和「工具坏了 / 参数没写好 / 需要换个问法」无法区分；而训练分布里，
   「热心补一个推荐」远多于「拒绝回答」。
2. **它没有裁判。** 模型在生成 `Bella Italia` 这个 token 时，没有任何机制能
   查询「这个名字在不在工具结果里」。它不是故意撒谎，是**无法知道自己在编**。
3. **提示词是统计层面的规劝。** 「只能基于工具结果」会提高合规率，但没有任何
   强制力——它改变的是概率，不是可达性。你无法用 prompt 证明「这次一定没编」。

而「引用闭环」之所以是架构约束，正是因为它不依赖模型自觉。生产形态里对应的
三道代码闸门（先点名，后面逐章兑现）：

- **输入端**：谈哪几家店由确定性检索确定，取证据的接口在没有餐厅 ID 时直接
  拒绝——模型拿不到「凭空开一家店」的机会（第 9 章）；
- **生成端**：观点句必须挂本轮拥有的证据 ID，引用了不存在的 ID → 整轮重新
  生成（第 16 章）；
- **兜底端**：既没候选也没证据的 turn 走**固定拒绝话术**，根本不交给模型
  自由发挥。

这个空 `fakeSearch` 逼出的不是一个 bug，而是整个**第二篇（数据工程与 RAG）**：
要让模型有的可依，先得有真实的语料、召回和证据组装。

## 3.4 七个问题：本课程的回收清单

空搜索只是第一面墙。把这个骨架认真当产品看，至少有七个问题瞪着你。后续章节
会逐一回收，建议你把这张表折角：

| # | 问题 | 在这个循环里的症状 | 回收章节 |
|---|---|---|---|
| 1 | **模型会一本正经地编，怎么办？** | 空/弱工具结果 → 虚构店名、评分与体验 | 第 1、9、16 章 |
| 2 | **工具怎么声明给模型？参数谁来校验？** | Schema 手写、解析失败只会裸奔报错；恶意/缺字段参数直接进函数 | 第 14 章 |
| 3 | **循环何时停？模型一直调工具怎么办？** | `maxRounds=5` 是拍脑袋的；写操作在循环里可达就更危险 | 第 11、13 章 |
| 4 | **槽位缺失、同名歧义怎么办？** | 「中城那家 Joe's」模型可能瞎选一个；缺人数/日期它会替你脑补 | 第 15 章 |
| 5 | **状态放哪？进程挂了呢？** | 记忆只有那个内存切片；服务重启，等待确认的预约和全部历史蒸发 | 第 13、20 章 |
| 6 | **模型挂了 / 超时 / 返回畸形怎么办？** | 一次 429 整个 turn 失败；流式返回半截 JSON 无法解析 | 第 4、23 章 |
| 7 | **怎么在不花钱、不连库的情况下测它？** | 每跑一次测试都调真实 API：慢、贵、不可复现，CI 没法用 | 第 4、21 章 |

另外两个此时还看不见、但已经埋下的问题，也登记一下：

- 循环里目前只有**一个假工具**。工具变成六个、有读有写时，「同一轮只读调用
  想并发、写操作必须立刻截停」这套调度纪律无处安放（第 14、18 章）；
- 最终答案如果是**流式**逐字发给用户的，而引用校验发生在生成之后——错话已经
  上屏了怎么办（第 16、19 章，`message.replace` 机制的由来）。

## 3.5 从 40 行到最终形态：同一台发动机，各就各位

这门课后面会做的事，不是推倒这个循环重写，而是让它**长出状态、工具、边界和
观测**。预先看一眼每个部件在最终系统里的位置，只建立映射，细节都在第三篇：

| 40 行循环里的部件 | 最终形态里的位置 | 回收的问题 |
|---|---|---|
| 内存里的消息切片（全部记忆） | 显式的 turn 状态 + 会话仓储 + 长期记忆（可持久化） | #5 |
| `for round < 5` | 编译好的状态图 + 三个护栏常量：最多 5 轮工具、一条线程最多 3 次澄清、128 帧事件缓冲 | #3 |
| 一个 `fakeSearch` 函数 | 工具注册表 + 六个确定性工具；只读并发（≤3）、写操作出现即截停 | #2 + 写操作 |
| 裸 `return err` | 模型端口适配器：超时、重试分类、网关方言错误 | #6 |
| 真实 API 才能跑 | 脚本化模型 + 确定性 embedding：离线、零成本、可复现驱动整张图 | #7 |

三个关键概念现在只留印象：

- **编译图**：最终形态在启动时把节点和边一次性声明好、编译成可执行对象；
  图没闭合、类型对不上在**启动时**就报错，而不是第三次对话时（第 12 章）。
- **两个入口**：一个入口跑完返回完整转录（离线评测要这个），另一个入口在
  独立 goroutine 上驱动图、逐帧回调（SSE 首字节延迟要这个）；128 是事件缓冲，
  不是答案长度上限（第 13、19 章）。
- **护栏数值化**：5 轮、3 次澄清都是配置化的停机条件——模型可以决定每一轮
  做什么，但「最多转多少轮」必须在代码手里。

## 3.6 取舍与边界

- **先写循环，再上框架，顺序不要反。** 没有撞过这七面墙，框架里的每个抽象
  对你都只是名词。本课程把 Eino 放到第 12 章，是有意的。
- **`maxRounds=5` 不是玄学，是停机护栏。** 生产取值 5（可由环境变量调），
  因为本产品的 turn 是「检索 + 少量工具」的短流程；任务越开放，这个值和它的
  成本上限越要认真设计。
- **循环骨架要薄，纪律要厚。** 真正的 Agent 工程不在于循环多精巧，而在于
  循环周围那些「模型不可越过」的东西：参数校验、写操作确认门、证据闭包、
  审计与评测。这也是 PlatePilot 选择「固定图骨架 + 有界 ReAct 环」的原因。
- **这个骨架故意没有的东西**：embedding 与多路召回（第二篇）、持久化与
  检查点（第 13、20 章）、真正的工具实现（第 14 章）。缺了它们它只是教学
  具——但它的循环结构，就是最终系统的循环结构。
