# 课程文档标准（评审用）

> **权威口径说明**：本文件已落地为 `course-doc-reviewer` 技能（`.workbuddy/skills/course-doc-reviewer/`），
> 评审执行以该技能为准；本文件作为人读基线保留，内容与其同源。

> 适用对象：`docs/course/` 下的章节文档（第 0–24 章）。
> 本标准是**评审清单**，不是新的写作规范——`00-课程提纲.md` 的「五、写作约定」是**权威基线**，
> 本文只在其之上补两件事：
> 1. 把「教学文档 vs 代码分析」这条用户最关心的边界，落成**可操作的判定标准**；
> 2. 把「概念 / 流程 / 遗漏 / 过度深入」四个评审维度，落成**逐条检查项与输出格式**。
>
> 评审时先套基线，再套本文；本文与提纲冲突时，以提纲为准。

---

## 1. 一份好课程文档是什么

一句话：**教会读者「这一类问题该怎么想、怎么解」，而不是教会读者「这份代码怎么读」。**

- 知识点是**主线**，项目（PlatePilot）是**证据**——项目用来佐证「这套思路在真实系统里如何落地」，
  不是用来逐行走读。
- 读者**不打开任何源码文件**，应当能读懂正文、建立直觉、知道何时用、知道代价。
- 每章统一遵循提纲的六段结构（坏 case 开场 → 概念与原理 → 最小示例 → 取舍与边界 →
  课后实验 → 参考代码与目录）；其中**正文（前四段）以知识与思路为主线的，正文不逐段走读源码**，
  真实文件路径与函数名集中在章末「参考代码与目录」。

---

## 2. 不可违反的红线（来自提纲，复述即约束）

- 中文行文；面向用户的文案沿用项目中文风格。
- 一切数字、行为、文件路径必须来自仓库现状（README / docs / 代码 / 迁移 / 测试），不臆造；
  项目演进而本章过时，以仓库为准并修订本章。
- 原理只讲核心思想与关键过程，不逐行抠源码、不推导公式。
- 正文以知识与思路为主线，不以代码为主线；不按代码文件顺序组织章节、不逐段走读源码。
- 最小示例只保留 10–40 行教学骨架，不复制大段真实源码；章末「参考代码与目录」才是读代码的入口。

## 3. 教学文档 vs 代码分析——判定标准（核心新增）

这是本标准的重点。判断一段正文「是不是滑向了代码分析」，用下面三层测试 + 信号对照表。

### 3.1 三层测试（No-Code Comprehension Test）

> 对正文的任意一个小节，问：**一个没打开过被引用源文件的读者，能不能回答下面四件事？**
>
> 1. 它在解决什么问题？
> 2. 核心思想 / 关键决策是什么？
> 3. 为什么这样做（取舍 / 代价）？
> 4. 怎么识别它、何时该用 / 何时不该用？

- 四件都能答 → **教学**（达标）。
- 必须去读源码才懂，或正文主要内容是「`file X` 里的 `func Y` 做了 Z，分 N 步」→ **代码分析**（违规）。

### 3.2 信号对照表

| 维度 | ✅ 这是教学 | ❌ 这是代码分析 |
|---|---|---|
| 主线 | 讲「为什么 / 怎么想 / 权衡」 | 讲「函数怎么一步步执行」 |
| 项目的作用 | 作为**证据**佐证一个通用原理 | 作为**讲解对象**本身 |
| 类比 / 反例 | 有「城市找地址」「坏 case 开场」等认知冲突 | 缺失，直接进实现细节 |
| 代码片段 | 仅在 §X.3「最小示例」，且 ≤40 行、合成骨架 | 正文内大段贴真实源码、逐行注释 |
| 组织顺序 | 按「问题 → 思路 → 取舍」 | 按「文件 / 函数 / 调用顺序」 |
| 配置 / 签名 | 作为「产品决策」点出（为什么这个值） | 当作正文主体逐字段罗列 |

### 3.3 量化红线

- 正文（§X.1–§X.4）出现**真实源码整段引用**（>10 行连续）或**逐函数走读** → 违规，应下沉到 §X.6。
- §X.3 最小示例超过 40 行、或复制真实函数体 → 违规，应改为合成骨架。
- 「重头戏」小节若超过 ~1.5 屏且主体在讲 prompt 文本 / 函数契约细节而非设计决策，降为黄档，建议拆出或后移。

## 4. 四维度评审清单

每次评审逐章打 **红 / 黄 / 绿**，并附证据（章节号 + 原文要点）与修改建议。

### 维度一 关键概念是否讲清（Concept）

- [ ] 每个新术语都有「它是什么 / 为什么需要 / 一句话直觉」？
- [ ] 易混边界是否被显式区分：`近似 vs 精确`、`硬条件 vs 软条件`、`前提 vs 事后过滤`、
      `可引用 vs 不可引用`、`召回 vs 引用`、`restaurant scope vs evidence scope`？
- [ ] 「坏 case 开场」是否真的制造了认知冲突，而非铺垫？
- [ ] 概念能否脱离代码独立理解（过 §3.1 三层测试）？

### 维度二 流程是否讲清（Flow）

- [ ] 是否有显式的「输入 → 处理 → 输出」链路（图 / 表 / 编号步骤）？
- [ ] 多步骤是否标了**顺序与依赖**（谁先于谁、谁依赖谁的产出）？
- [ ] 跨章节的流程是否在本文给出**最小连接**（或明确「见第 X 章」）？
- [ ] 失败 / 分支路径是否画出（不只 happy path）？

### 维度三 信息遗漏（Gap）

- [ ] 读者动手 / 理解全貌所需的前置是否补齐？
- [ ] 是否「提了名字但没展开」的关键概念（如六种文档只讲三种）？
- [ ] 数字 / 配置是否有出处且自洽？
- [ ] 是否缺「为什么不做 X」的反向说明（项目取舍）？
- [ ] 跨章节**主干（spine）**是否在某处被显式串成一张图 / 一张表？

### 维度四 过度深入 / 代码化（Over-deep）

- [ ] 过 §3 三层测试与信号对照表。
- [ ] 正文是否出现大段真实源码 / 逐函数走读？
- [ ] 是否把「配置项清单」「函数签名」当正文主体（应进 §X.6）？
- [ ] 是否为讲一个细节牺牲了主线节奏（重头戏是否过长、可拆）？

---

## 5. 评审输出格式

按章输出，每章四维度各给 红 / 黄 / 绿 + 一句证据 + 一条建议；章末汇总「重点问题」与
「修改建议清单（行动项）」。红 = 必修（概念错 / 主线被代码化 / 流程缺失导致无法动手）；
黄 = 建议（可补的概念、可优化的表达、潜在的读者混淆）；绿 = 达标，可注明亮点。
