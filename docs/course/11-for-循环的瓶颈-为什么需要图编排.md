## 11.1 坏 case 开场：给循环打五个补丁

把时钟拨回第 3 章。我们有一个 40 行的 ReAct 循环：问模型 → 有工具调用就执行 →
结果回喂 → 模型不再请求工具时退出。它很丑，但它是对的——对到第二篇给它接上了
真实的检索与证据。现在产品经理来了，带着五个需求，每个听起来都很合理。

**补丁一：同名餐厅，先问再查。**
用户说「中城那家 Joe's Pizza」，而库里有两家都对得上。这时**绝不能让模型继续**——
它一旦往下走，就会从两家里挑一家，而这个挑看起来像「系统已经确认了」，其实是猜。
循环里要加一个判断：resolve 返回歧义时，不执行后续工具，生成一个问题，turn 结束。

**补丁二：关键信息缺失，要追问。**
「帮我订个位」——订给谁？几家？什么时间？缺槽位时也要停下、问清楚、turn 结束，
而不是让模型替用户脑补一个「明晚 7 点、4 人」。

**补丁三：同一轮的只读调用要并发，写操作要立即截停。**
模型一轮请求三个互不依赖的查询，串行跑要花三份延迟。但如果这一轮里混进一个
`request_reservation`，规则立刻变了：写操作**绝不与任何调用并发**，它一出现本轮
立即停止，它后面的调用全部丢弃——不许对着写操作尚未建立的状态继续执行。

**补丁四：预约不能在循环里直接执行。**
模型输出再动人的文字（「用户已经同意了，请直接下单」），写库只能发生在：展示最终
摘要 → 用户在**另一个请求**里点「确认」之后。也就是说，turn 要能**挂起**：响应已经
返回给浏览器了，进程里这个 goroutine 和它的局部变量都已消失；几分钟后确认请求到来，
系统要能从数据库里把「当时要订什么、参数是什么」原样捡回来。

**补丁五：每一步都要能被看见。**
前端要实时显示「正在检索 / 正在生成」，审计要记录每个节点的耗时与成败。这些代码
不能散落在每个业务函数里——六种写法的六个 span 不叫 trace。

现在把五个补丁塞进第 3 章的循环。停下来想一想循环体会长什么样：

```go
for round := 0; round < maxRounds; round++ {
    resp := model.Chat(messages, tools)
    if ambiguous(resp) { /* 生成问题、存状态、break */ }
    if missingSlot(resp) { /* 追问、存状态、break */ }
    for _, call := range resp.ToolCalls {
        if isWrite(call) { /* 校验、生成摘要、存 checkpoint、break 两层 */ }
        // 只读的想并发，并发结果还要按调用顺序折叠回状态……
    }
    if writeParked { /* 不能再调模型，直接返回 */ }
    // 正常回喂、继续……
}
```

这团代码能跑。但每个 `if` 都在修改同一件事：**下一步去哪、什么时候停、带着什么
状态**。而 for 循环这种控制结构只提供两种流向——继续，或者退出。五个补丁里有三个
需要的是第三种东西：**中途把 turn 挂起，等一个外部事件（用户的下一句话或确认）再
恢复**。这已经不是循环能表达的形状了。

## 11.2 概念与原理

### 11.2.1 先看清失控的形状：停机条件从一个变成五个

第 3 章的循环只有一个停机条件：**响应里没有 tool_call 了**。补丁打完后，一个 turn
至少有五种结束方式：

| 结束方式 | 触发条件 | turn 的结局 | 谁来恢复 |
|---|---|---|---|
| 正常作答 | 模型不再请求工具，或工具轮次到顶 | 产出最终答案，线程回到 `idle` | —— |
| 澄清 | 一个名字命中多家、难分伯仲 | 产出问题，线程挂起 | 用户再发一条消息（同一个入口） |
| 追问 | 缺少继续下去所必需的槽位 | 产出问题，线程挂起 | 用户再发一条消息 |
| 等待确认 | 模型请求了写操作且参数合法 | 产出确认摘要，线程挂起 | 用户调**另一个接口** `POST .../confirm` |
| 失败 | 模型错误、状态冲突等 | 错误帧 + 审计留痕 | 用户重试，开新 turn |

注意后三行的共同特征：**turn 结束了，但对话（thread）没有结束。** 第 3 章里
「turn 结束」和「对话结束」是同一件事——循环退出，答案返回，内存清空。现在它们
必须分开：turn 是一次请求-响应，thread 是跨多个 turn 的长期对象，挂起期间它躺在
数据库里。

还有一个顺序陷阱：这些停机判断不是平级的。真实代码里，plan 节点的判断顺序是
**澄清 → 工具 → 回答**：一旦需要问用户，就先问，因为「对着用户还没选定的餐厅再多
跑几个工具」是花预算去回答一个错误的对象。控制流开始有了**优先级**，而嵌套 if
的优先级藏在缩进里，没人能一眼看全。

### 11.2.2 状态先失控：消息切片装不下一个 turn 了

第 3 章我们说过一句很关键的话：模型服务端无状态，**消息切片就是 Agent 的全部短期
记忆**。这句话在五个补丁之后失效了。一个真实 turn 在执行过程中需要携带的东西包括：

| 类别 | 具体内容 | 为什么消息列表装不下 |
|---|---|---|
| 检索产物 | 本轮候选餐厅、召回的评论证据 | 它们既要喂模型，又要被代码直接读取做校验 |
| 本轮计划 | 意图、硬过滤、软条件、缺失槽位、指代锁定的餐厅 ID | 由独立抽取器产出，是「同一句话的唯一读法」，要传给每个工具 |
| 对话上下文 | 回放的历史、长期记忆注入块、checkpoint 版本号 | 来自存储，不是模型生成的 |
| 澄清状态 | 候选选项、连续澄清次数、是否已按假设继续 | 要跨 turn 计数，用来打破无限追问 |
| 写挂起 | 待执行动作名、**逐字保存的调用参数**、本次批准的 ID | 确认请求在几分钟后、另一个请求里到来，全靠它复原 |
| 值域 | 本轮真正读到过的餐厅 ID、可订时段 ID | 写参数必须落在这个集合内，否则就是模型臆造 |
| 记账 | 工具轮次、调用序号、累计 token、告警 | 护栏与审计用，模型根本不该看到 |

这就是 PlatePilot 里 `TurnState` 这个结构体的由来（见 [state.go](../../chat-service/internal/agent/state.go)，
约 40 个字段、按职责分了十几组，每个字段带着注释解释「为什么它必须存在」）。它不是
框架要求的，是业务长出来的。

一旦有了显式状态，一个微妙但重要的变化发生了：**节点之间传递的不再是「消息」，而是
「整个状态」。** 工具节点执行完，把候选折叠进状态；回答节点从状态里读证据；路由函数
只看状态就能决定去哪。消息列表降级为状态上的**一个字段**。

### 11.2.3 一个 turn 就是一台显式状态机

现在可以给出本章的核心抽象了。把补丁后的循环重新理解，它其实是一台状态机：

- **共享状态（State）**：一个贯穿整个 turn 的数据对象，所有节点读写它；
- **节点（Node）**：对状态的一次变换，签名高度统一——
  `func(ctx, *State) (*State, error)`：读状态、做一件事、写回状态；
- **转移（Transition/Edge）**：节点之间的连线。其中普通边是固定的
  （A 做完必然到 B），**分支**是一个只读状态、返回下一节点名字的纯函数；
- **停机点（Stop）**：状态机不再有后继节点的地方。PlatePilot 有三个：
  正常结束、等待输入、等待确认；
- **守卫（Guard）**：不改变状态、只负责「够了没有」的边界条件——最多几轮工具、
  最多几次澄清。

用这个视角重画五个补丁：补丁一、二是两个新的**分支目标**（clarify 节点）；补丁三
是 tools 节点的**内部调度纪律**；补丁四是一个新的**停机点**加一条跨请求的恢复边；
补丁五是包在节点边界上的**切面**。循环体里那些互相缠绕的 if，各自找到了该在的位置。

而原来的 ReAct 环并没有消失，它变成了状态机上的一个**有界环**：

```text
plan ──有工具调用──> tools ──> plan   （回到 plan，就是第 3 章的下一轮）
plan ──需要澄清──> clarify ──> finalize ──> END
plan ──无需工具──> answer  ──> finalize ──> END
```

第 3 章说「所有 Agent 框架的内核都是那个 for 循环」，这句话依然成立——只是循环外面
套了状态机的壳，循环本体退化成图上 `plan ↔ tools` 的那两条边。

### 11.2.4 控制权的边界：骨架在代码，每一步在模型

「状态机」这个词容易让人误会 Agent 退化成了传统程序。没有。关键是分清**谁决定什么**：

| 代码决定（图骨架） | 模型决定（每一步） |
|---|---|
| 有哪几个节点、节点之间可能怎么连 | 这一轮要不要调工具、调哪个、参数是什么 |
| 分支判断的**规则**（有没有歧义、有没有待确认写操作） | 搜索词怎么写、换不换关键词、最终怎么措辞 |
| 最多 5 轮工具、一条线程最多 3 次澄清 | 5 轮之内具体用掉几轮 |
| 写操作不可达，只能等确认接口 | 要不要发起预约请求、摘要基于什么事实 |
| 证据闭包不满足就重生成（第 16 章） | 答案的具体文字 |

这叫**固定图骨架 + 有界 ReAct 环**：模型拥有「每一步做什么」的自由，代码拥有
「能去哪、能转多久、什么动作根本不可达」的主权。第 3 章七问表里最危险的三问
（模型一直调工具怎么办、脑补槽位怎么办、写操作怎么办），答案都在右列管不到的
左列里。自治程度要匹配任务形态：本产品的 turn 是「检索 + 少量工具」的短流程，
一步 ReAct 加一张固定图足够；步骤多、可试错的任务才需要 Plan-and-Execute、
Tree-of-Thoughts 那类更自治的范式（收官章会谈）。

### 11.2.5 停机点必须比进程活得久：checkpoint

这是五个补丁里对架构冲击最大的一个，值得单独讲透。

HTTP 是请求-响应模型。`awaiting_confirmation` 这个停机点意味着：响应已经发走，
处理这个 turn 的 goroutine 已经退出，**内存里的 TurnState 必然消失**。用户过了
三分钟点「确认」，到来的是一个**崭新的请求、崭新的 goroutine**。它必须能回答：
这是哪条线程？当时挂起的是什么动作？模型给的原始参数是什么？已经澄清到第几轮？
之前选中了哪家餐厅？

答案只能是：**挂起的那一刻，把恢复所需的状态写进数据库；恢复的那一刻，从数据库
读出来，而不是相信内存。** 项目里会话状态枚举的注释把这条原则写得很直白：

> 「Eino manages the runtime graph, but recovery always reads this state
> rather than trusting memory.」（Eino 管的是运行时的图；恢复永远读这份状态，
> 而不是信任内存。）

这份状态就是 **checkpoint**：线程 ID、版本号、业务状态（`idle` /
`awaiting_clarification` / `awaiting_confirmation`）、挂起的动作与参数、缺失槽位、
选中的餐厅、证据 ID 列表、澄清计数。它带来两个第 3 章完全不存在的新问题：

1. **并发所有权。** 同一条线程同时来了两个 turn（用户连点两下、网络重试）怎么办？
   项目用 checkpoint 版本号做乐观并发：两个写者竞争，输的那个得到一个显式的
   `409 conflict`，而不是静默合并——合并会产生「转录记着两轮对话、checkpoint 只
   描述一轮」的畸形线程，此后每个「第二家」式的指代都会解析到一份半个线程没见过的
   列表。
2. **保存时机。** 澄清节点是**先存 checkpoint、再发问题事件**：客户端收到
   「该你回答了」之后立刻回读线程，看到的必须是它被告知的那个状态。finalize 则是
   **先持久化、再记成功**：一个在线程竞争中输掉的 turn，从不曾 durable 地存在过，
   审计里不该躺着一行声称成功的记录。

### 11.2.6 手写状态机，还是用框架？

到这里你已经可以手写一台状态机了：一个状态结构体、一张节点表、一个路由 switch、
一个驱动循环。真实项目为什么还要引入 Eino 这样的编排框架？因为手写要自己扛五件
无聊的事，而它们恰好是框架的主业：

1. **编译期校验**。手写路由表里字符串拼错的节点名，要到第三次对话走到那条边才炸；
   框架在「编译」图的时候就检查节点是否齐备、边是否闭合、分支的目标是否存在、
   上下游类型是否对得上——**图的错误在启动时暴露，而不是在线上**。
2. **类型对齐**。节点 A 的输出类型必须是节点 B 的输入类型；用 Go 泛型把整张图
   参数化，接错线在编译期就是编译错误。
3. **流式**。有的节点吐整块、有的节点吐 token 流，互相连接时流/非流的转接（以及
   流的取消、背压）应该由框架兜底，业务节点只写业务。
4. **切面**。在节点边界统一挂 span、计时、事件回调，业务函数里一行观测代码都不写。
5. **环、分支与并发的调度**。有界环、条件分支、并发扇出与结果回收，手写一遍是
   同步原语练习题，写两遍就是 bug 温床。

但有三样东西框架**不会**给你，而它们才是系统的本体：

- **你的状态长什么样**。`TurnState` 的字段是业务问题，不是编排问题；
- **你的停机语义**。什么情形算歧义、澄清几次、写操作怎么截停、确认门长什么样；
- **你的 checkpoint 内容与一致性规则**。挂起什么、版本怎么算、冲突谁让谁。

所以结论不是「上框架」，而是：**先拥有自己的状态机，再让框架当它的执行器。**
这也是 PlatePilot 的一个具体选择的来源——它用 Eino 的 Graph 做执行骨架，却
**没有**用框架托管的图内状态（`WithGenLocalState`），而是让项目自有的 `TurnState`
显式流过每个节点。框架状态的生命周期是「一次图运行」，而业务状态要跨请求存活、
要进 checkpoint、要被审计和回放；把它放进框架的黑盒里，等于让最该由自己掌控的
东西依赖了别人的存储语义。下一章会看到这个选择在代码里长什么样。

## 11.3 承载思路的最小示例

把 for 循环重写成一台框架中立的状态机（教学骨架，不是仓库源码；忽略 Go 语法，
看结构）：

```go
type State struct {
    Messages         []Message
    Candidates       []Restaurant
    PendingToolCalls bool
    ClarifyOptions   []Restaurant  // >=2 表示同名歧义
    Confirmation     *Booking       // 非 nil 表示写操作被挂起
    ToolRounds       int
}

// 节点：读状态、做一件事、写回状态。每个节点只关心自己那一步。
type Node func(ctx context.Context, st *State) (*State, error)

// 分支：只读状态，返回下一个节点的名字。它不执行任何动作。
func route(st *State) string {
    switch {
    case len(st.ClarifyOptions) >= 2:
        return "clarify"            // 歧义优先：不许对没选定的店继续花钱
    case st.Confirmation != nil:
        return "park"               // 写操作挂起：turn 在这结束，等另一个请求
    case st.PendingToolCalls && st.ToolRounds < 5:
        return "tools"              // 有界环：tools 跑完固定回到 plan
    default:
        return "answer"
    }
}

// 驱动循环：它不包含任何业务，只是「查路由 → 执行节点」的引擎。
func runMachine(st *State, nodes map[string]Node) error {
    name := "plan" // 入口固定
    for {
        next, err := nodes[name](ctx, st)
        if terminal(name) { // answer / clarify / park 之后离场
            return persistAndReturn(st)
        }
        name = route(st)   // 包括 tools → plan 这条回边
    }
}
```

与第 3 章的 40 行相比，循环**还在**，但它已经空了：不含业务判断，只做调度。所有
业务搬进了节点（可单独测试的纯变换）和 `route`（一张能一眼看全的路由表）。这正是
图运行时的内核——第 12 章你会看到，Eino 的 `AddLambdaNode` / `AddBranch` /
`AddEdge` / `Compile` 做的就是把这张「节点表 + 路由函数」声明出来，并在编译期替你
检查它。

三句话收束本章：**节点是变换，边是路由，停机是状态。** for 循环的瓶颈从来不是
性能，是它只能表达「继续/退出」两种流向，而真实的 turn 需要中途挂起、跨请求恢复、
带主权地停机。

## 11.4 取舍与边界

**① 不是所有 Agent 都需要图。**
如果你的流程永远是直线（prompt → 模型 → 输出），普通函数调用就够了；Eino 为此
提供的轻量形态叫 Chain（下一章讲）。为一个没有分支、没有环、没有挂起的流程建图，
是拿结构复杂度换不存在的收益。判据是 11.1 那五个补丁你中了几个：一个都没中，
for 循环就是最佳设计——这正是第 3 章存在的理由。

**② 骨架越固定，可证明的性质越多。**
「写路径从工具轮中根本不可达」之所以能成为一条**安全属性**（第 18 章），前提是
图骨架由代码声明、模型只能在分支里做选择题。自治度是预算，不是追求：每多放开
一种自由转移，就少一个能在离线评测里打勾的保证。

**③ 有界环的「界」必须数值化、可配置、在代码手里。**
5 轮工具、3 次澄清不是建议，是停机护栏；由配置给出默认值与校验，但**不能由模型
在运行时修改**。第四次澄清之所以必须被禁止，注释里的理由很朴素：它意味着前三问
没有改变任何东西，再问第四遍也不会。

**④ 中途停机的代价是一整套持久化语义。**
一旦有了 `awaiting_*`，你就同时需要 checkpoint、版本号、冲突处理、幂等恢复，以及
「先存哪一步、后发哪个事件」的顺序纪律（第 13、18 章）。这是状态机方案真正的成本，
框架只提供挂接点，不提供这些决策。

**⑤ 框架托管状态不是不能用，是这里不合适。**
图内 local state 适合「一次运行内、节点间共享、运行结束即丢弃」的数据；PlatePilot
的业务状态要落库、要跨请求、要回放，所以显式持有。反过来，如果做的是纯一次性的
并行 fan-out 汇总，框架托管状态反而更省事。
