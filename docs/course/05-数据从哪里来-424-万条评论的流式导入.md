## 5.1 坏 case 开场：为什么不能让模型「凭记忆」回答

第 3 章那个 40 行的 Agent，第一次撞的墙就是幻觉：搜索函数返回空，它不停下来
说「我没查到」，而是编出一家不存在的店、一段「很安静、服务很好」的点评。

第 1 章的结论是：**幻觉不能靠提示词治，只能靠「把真实数据喂进上下文」+「让每个
结论都能指回一条真实评论」来治。** 这句话听起来像一句产品口号，落到工程上却是本
章的全部工作量：

> 要让模型「有据可依」，第一件事是**先有据**。

「据」是什么形状？不是一段说明文档，而是能被检索、能被定位、能被引用的**结构化
语料**——一家里有哪些餐厅、每家的菜系价格营业时间、每条评论的原文与作者评分时间。
而这份语料的原始形态，是 Google Local 纽约市的一份公开切片：

| 原始文件 | 体量 | 内容 |
|---|---|---|
| `meta-New_York.json.gz` | 27.2 万行 POI | 店名、类别、均分、价格档、坐标、营业时间、MISC 属性 |
| `review-New_York.json.gz` | 约 2.5 GB、3350 万行 | 每条评论的作者、评分、时间、正文 |

先记住一件事：**这是 2021-09-01 的历史快照**（`SnapshotObservedAt`），不是「最新数据」。
后面每条评论、每家店的观测时间都取这个值，而不是导入那一天。第 9 章会把它变成一条硬
规矩：引用必须带观测时间，且**不能把「生成时间」当成「观察时间」**——那会让所有基于
时间的新鲜度声明朝着「看起来更新」的方向撒谎。

问题从第一秒就来了。**这份文件你没法 `json.Unmarshal`。** 一个 2.5 GB 的 JSON
数组读进内存是什么后果？先不说内存，实际这份数据根本不是一个合法 JSON 数组——它是
**gzip 压缩的 JSONL**：整个文件被 gzip 压过，解压后是**一行一条 JSON 记录**的流。

本章要回答这一类问题：**面对一份装不进内存、还压着 gzip 的真实语料，怎么把它可靠地
变成数据库里可以被检索的证据。** 这条链路里藏着一堆看起来琐碎、但每一处决定后面所有
章节能不能成立的决策。

## 5.2 概念与原理

### 5.2.1 大文件的正确打开方式：流式，而不是全量

「读一个大文件」在三类做法之间，选择取决于一个朴素的事实：**你能不能把它放进内存。**

```text
① 全量读入：os.ReadFile → json.Unmarshal
   内存 ≈ 文件大小 × 常数倍（解压后可能还要再翻几倍）
   2.5 GB gzip → 解压后十几 GB → 单机直接 OOM

② 一次性解压到磁盘，再逐行读
   可以跑，但要先落一份十几 GB 的中间文件，磁盘换内存

③ 流式：边解压边逐行解析，一行处理完就丢
   内存 ≈ 一行 + 缓冲区的常数，与文件大小无关 ← 唯一可扩展的做法
```

第 ③ 种就是**流式处理（streaming）**：把「文件」看成一个**惰性的、一次只吐一行的
数据源**，而不是一个可以随便下标访问的数组。它带来的约束和它带来的好处一样重要：

- **只能顺序读一遍。** 没有 `Seek`，不能回头。所以任何需要「看完整个文件再决定」
  的逻辑，都必须改成**在线（online）累积**的形式；
- **进度只能按已消费的字节量估计。** gzip 解压后总字节数、总行数在读完之前都**未知**
  （gzip 尾部才有原始长度，且很多生产者不写），所以「进度 40%」是靠**已读压缩字节数
  ÷ 文件大小**估出来的，不是数出来的；
- **单行仍然可能很大。** JSONL 的「一行」没有上界，一条超长评论能把默认的 64 KB
  `bufio.Scanner` 直接撑爆。

这三条约束会在 §5.3 里变成三行真实的代码。

### 5.2.2 清洗（curate）：把「能存」变成「能查」

把 JSON 一行行解析出来只是完成任务的一半。原始数据里塞满了**对检索毫无用处、
甚至会捣乱**的东西，导入之前必须先「清洗」。这里的每一个决策，本质都在回答同一个
问题：**这条字段将来会不会被用来筛选、排序或引用？**

**① 菜系归一（cuisine）**

Google 的 `category` 是一个自由字符串（`"pizza restaurant"`、`"Italian restaurant"`、
`"Restaurants"`……），同一件事有好几种写法，还有大量「Restaurants」这种没有信息量的
泛化类别。检索要按菜系过滤，就必须把它折叠成一个**受控词表**：

```text
"pizza restaurant"  → {pizza, italian}
"Pizza Delivery"    → {pizza}
"Japanese restaurant" → {japanese}
"Restaurants"       → {}        ← 泛化类别，丢弃
```

做法是一张显式映射表（仓库里 40 多条规则）+ 泛化前缀过滤。这里没有 NLP、没有模糊
匹配——**映射表就是产品决策**，它决定了「用户说意大利菜时能搜到什么」。做成显式表
而不是算法，是为了可审计：查出来不对，你能直接看是哪条规则错了。

**② 价格等级（price level）**

原始价格字段是 `"$$"` 这样的符号串。检索要支持「人均中等」这种过滤，就得有数字等级。
但这里有一个**反直觉的取舍**：

> 价格等级**不是**一张映射表，而是一条「严格才认，否则 `nil`」的规则。

规则是：**非空、全部是 `$`、长度 1–4，才算 `level = len`；其他一律 `nil`。** 为什么
这么保守？因为过滤是**硬条件**——把 `"$$-$$$$"` 这种含歧义的值硬凑成某个等级，会让
「人均 2 档」的查询返回错误结果，用户看不出是数据错了。**宁可缺一个值（`nil`），也
不要把不确定的值猜成一个确定值**——这是「硬过滤必须永远正确」这条纪律在数据侧的第一
次露面，第 8、10 章会反复回到它。

**③ 营业时间（hours）**

原始营业时间是按周的字符串表（`"Monday: 11:00 AM – 10:00 PM"`）。要能被程序判断
「现在开门吗」，得归一成**分钟数**：`{weekday, open_minute, close_minute, is_closed}`。
两个坑：

- **跨午夜**：`11:00 AM – 2:00 AM` 的关门时间在数值上**小于**开门时间，要加一整天
  修正（`close ≤ open` 时 `close += 24×60`）；
- `"24 hours"` 要映射成 `0..1440`（整天），而不是解析失败。

**④ PII 脱敏：评论是数据，作者是隐私**

评论正文里可能出现邮箱、电话，身份字段（`user_id`、`name`）更是直接的隐私。做法是
**两层**：正文用正则替换成占位符（`[redacted-email]` / `[redacted-phone]`），并**剥掉
控制字符**（尤其 NUL——PostgreSQL 会直接拒绝，报 SQLSTATE 22021）；身份字段在写盘
阶段就**整列清空**。为什么 PII 要在**写盘阶段**就清？因为一旦带进数据库，后面所有
「导出」「备份」「调试 dump」都会带着它，清理点的位置比清理动作本身更重要。

**⑤ 行政区：点-面判定，以及一个 10.2% vs 24.1% 的故事**

「曼哈顿的意大利菜」这种查询，需要知道每家餐厅属于哪个行政区。原始数据只有经纬度，
没有行政区字段。最省事的做法是**包围盒**：给五个区各画一个矩形，点落在哪个盒子里就
算哪个区。

省事，但**错得离谱**。真实的纽约五个区边界是**不规则的多边形**（尤其布鲁克林和皇后
区交界的锯齿、曼哈顿和布朗克斯之间的大片水域），矩形近似会把边界附近的点判错。
仓库里做了实测，把两种判定在同一份语料上对比：

| 判定方式 | 与真实边界的差异率 |
|---|---|
| 真实边界多边形（点-面判定） | 基准 |
| 矩形包围盒近似 | 全量 **10.2%** 判错 / 存活行 **24.1%** 判错 |

也就是说，**用包围盒会错掉近四分之一**。这个数字必须有真实边界几何来兜，做法是
**自实现的射线法（crossing number）点-面判定**——不引第三方几何库，因为这一处逻辑
简单到可以自己写且必须可测。几何文件还带一个 SHA256 指纹（`9c271db1…`，版本号
`nyc-borough-wh2p-dxnf-26b`），**指纹对不上就拒绝用**；文件真的缺失时，系统会**降级**
回包围盒并**打警告**——正式跑批用 `--require-boundaries` 关掉这个降级，让缺文件直接
失败，而不是悄悄用错数据。

> 这里有一个通用教训：**「近似」是可以接受的，但必须被显式标注为降级。** 包围盒不是
> 不能用，是不能在没人知道的情况下被用。

**⑥ 打分（score）：决定「哪条更值得看」**

语料太大，搜索不可能每次都扫全库。需要给每家餐厅算一个**知识分（knowledge score）**，
让「信息更全、更值得优先看」的店排在前面。它是一个可解释的加权和：有没有描述、
有多少条评论（`log10(1+n)` 压缩，避免评论多的店一家独大）、属性是否完整……
值得注意的是**永久停业的店直接扣到 -100**——它们不是「低分」，是**应该被排除**，
用一个大负分表达「几乎不可能被选上」。

**⑦ 去重与幂等**

最后一条，也是最容易在「重跑」时咬人的一条：**这份导入必须可以反复跑，且结果一致。**

- **主键由数据库生成**（`bigint GENERATED BY DEFAULT AS IDENTITY`），应用**从不**
  自己造 ID——这消除了「重跑时 ID 漂移」这一类最难查的 bug；
- 餐厅用 `source_record_id`（Google 的 `gmap_id`）做 **upsert 冲突键**：重跑是更新，
  不是插入重复；
- 评论用**四列唯一键** `(restaurant_id, text_hash, rating, reviewed_at)` 去重。

四列里只有 `text_hash` 是**哈希列**（评论正文的 sha256），另外三列是原始字段。四列
**合起来**才是幂等键——它回答的是「这两行是不是同一条评论」，不是四个各自独立的身份
维度；单独拿 `restaurant_id` 或 `rating` 去查，什么都定位不到。

关于评论唯一键有一个值得记住的细节：早期设计用的是 **sha256(`gmap_id`+`user_id`+`time`+`text_hash`)**
的四段拼接。项目在 **415 万行全量**上对比过新旧两种键——**选出了完全相同的行，0 组差异**。
最终选了**四列**而不是**一列哈希**，理由是前者更**可读、可索引、可调试**：数据库里能
直接 `WHERE restaurant_id = ? AND text_hash = ?` 定位，不用先去猜哈希怎么算的。工程上，
「两个方案等价时选更可解释的那个」通常是对的。

### 5.2.3 prefilter：在 join 之前过滤，省掉小时级写入

到这里，一个天真的流程是：**把所有评论导入数据库，再和餐厅表 join，把不相关的删掉。**

算一下这笔账就发现它荒谬：3350 万条评论里，**只有约 12.7% 是可导入的**——大部分评论
对应的餐厅根本不在 NYC 服务区里（约 74% 落在服务区外），剩下的还有相当一部分
**没有正文文本**。为了留下那 12.7%，你愿意先写进去 3350 万行、再删掉 87.3% 吗？

**prefilter（预过滤）** 的思想极其朴素：**把过滤放到最便宜的一步去做。**

```text
朴素做法：  3350 万行 → 全部写库 → join → 删除 → 剩 424 万
prefilter： 3350 万行 → 边读边判断 → 只写 424 万
```

差别不是「快一点」，是**数量级**：数据库写入、索引维护、事务日志，全是按行数计的
重活；把 87.3% 的行挡在数据库之外，省下的是**小时级的写入**。

prefilter 还有一个工程上很值得抄的细节：**输出用临时文件 + 原子 rename**。它边处理边
写一个新文件（`review-filtered.json.gz`），全部成功后才 rename 成最终名。中途崩了，
你不会得到一个「看起来完整、其实截断」的产物——**半成品文件比没有文件更危险**。

### 5.2.4 为什么一个 PostgreSQL 扛四件事

语料落在 PostgreSQL 里，而检索需要四种完全不同的查询能力：

| 查询形态 | 例子 | 数据库能力 |
|---|---|---|
| 结构化等值/集合过滤 | `borough = 'manhattan' AND price IN (1,2)` | 普通 **btree** 索引 |
| 地理范围 | 「离某点 500 米内」 | **PostGIS** GiST 索引 |
| 语义近邻 | 「安静的意大利菜」 | **pgvector** HNSW 索引 |
| 模糊文本 | 「Sbar」（店名记不全） | **pg_trgm** 三元组索引 |

「四个能力一个库」是一个**刻意的取舍**，不是「图省事」：

- **好处**：一次连接、一个事务、一套备份、一份 schema。更重要的是——**「硬过滤
  先于向量召回」这条纪律（第 7 章的重头戏）只有在过滤和向量在同一个引擎里才成立**。
  如果结构化过滤在 Postgres、向量检索在专用向量库，你就得先把过滤结果在两个系统间
  搬运，或者忍受「先向量召回、再回 Postgres 过滤」——后者会把第 7 章那个 HNSW 事故
  在最糟糕的地方复现。
- **代价**：一个库要同时调 btree、GiST、HNSW、GIN 四种索引的规划，SQL 会更复杂；
  向量检索的极限性能不如专用向量库。
- **什么时候要重新考虑**：语料或 QPS 涨到 Postgres 扛不住、或者需要跨库分布式向量
  检索时，才值得拆。

还有一个很「运维」的取舍写在部署里：本地用的 Postgres 镜像是**自建的**，因为
**没有任何一个已发布镜像同时带 arm64 的 pgvector 和 PostGIS**（官方 pgvector 镜像
不含 PostGIS）。于是镜像基于 `pgvector/pgvector:0.8.6-pg17-trixie` 再装
`postgresql-17-postgis-3`。这类「生态拼图」问题在真实项目里很常见，写出来是因为它
恰好说明：**选型不只是选库，还包括它周边能不能装得起来。**

### 5.2.5 四个导入阶段：谁依赖谁

`import` 命令有一个 `--stage` 参数，取值 `meta|review|stats|score|all`。它不是
「跑哪一段都行」的开关——四个阶段是**单向依赖**的，顺序错了不会报错，只会得到一份
自相矛盾的语料：

| 阶段 | 读什么 | 写什么 | 为什么必须排在下一段之前 |
|---|---|---|---|
| `meta` | meta 文件 | `restaurants`（含行政区判定） | 后三个阶段都以餐厅行为锚点 |
| `review` | 评论文件（通常先过 prefilter） | `reviews` | `stats` 只能聚合**已经入库**的评论 |
| `stats` | `reviews` 的聚合 | 回填每店评论数与平均分 | `score` 的「评论数量」项读的就是这两个值 |
| `score` | `restaurants` | `knowledge_score` + 选出活跃集 | 知识文档只为活跃集生成（`SelectForDemo`），所以它必须早于 `build-documents` |

`--stage=all` 就是按 `meta → review → stats → score` 串起来跑，任何一段失败即中止；
已提交的阶段会保留，重跑是幂等的（§5.2.2 的 ⑦）。全量语料上的实测耗时约为
**8.6s / 281s / 32s / 5.3s**——重活全在 `review`，而它之所以只有 281 秒，正是
prefilter 把 87% 的行挡在了库外。

导入四段跑完之后，才轮到知识侧的两步：`build-documents --scope=restaurant` 与
`--scope=evidence`（两个 scope 分别构建），最后 `embed` 把文档变成向量。

## 5.3 承载思路的最小示例

把 §5.2 的三条约束落成伪代码。以下片段是**教学骨架**，不是仓库源码——它只表达
「流式逐行读 + 单行上限 + 字节进度」这三件事的形状：

```go
func streamJSONL(path string, handle func(line []byte) error) error {
    f, _ := os.Open(path)
    defer f.Close()

    gz, err := gzip.NewReader(f) // gzip 不可 Seek，只能顺流
    if err != nil {
        return err
    }
    defer gz.Close()

    // 关键：抬高单行上限（默认 64KB 会被超长评论撑爆）
    sc := bufio.NewScanner(gz)
    sc.Buffer(make([]byte, 0, 1<<20), 16<<20) // 上限 16 MiB

    for sc.Scan() {          // 一行一行吐，一行处理完就丢
        if err := handle(sc.Bytes()); err != nil {
            return err
        }
    }
    return sc.Err()
}
```

三个细节各自对应 §5.2.1 的一条约束：

1. **`gzip.NewReader` + `bufio.Scanner`**：边解压边逐行，内存与文件大小无关；
2. **`sc.Buffer(_, 16<<20)`**：把单行上限抬到 16 MiB，因为 JSONL 的「一行」没有上界；
3. **进度用已读压缩字节数估**：因为 gzip 不能 seek、解压后总行数未知，
   「到哪了」只能靠字节量近似——比如「已读 40% 压缩字节」。

而「清洗」的取舍，浓缩成一条可对照的规则（同样是示意）：

```go
// 严格才认，否则 nil —— 宁可缺值，不猜值
func PriceLevel(raw string) *int {
    if raw == "" || len(raw) > 4 { return nil }
    for _, c := range raw {
        if c != '$' { return nil } // "$$-$$$$"、"Free" 一律不算
    }
    n := len(raw)
    return &n
}
```

这段代码的全部价值不在实现，而在**它拒绝做什么**：它拒绝把歧义数据拟合成一个确定值。
第 7、8、10 章里所有「硬过滤必须 100% 正确」的纪律，源头都在这里。

## 5.4 取舍与边界

- **流式是唯一可扩展的选择，但它买来了「只能顺序读一遍」的约束。** 任何「需要全量
  视角」的逻辑（比如统计全局分布）都不能在流里临时决定，必须变成在线累积或拆成两趟。
- **清洗规则是产品决策，不是数据细节。** 菜系映射表、价格等级规则、行政区判定，
  这几个「小」决策直接决定了用户能搜到什么、搜得对不对。把它们做成**显式、可测、
  可审计**的表，比写成聪明的算法重要。
- **`nil` 优于猜测。** 价格等级、缺失字段一律留空，不在数据侧替用户做「合理推断」。
  推断错了，错误会以「结果不对但看起来正常」的形式出现，最难查。
- **近似必须标注为降级。** 包围盒判定能用，但要打警告、且能被 `--require-boundaries`
  关掉。真实边界文件缺失时的行为，是整个语料行政区标注的上游依赖，动它要有意识。
- **一个库扛四件事的边界条件**：单库的便利建立在「过滤与向量同引擎」之上；当 QPS、
  语料规模或跨库需求突破 Postgres 的舒适区时，这套取舍要重新评估——但那是规模问题，
  不是现在的问题。
- **幂等是「能重跑」的前提，而「能重跑」是数据管道的地基。** 导入脚本必须假设
  「同一份输入跑十遍」，结果和跑一遍一样。数据库生成主键、显式冲突键、四列唯一索引，
  都是为这一条服务的。
- **`data/processed/` 是本地产物。** 重导 restaurants 之后，prefilter 必须重跑——
  这两个产物之间有顺序依赖，不能只更新其中一个。

## 5.5 课后实验

**跑（大部分不需要模型，需要库）**

```bash
make pg-up          # 起本地 Postgres（自带 pgvector + PostGIS）
make migrate        # = make -C data-pipeline migrate，建 schema 与索引
# data-pipeline 是 CLI（没有 make run 这个 target），直接用子命令 + flag。
# 先在 data-pipeline/ 准备好 .env（可 cp .env.example .env，至少要有 POSTGRES_DSN）。
cd data-pipeline
# 只跑导入：--limit 限制「从源文件读的行数」；--stage 取值 meta|review|stats|score|all
go run . import --stage=meta --limit=5000
go run . prefilter      # 观察 33.5M → 4.24M 的收缩与耗时
```

**读 EXPLAIN（看四种索引真的在干活）**

```sql
-- 结构化：应该走 btree
EXPLAIN ANALYZE SELECT * FROM restaurants WHERE borough = 'manhattan' LIMIT 10;
-- 向量：应该走 HNSW（第 7 章细讲为什么这一句是关键）
EXPLAIN ANALYZE SELECT * FROM knowledge_documents
  WHERE is_active ORDER BY embedding <=> $1 LIMIT 10;
```

**改配置 / 改行为，观察变化**

- 把 prefilter 加上 `--keep-short-text` 再跑，对照 §5.2.3：被过滤掉的行数发生了什么变化？
  「12.7% 可导入」里有多少是卡在「没有正文」这一条？
- 故意把 `data/boundaries/` 下的几何文件挪走再跑 prefilter，观察它如何**降级为包围盒
  并打警告**；再加 `--require-boundaries` 看它如何**直接失败**。这就是「降级 vs 拒绝」。
- 对着 `curate/cuisine.go` 的映射表，想一个你觉得应该归一但表里没有的 `category`，
  加一条规则、跑单元测试——体会「清洗规则是产品决策」是什么手感。

## 5.6 参考代码与目录

> 本节是本章涉及的真实实现清单。正文只讲思路，想深入实现的读者从这里进去。

**流式读取（大文件的正确打开方式）**

- [data-pipeline/internal/pipeline/raw/jsonl.go](../../data-pipeline/internal/pipeline/raw/jsonl.go)：
  面向「gzip + 3300 万行」的流式读取器，文件头注释写明「never reads a whole file into
  memory: callers iterate line by line and decode on demand」；`maxLineBytes = 16 << 20`
  （16 MiB）；`gzip.NewReader` + `bufio.Scanner`；进度按**已读压缩字节数**估计。
- [data-pipeline/internal/pipeline/raw/meta.go](../../data-pipeline/internal/pipeline/raw/meta.go)、
  [raw/review.go](../../data-pipeline/internal/pipeline/raw/review.go)：两类原始记录的解码。

**导入与幂等**

- [data-pipeline/internal/pipeline/import.go](../../data-pipeline/internal/pipeline/import.go)：
  文件名常量（`meta-New_York.json.gz` / `review-New_York.json.gz`）、快照时间
  `SnapshotObservedAt = 2021-09-01`、`PIPELINE_BATCH_SIZE`（默认 1000）；
  `--limit` 限制「从源文件读的行数」而非写入量。
- [prefilter.go](../../data-pipeline/internal/pipeline/prefilter.go)：3350 万行 → 424 万行、
  308 MB、约 3m15s；输出 `review-filtered.json.gz`，`.partial` 临时文件 + 原子 rename；
  `--keep-short-text` 开关。
- [shared/store/postgres/migrations/0001_init.sql](../../shared/store/postgres/migrations/0001_init.sql)：
  `restaurants` / `reviews` 表；主键 `bigint GENERATED BY DEFAULT AS IDENTITY`；
  评论四列唯一键 `(restaurant_id, text_hash, rating, reviewed_at)`（约 184–186 行）；
  `source_record_id`（Google `gmap_id`）保持 `text`。

**清洗（curate）**

- [curate/cuisine.go](../../data-pipeline/internal/pipeline/curate/cuisine.go)：菜系归一映射表
  （40 多条规则）+ 泛化前缀过滤 + slug。
- [curate/price.go](../../data-pipeline/internal/pipeline/curate/price.go)：价格等级的
  「非空、全 `$`、长度 1–4 → `len`，否则 `nil`」规则。
- [curate/hours.go](../../data-pipeline/internal/pipeline/curate/hours.go)：跨午夜修正
  （`close ≤ open` 时 +24h）、`"24 hours"` → 0..1440。
- [curate/pii.go](../../data-pipeline/internal/pipeline/curate/pii.go)：`ScrubPII`
  （邮箱/电话占位符、去控制字符，NUL 必去）。
- [curate/boundary.go](../../data-pipeline/internal/pipeline/curate/boundary.go)、
  [curate/geo.go](../../data-pipeline/internal/pipeline/curate/geo.go)：真实边界
  **射线法点-面判定**（自实现，无第三方几何库）；`DefaultBoundarySHA256="9c271db1…"`、
  版本 `nyc-borough-wh2p-dxnf-26b`；缺失时降级包围盒并 Warn。
- [curate/score.go](../../data-pipeline/internal/pipeline/curate/score.go)：`KnowledgeScore`
  各加分项、`log10(1+n)×1.5`；永久停业 −100；选择确定性（分数降序、`source_record_id` 升序）。

**一次真实的取舍记录（数字来自实测）**

| 数字 | 含义 |
|---|---|
| 约 2.5 GB / 3350 万行 | 原始评论文件（gzip JSONL） |
| **12.7%** | 可导入比例（多数餐厅在服务区外，其余部分无正文） |
| **424 万行 / 308 MB / 3m15s** | prefilter 产物规模与耗时 |
| **10.2% / 24.1%** | 包围盒 vs 真实边界的判错率（全量 / 存活行） |
| 27.2 万 → 3.6 万 | 原始 meta 行 → 入库餐厅数 |
| **0 组差异** | 旧哈希键与新四列键在 415 万行上的对比结果 |
