## 1.1 坏 case 开场：模型会「认真地骗你」

假设我们现在什么数据工程都没做，直接把用户问题发给一个聊天模型：

> **用户**：推荐一家曼哈顿中城安静的意大利菜，最好能约会。
>
> **模型**（训练语料里恰好有印象）：推荐您尝试 *Bella Italia Trattoria*，
> 位于曼哈顿中城，评分 4.7，以浪漫安静的氛围闻名……

听起来无懈可击。问题是：**这家店可能根本不存在**；就算存在，评分和「安静」也
可能是编的。更隐蔽的是第二种情况——店是真的，但「安静、适合约会」是模型凭
词频联想补出来的，没有任何一条评论这么说过。

把餐厅数据塞进 prompt 能解决吗？能解决一部分，但你很快会遇到：

- 检索本身就会错（找店名精确匹配失败、行政区被「语义相近」带偏）；
- 模型会引用你没给它的证据 ID；
- 模型会拿商家记录里不存在的字段「答题」（营业时间、有没有停车位）。

在动手解决这些之前，先回答两个更上游的问题：**我们手里的数据到底是什么形状？
我们到底要让 Agent 做什么、不做什么？** 这就是本章。

## 1.2 数据盘点：两份 gzip JSONL

数据来自 Google Local（UCSD McAuley lab 发布，cite-only 授权）。两个文件都是
**gzip 压缩的 JSONL**——每行一个 JSON 对象，不是一个大 JSON 数组。这个格式
细节不是小事：2.5 GB 的文件意味着永远不可能一次性读进内存解析，只能边解压边
逐行读（第 5 章的第一件工程事）。

### 1.2.1 Meta：POI 快照记录

Meta 是「地点」的快照，一家店一行。它的字段和各自的脏法，是后面全部清洗工作
的需求来源：

| 字段 | 形状 | 说明 | 脏在哪 |
|---|---|---|---|
| `name` / `address` | 文本 / 可空文本 | 店名与地址 | address 可空 |
| `gmap_id` | 文本 | Google 的外部稳定 ID | 形状不归我们管，全程当不透明字符串 |
| `description` | 可空文本 | 短描述 | 可空 |
| `latitude` / `longitude` | 可空数值 | 坐标 | 可空，是行政区判定的唯一依据 |
| `category` | 字符串数组 | 如 `["Pizza restaurant", "Restaurant"]` | 一店多类、层级混乱、误匹配 |
| `avg_rating` | 可空数值 | 平均评分 | 可空 |
| `num_of_reviews` | 可空整数 | 评论数 | **头部有截顶风险**（demo 里多家是 9998），不能当精确值 |
| `price` | 可空文本 | `$`、`$$` | 少数行是异常货币字符 |
| `hours` | 二维字符串数组 | `[["Monday","11AM–10PM"]]` | 格式是给人看的文本，要解析 |
| `MISC` | 对象 | 属性主题 → 值 | 值可能是数组、裸字符串或混合 |
| `state` | 可空文本 | `Open` / `Closed` / `Permanently closed` | 2021 快照状态 |
| `relative_results` / `url` | — | 近邻 POI、Google Maps URL | 本期未用 |

这里有两个值得记住的**数据工程原则**，比任何单个字段都重要：

1. **一个形状奇怪的属性，永远不许连累一家本来合法的餐厅。** 比如 `MISC` 大多数
   值是字符串数组，但也会遇到裸字符串——读不懂的值直接忽略，而不是让整行解析
   失败。导入 27 万行数据时，「宽容解析、记录异常、继续前进」是唯一可行的姿态。
2. **数据带着来源和时间。** `MISC` 里能挖出十几个属性主题（服务选项、无障碍、
   氛围、适合人群、支付方式……），它们是后面「属性标签」的来源；但所有属性都
   是 **2021-09 的快照**，回答里引用事实时必须能交代「这是什么时候的快照」。

### 1.2.2 Review：评论记录

Review 是一条用户评论，一行一条：

| 字段 | 形状 | 处理策略 |
|---|---|---|
| `user_id` / `name` | 文本 | **PII**：只参与确定性评论 ID 的哈希计算，绝不写入库和任何文档 |
| `time` | Unix 毫秒 | 转为评论时间 |
| `rating` | 1–5 整数 | 评分分布、过滤、重排 |
| `text` | 可空文本 | 体验类问答的**唯一证据来源**；短于阈值的不进证据，但仍计入评分样本 |
| `pics` / `resp` | 任意 | 本期不索引；原样吞掉，避免嵌套形状导致整行解码失败 |
| `gmap_id` | 文本 | 与 Meta 关联的唯一线索 |

两个细节先记住，第 5 章会展开：

- **原始数据没有评论 ID。** 入库时用 `gmap_id + user_id + 时间 + 文本哈希`
  派生确定性标识（`user_id` 进哈希但不落库）；主键改由数据库赋值后，幂等改靠
  「餐厅 + 文本哈希 + 评分 + 时间」的唯一索引保证。
- **没有文本的评论不是废物。** 它不能当证据，但仍然是评分样本——「多少人打过
  分」和「他们写了什么」是两笔账。

### 1.2.3 规模：三个口径的数字，别混

这份数据在不同文档里出现三组容易混淆的数字，它们是不同阶段的口径：

| 口径 | 餐厅 | 评论 |
|---|---|---|
| 原始文件 | meta 272,189 行（270,720 个唯一 `gmap_id`） | 33,459,761 条，gzip JSONL，2.5 GB |
| 早期探索（业务筛选估算） | 约 17,763 家餐饮相关场所 | 约 499 万可关联，其中约 275 万有非空文本 |
| **最终入库实测** | **36,133 家写入**，demo 激活 3,000 家 | **4,243,445 条**，预过滤后 308 MB |

探索期估算和最终入库口径不同（类别清洗、bbox、评分样本等规则在演进），**以
最终实测为准**。文本侧的探索结论至今描述了语料性格：评论总字符约 4.25 亿，
中位数约 85 字符，时间集中在 2017–2021 年。**评论天生短**——这个事实第 6 章
会再出场：它解释了为什么这份语料做 RAG 不需要切块。

## 1.3 那个决定性的数字：12.7%

这份语料最重要的一个数据事实是：

> 2.5 GB / 3350 万行评论里，只有约 **12.7%** 可导入：约 **74%** 的行引用的
> 地点根本不在入库服务范围内（永远关联不到餐厅），剩下的里约一半没有文本。

全量导入的实测流水（本地容器）：

```text
预过滤：33.5M 行进 → 4.24M 行保留（12.7%）→ 308 MB，耗时 3 分 15 秒
        覆盖 36,133 家餐厅中的 35,979 家
全量导入：meta   272,189 读 → 36,133 写    8.6 秒
         review 4,243,445 写              281 秒
         stats  35,979 家聚合              32 秒
         score  36,133 打分，3,000 家激活   5.3 秒
最终库：2.9 GB，其中评论表占 2.7 GB
```

「12.7%」不是背景数字，它决定了后续的一串设计：

1. **在关联之前过滤，而不是之后。** 把 3350 万行全部推过数据库关联和写入路径，
   浪费的是小时级 I/O。正确做法是先拿到「全部可关联的 ID 集合」，在本地流式
   筛完，产出一个**格式与原始完全相同**的小文件，后续导入零改动读它。
2. **源文件其实覆盖全美，五区是筛出来的。** 餐厅侧先用包围盒、再用行政区边界
   几何做点-面判定；所以「只读前 2 万行 meta」只写约 6%——limit 限制的是读取
   行数，不是写入量。
3. **行政区标注必须用真实边界几何。** 缺几何文件时系统会降级为包围盒并告警；
   全量 meta 上包围盒与真实边界的分歧率是 10.2%，而在**真正入库存活的行**上
   高达 **24.1%**——你查的那批数据错得比全量更狠。降级因此绝不能静默。
4. **语料小而长尾，决定了检索架构。** 3,000 家激活餐厅，一份 Postgres 就够，
   不需要搜索引擎、不需要专用向量库；但体验类问题极多长尾，又逼着检索必须
   多路召回（第 8 章）。

## 1.4 清洗之后长什么样：从一条 demo 记录看关键决策

原始行 → 入库对象，中间这层叫 curate。用 demo 语料里 Ellen's Stardust Diner
的记录看它做了什么（demo 是 5 家餐厅、每家 3 条样例评论的展示集，不是正式语料）：

```json
{
  "name": "Ellen's Stardust Diner",
  "cuisine": "American",
  "price_level": 2,
  "price_raw": "$$",
  "avg_rating": 4.4,
  "review_count": 9998,
  "hours": [{"day": "Sun", "open": 660, "close": 1320}],
  "attributes": {
    "wheelchair_accessible": true, "good_for_kids": true,
    "atmosphere": ["Casual", "Cozy", "Historic"],
    "popular_for": ["Breakfast", "Lunch", "Dinner", "Solo dining"]
  },
  "provenance": {
    "source": "google_local_2021",
    "observed_at": "2021-09",
    "license": "cite-only (UCSD McAuley lab)",
    "note": "Google Maps snapshot up to Sep 2021; verify freshness at query time"
  }
}
```

curate 的关键决策：

- **菜系归一**：自由文本的类别数组 → 单一菜系标签；
- **价格等级**：`$$` → 数值等级 2，同时保留原始文本，归一失败不丢数据；
- **营业时间**：`"11AM–10PM"` 这种给人看的文本 → 从午夜起算的分钟数
  （660 = 11:00），关门的日子显式是 `null`；
- **属性展开**：`MISC` 的十几个主题 → 布尔位与标签数组；
- **来源信封 provenance**：每条事实带着快照时间 `2021-09` 和来源许可；
- **评论只留评分、时间、正文**——没有用户 ID，没有姓名。

这些规则全部实现为**无 I/O 的纯函数**：输入一条原始记录，输出一条领域对象，
所以它们的单测不需要数据库、不需要文件，离线毫秒级跑完（课后实验可验证）。

## 1.5 需求拆解：Agent 要做的五类事

产品一句话：**支持中英文对话的餐厅搜索、推荐与证据问答 Agent**，可选地通过
Mock 演示预约。拆开是五种问题形态：

1. **自然语言搜索**：「曼哈顿人均 $$ 以下、评分 4.5 以上的日料」——确定性
   条件走数据库，不许模型算；
2. **推荐（软条件）**：「安静」「适合约会」「适合带孩子」——评论推断，必须
   标记为评论观点并带证据；
3. **体验类问答**：等位久吗、服务怎么样、招牌菜是什么——只能用召回的评论和
   描述回答，证据 ID、来源、时间齐备；
4. **多轮追问**：「那第二家呢？」「它周末人多吗？」——靠会话里保存的候选
   集合继续，而不是重新猜一家店；
5. **可选 mock 预约**：查库存、hold、确认、取消改期——明确是 demo 状态，
   不伪装成真实预订。

非目标同样重要，它们挡掉了大量「顺手加一下」的诱惑：不接真实预订平台/POS、
不做支付短信、不追求 2021 数据的实时正确性、不引入搜索引擎/专用向量库/消息
队列/图数据库、MVP 不微调模型、不建多租户权限平台、**不把评论文本里的指令当
系统指令执行**。

### 核心产品原则

整门课请背下这一句：

> **模型负责理解、规划和表达；数据库与领域服务负责确定性查询和写入。**

配套的正确性策略：

- 所有快照事实统一标 `observed_at=2021-09`；实时营业、桌位、政策统一标 `mock`；
- **字段缺失按「未知」处理，不靠模型常识补全**；
- 影响预约结果的硬条件必须经过确定性校验；
- 检索结果必须带来源和证据 ID。

## 1.6 为什么「有据可依」是架构约束，不是提示词

回到 1.1 的坏 case。把「不要编造，请基于提供的资料回答」加进系统指令，为什么
不够？

因为模型端没有「真」这个裁判。它做的是生成「最像合理回答」的 token 序列；它
无法在生成时对照数据库验证「Bella Italia 是否存在」「4.7 分是哪来的」。提示词
是**恳求**，架构约束是**让错误形态根本无法到达用户**。这句话落成了四个具体
设计（先点名，后面逐个兑现）：

| 架构推论 | 落地位置 |
|---|---|
| 「谈哪几家店」必须先由确定性检索确定，不能召回后再随手过滤 | 两级检索：scope 是前提；取证据的接口在没有餐厅 ID 时直接拒绝（第 9 章） |
| 证据有 token 预算，超预算**整块丢弃**，不许半句引用 | 证据组装器 + 丢弃原因统计（第 9 章） |
| 回答里的引用 ID 必须是本轮真正拥有的，首轮违规 → 整轮重新生成 | 引用闭包在代码侧校验（第 16 章） |
| 有些文本天生不是证据：摘要只配参与排序 | `restaurant_review_digest` **永不可引用**（第 6、9 章） |

再加上开篇词说的**校验闭环**——模型给的工具参数、槽位、来源 ID 全部先过代码
校验才允许生效。两条闭环一进一出，构成整个系统的信任模型：**默认不信模型的
任何结构化输出，默认不让任何无出处的结论出门。**

这也决定了几处「不讨喜但刻意」的 API 行为，第 8、9 章会反复见到：

- 没有 filter 也没有 text 的搜索**直接拒绝**，而不是按分数返回全库；
- 未知行政区返回 **400**（「这不是个行政区」），查无结果是 **200 + 空数组**
  （「那里没有店」），两者绝不能看起来一样；
- 全部证据不可用时**报错**，而不是返回一个空证据包——空包会被读成
  「这家店没有评论」。

## 1.7 取舍与边界

- **快照即边界。** 2021-09 的事实不代表今天营业；记录和回答都显式标注快照
  时间，实时信息一律 mock。要做真实时效，需要的是新数据源而不是 prompt。
- **一个 Postgres 扛四件事。** 结构化过滤、地理、向量、模糊文本统一在一个库里，
  省掉运维四套存储的代价；边界是语料再涨一个数量级时要重新评估（收官章）。
- **模糊匹配靠 trigram，不是中文分词器。** 它能做名称/地址的模糊匹配，但不是
  中文分词；语料里中文内容多起来时要回来改。
- **安全边界是 demo 级的。** 对话 API 信任 `X-User-ID` 请求头，没有鉴权；
  管理面只靠 loopback 限制。这是本地单用户 demo 有意的起点，多用户部署前
  第一项就要换掉。
- **护栏只做注入这一种。** 语料已 PII 脱敏、本地单用户，所以只保留
  「评论是数据不是指令」这条边界；输入审核、越狱分类器、输出 PII/毒性过滤
  都留给多用户场景（第 9 章）。

## 1.8 课后实验

**跑（全部离线）**

```bash
# 清洗规则是无 IO 纯函数，单测不需要数据库、不需要原始文件
cd data-pipeline && go test ./internal/pipeline/curate/...

# 有原始文件（data/raw/google_local/）但没有库时：--dry-run 只走读取与清洗
bin/data-pipeline import --stage=meta --limit=500 --dry-run
```

**观察（改环境变量，看行为变化）**

- 在 `.env` 里改 `PIPELINE_MIN_REVIEW_CHARS`（默认 20），思考：调大它会让
  12.7% 变大还是变小？被丢掉的评论还该不该计入评分样本？（第 5 章核对答案。）
- 不带任何配置执行 `make run-pipeline`（= `check-config`），看它打印的解析后
  配置里包围盒、demo-target 各是什么——配置即产品决策，这是第一次见面。
