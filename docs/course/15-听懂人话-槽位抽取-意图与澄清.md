## 15.1 坏 case 开场：一次"合法但漏了条件"的读调用

第 14 章的坏 case 是模型**多给了不该给的**——它凭空拼了一个 `restaurant_id`。本章的坏 case
方向相反，是模型**漏了本该给的**：

```text
用户：曼哈顿中城有安静点的意大利餐厅吗？人均别超过 $$
模型：tool_call search_restaurants { "text": "安静的意大利餐厅" }
```

这个调用完全合法：`text` 是一个字符串，满足 `"type": "string"`。但核对着这句话里的事实，
它同时丢了四样东西：

- `borough = manhattan` —— 用户明确说了"曼哈顿"，召回却不受行政区约束；
- `neighborhood = Midtown` —— "中城"被丢掉了；
- `price_levels = [1, 2]` —— "人均别超过 $$"是一个上界，被完全忽略；
- "安静" 被塞进 `text`，而不是放进**软条件**。

后果不是一次报错，而是**召回静默变宽**：皇后区的店、$$$$ 的店、跟"安静"毫无关系的店
都可能回来，而且"安静"一旦被当成关键词，只会去匹配名字或描述里带"安静"二字的店——
它本该由**评论证据**来判断（"这家吵不吵"是评论里的观点，不是一个可以 `=` 过滤的列）。

> 第 14 章的 schema 校验的是模型**给了什么**；这一章要处理的，是模型**没给什么**，
> 以及它转述过的那句 `query` 还是不是用户的原话。同一道校验闭环，另一头。

同一句话还带出另外两类"模型无从下手"的用户消息：

```text
① 第二家安静吗？          —— 指代：没有店名，只有一份"上一轮的候选列表"
② 帮我订那家             —— 写操作：对象要靠指代和消歧才能定下来
```

这些都不是工具参数 schema 能表达的。要补上这一层，得先回答一个问题：**一句话到底要被
拆成哪些东西，后续的检索、工具、回答才能确定性地用起来？**

本章按「拆成什么 → 谁来拆 → 拆完怎么归一 → 指代怎么落地 → 缺什么/歧义怎么问回去」展开。

## 15.2 概念与原理：一句话 → 一张可执行的计划

PlatePilot 把这层理解叫 **slot extraction（槽位抽取）**，产物是一张 `Plan`。它是"这一轮
用户到底要什么"的唯一答案，后续每个环节（检索、工具参数补齐、回答）都吃它。

| 字段 | 是什么 | 在 PlatePilot 里对应什么 |
|---|---|---|
| `Intent` | 这一轮想干什么 | `discover` / `recommend` / `restaurant_qa` / `reservation` / `chit_chat` |
| `Query` | 用户原话（逐字） | 喂给关键词通道与向量通道的自由文本 |
| `HardFilters` | 有数据库列、可确定性过滤的条件 | 行政区 / 商圈 / 菜系 / 价格 / 评分 / 是否营业中 |
| `SoftConditions` | 没有列、只能靠评论证据支持的条件 | "安静""服务好""适合约会"…（带 topic） |
| `NamedRestaurants` | 用户提到的店名 | 交给 `resolve_restaurant` 去消歧 |
| `MissingSlots` | 还缺什么才能答 | 追加一轮澄清问题 |
| `NeedClarification` | 要不要先问人再干活 | 图从 plan 出口转去 clarify 节点 |

`Intent` 的取值是**封闭集合**，因为它决定路由，一个不认识的值没有路由可走。默认值是
`discover`，这个默认选得很有讲究：

```go
// DefaultIntent is the intent a plan falls back to when nothing else can be
// established. It is deliberately the one that still searches: a misread
// question that returns candidates is recoverable, while a misread question
// that returns nothing looks like the corpus is empty.
const DefaultIntent = IntentDiscover
```

（一个被误读、但返回了候选的问题是可恢复的；一个被误读、又什么都不返回的问题，
看起来像语料库是空的。所以默认落在**仍然会去检索**的那个意图上。）

`Intent` 只是**路由提示**，不是对模型决策的覆盖。回想第 13 章：`interpret` 只在
`st.Intent == IntentUnknown` 时才采纳 plan 的意图，模型之后仍可以决定走别的路——
一个"说到店名"的 turn 照样可能需要一次搜索。槽位层与规划层各有各的判断，
谁都不该把对方的话当成命令。

### 为什么要独立一个抽取器，而不是"让规划模型顺手填"

回到坏 case。你可能会想：既然规划模型本来就要输出 `tool_call`，为什么不干脆在
`search_restaurants` 的 schema 里把 `borough / cuisine / price_levels` 加进去，
让模型一次性填全？三个原因，一个比一个硬：

1. **"漏了"是不可见的。** 一个漏填的 `borough` 不会报错，它只会让召回变宽——这正是
   本章开头那个坏 case。而一个独立的抽取器产出的 `Plan` 是**每轮一次**的确定性产物，
   带着 `Source`（`"model"` 还是 `"rules"`）与 `Warnings`，可以离线审计"它到底读出了什么"。
2. **两件事失败的方式不同。** "选动作"（规划）和"听懂输入"（抽取）是两个不同的判断。
   分成两层，各自才能有自己的降级路径：规划模型挂了 ≠ 理解层挂了；理解层降级到规则，
   规划层照常工作。
3. **query 必须是用户原话。** 让模型一边规划一边转述用户的句子，它就会顺手"改写得通顺一点"。
   抽取器把这件事拆出来并**逐字保留** `Query`，因为语义通道正是在这些原话上召回的——
   把"想吃点清淡的"概括成"清淡餐饮需求"，向量通道就没东西可匹配了。

抽出这一层的形状很小，但它把后面几章要用的一切都定下来了：

```go
// 一句自然语言进，一张可执行计划出。这里只保留字段名，细节在后面各节。
type Plan struct {
    Intent            Intent                  // 路由提示：discover / recommend / ...
    Query             string                  // 用户原话，逐字，不改写
    HardFilters       search.RestaurantFilter // 有列的确定性条件
    SoftConditions    []SoftCondition         // 无列、只能评论支持的条件
    NamedRestaurants  []string                // 说到的店名
    MissingSlots      []string                // 还缺什么
    NeedClarification bool                    // 要不要先问人
    Source            string                  // "model" 还是 "rules"
    Warnings          []string                // 每一处降级/归一都留痕
}
```

## 15.3 硬条件与软条件：一条类型边界，不是口头约定

上面那张表里最值得单独讲的，是 `HardFilters` 与 `SoftConditions` 的**分界**。它是整章的地基。

- **硬条件**有数据库列，能确定性过滤：`borough`（五区之一）、`neighborhood`（地址子串）、
  `cuisines`、`price_levels`、`min_rating`、`open_now`。
- **软条件**没有列，只能由评论证据支持：`ambience`（安静/氛围）、`wait`（排队）、
  `service`（服务）、`value`（性价比）、`food`（好吃/正宗）、`kid_friendly`、`group_friendly`。

规矩只有一条，但它是承重的：

> **软条件绝不能进硬过滤。** 把"安静"当成一个可 `=` 的列，等于把"评论里有人提到安静"
> 当成"这家客观上就安静"——那是把一条观点升格成一条事实。

这条规矩**由类型保证**，而不是靠注释提醒。软条件住在自己的字段里（`SoftConditions`），
它是一个指向 `retrieval.SoftCondition` 的类型别名，从头到尾不会流进 `search.RestaurantFilter`。
这意味着：一个试图把软条件塞进硬过滤的改动，在用它的时候会变成**编译期的形状不匹配**，
而不是一次静默的空结果。类型边界比"我们说好不这么干"要可靠得多。

同一句话的分派，对照着看最清楚：

| 用户说 | 归到 | 为什么 |
|---|---|---|
| "安静点的" | 软条件 `ambience` | 没有列，只能靠评论判断 |
| "意大利菜" | 硬条件 `cuisines` | 有列，可 `= / ANY` 过滤 |
| "中城" | 硬条件 `neighborhood`（**不是** `borough`） | 商业区，按地址子串过滤 |
| "人均别超过 $$" | 硬条件 `price_levels = [1,2]` | 是一个**上界**，不是恰好 2 |
| "第二家" | 指代（`SelectedRestaurantID`） | 不是条件，是对一份列表的定位（15.6） |

这套分派在**两个地方**都写了一遍：一次写进给模型的抽取 prompt（那是**请求**），
一次落在归一化代码里（那是**检查**）。prompt 是让模型照着做的，检查是不信它一定照做的——
第 2 章那条"校验闭环"的老规矩：模型给的东西，没被代码验过就不算数。

## 15.4 两条抽取路径：结构化输出，规则兜底

抽取器有两条路径，它们产出**同一个** `Extraction` 形状，然后在 15.5 走同一套归一化。
"同一个形状"是刻意的：

> 归一化是这里面**最有判断力**的一段，让两条路径共用它，才能保证
> 一个规则计划不会比一个模型计划"悄悄少归一"一点。

### 路径一：模型（结构化输出）

模型路径是**一次**带 schema 的调用，任务标签固定为 `task=slot_extraction`：

```go
resp, err := e.structured.CompleteStructured(callCtx, domainchat.StructuredRequest{
    Messages: messages,          // system 指令 + （可选）线程上下文 + 用户原话
    Model:    e.model,           // CHAT_MODEL_EXTRACT，可以是一个便宜的小模型
    Metadata: map[string]string{"task": "slot_extraction"},
}, json.RawMessage(extractionSchema))
```

几个容易忽略、但决定成败的细节：

- **schema 是"全 required + 可空用类型联合"写出来的。** 一份带 optional property 的 schema
  会被 strict-schema provider **直接拒绝**，而一份被拒绝的 schema 会让**每一次**抽取都
  静默跌到规则路径，还没人会发现。所以 `query` 写成 `["string","null"]`、`borough` 写成
  `["string","null"]` 且 `enum` 里带一个 `null`，所有键都进 `required`。
- **`query` 逐字抄写，不翻译、不改写、不概括。** prompt 里原话是
  "copy the user's sentence verbatim; do not rewrite, translate, or summarize it"——
  理由和 15.2 一样：语义通道就是在原话上召回的。
- **空抽取要和"模型答了"分开算。** 一段 `{}` 是合法 JSON，但里面一个槽位都没有；
  代码显式判它"没有任何槽位也没有 query"就报错，避免"模型什么都没答"和"模型答了"
  落进同一个桶。
- **超时是 10s，比 chat 的超时短。** 抽取是**可选的精炼**，一个正在"思考槽位列表"的模型
  不该让用户一直等——超时就该把规则计划先递给用户。

### 路径二：规则降级（这是官方支持的部署形态）

关键的一句在代码注释里：**`Structured` 可以为 nil，抽取器于是完全跑在规则上——
"这是一种受支持的部署形态，而不是降级形态"。** 什么情况下会走到规则：

- 压根没配 chat provider（`structured == nil`）；
- provider 挂了 / 超时 / 返回的不是 JSON；
- 返回了 JSON，但不是一个有效的抽取。

这四种情况的收尾**完全一样**：用户自己那句话原样当 `Query`，`Source` 记为 `"rules"`，
并挂一条 warning：

```go
if err != nil {
    note := "槽位抽取未使用模型（" + err.Error() + "），已按规则解析"
    return e.rulesExtraction(userInput), SourceRules, note
}
```

`Extract` 返回的 error **永远不是**建模或解析失败——它只有一个用途：调用方的 context 被取消了。
"抽不出槽位就拒绝服务，会把一次部分理解变成完全没有服务"。

规则解析器**刻意保守**：每个值都来自**封闭词表**（`boroughAliases` / `neighborhoodAliases` /
`cuisineAliases` / `softTopicKeywords`），所以一个规则计划里不可能出现语料库不认识的取值。
它认不出来的东西全部留在 `Query` 里——关键词和向量通道还能用得着。

两条路径还有一个共同的兜底：**"附近"没有坐标时降级。** 项目没有地理编码器，
"离我近"没有中心点可量，所以它降级成行政区/商圈过滤，**并把这条限制写进 warning**，
而不是假装算出了一个距离：

```go
// 没有地理编码器就没有中心点，编一个就等于按用户从没给过的位置排序。
// 降级到行政区/商圈过滤（诚实收窄），但把限制写下来而不是藏起来。
plan.Warn("请求包含“附近”，但没有可用坐标，已降级为行政区/商圈过滤（无地理编码器）")
```

## 15.5 归一化：抽取之后、执行之前的那一层

拿到 `Extraction` 之后、变成可执行 `Plan` 之前，有一段归一化（`BuildPlan`）。
它做**四件不能信任原始抽取**的事：

1. **拼写归一。** "曼哈顿" → `manhattan`，"意餐" → `italian`，"苏活" → `SoHo`。
   注意商圈的目标值刻意是**英文拼写**——语料库的地址是用英文写的，用户写中文也没关系，
   因为过滤器比对的是**子串**，用户的中文拼写不会出现在地址里。
2. **商圈从 `borough` 字段挪进 `Neighborhood`。** 模型把"中城"填进 `borough` 是**可修正**的错，
   不是非法的：用户说的是"要在哪个地方"，地址过滤器正好能表达它。所以它被**移动**并告警，
   而不是被拒绝。

   ```go
   if neighborhood, ok := canonicalNeighborhood(value); ok {
       plan.Warnf("“%s”是商圈而非行政区，已按地址关键词过滤", value)
       plan.HardFilters.Neighborhood = neighborhood
       return
   }
   ```
3. **软词从硬条件里剔出去。** 模型把"安静"塞进 `cuisines` 时，它被移到软条件，并记一条
   warning——`硬条件中的“安静”属于评论推断条件，已移入软条件（ambience）`。
   **模型的错误被看见，而不是被静默改正。**
4. **不凭空造 query。** 空 query 回退成用户的**整句**，保住关键词/向量通道。
   一个"有槽位但没有 query"的计划会静默丢掉所有只有软通道能解释的条件。

有一条容易踩、但被刻意保留的行为：**不认识的行政区留在原位，不丢弃。** 悄悄丢掉它，
会把"这不是一个行政区"变成"没有餐厅匹配"——这两个回答对用户是不同的，一旦值被丢掉，
就再也分不出来了。留在原位，让它走到 `Filter.Validate()` 变回一个明确的
`retrieval_invalid_filter`。

整段归一化有一条铁律：

> **每一处偏离原始抽取的地方，都进 `Warnings`。**
> 一次审阅者看不见的归一化，和"模型其实做对了"是无法区分的。

最后一条一致性保护：`MissingSlots` 非空时，强制 `NeedClarification = true`。这两个字段
描述的是**同一个状态**（"还答不了，得问你"），它们互相矛盾会表现为"流停了却没有问题"，
所以任何一个为真，另一个必须跟着为真。

## 15.6 指代解析：把"第二家"读成 id

回到 15.1 的第二类坏 case："第二家安静吗？"。这句话里没有店名，但线程里有一份
**候选快照**（上一轮给用户看过哪几家、什么顺序）。指代解析就是把"第二家"这类说法
落到快照里的某一行上，产出一个 `restaurant_id`。

三种 kind，各自失败的方式不同：

| kind | 例子 | 解析方式 |
|---|---|---|
| `ordinal` | "第二家"、"最后一家" | 快照里的一个**位置** |
| `demonstrative` | "这家"、"那家"、"它" | 已锁定的那家，或没有锁定时取第一家 |
| `modifier` | "那家安静的"、"布鲁克林那家" | 在快照里**匹配一个描述** |

第一件要钉住的事：**指代解析全程不调模型。**

> "第二家"是关于线程的**事实**，不是对线程的解释。一条每次都判得一样的规则，
> 比一个"通常同意"的生成更值钱——而持久化候选快照的全部意义，正是让"第二家"
> 成为一个事实。

几处设计上的取舍：

- **序数必须带量词。** "第二次"是次数，不是候选；所以正则要求 `第 N 家` 里的"家/间/个"
  不能省——接受一个光秃秃的"第二"，会把"第二次"解析成列表第一家。
- **越界是"列表比你以为的短"，不是错误。** 用户指的是一个真实的位置，只是快照没那么多项，
  所以回复是"你说的第 3 家超出了本轮候选范围（当前只有 2 家）"，而不是报错或瞎取最近的一个。
- **描述有两种强度。** 占有式（"那家安静的"）尾部的"的"明确标记了前面是描述，
  所以**即使没匹配也照做并报告**；裸前缀（"布鲁克林那家"）更弱，常常只是周围句子的一部分
  （"我第一次去这家店"），所以**只有恰好唯一匹配一家时才算**，否则掉回它包含的 demonstrative。
- **描述跑在"名字 + 匹配原因"上。** 快照除了位置还持久化了 `reasons`（候选是靠哪些条件
  命中的）。这就是 `reasons` 要和位置一起存下来的原因：一个复述了条件的描述
  （"布鲁克林那家"）能在 `reasons` 里找到候选，因为那条 reason 写着"匹配行政区：brooklyn"。
  用户写中文、语料存英文，两者靠别名表在这层对上。

### 解析出的 id 进 `SelectedRestaurantID`，不进 filter

这是最容易做错的一步。把"第二家"解析成 id 之后，这个 id 该放哪？

> **放进 scope（`SelectedRestaurantID`），而不是放进 filter。**
> filter 会把一次"接近命中"变成"查无此店"；而这里想要的是**消歧问题**——
> 当一个名字对应好几家，正确的动作是问用户，不是宣布餐厅不存在。

同一条 pin 还有**两种强度**，区别在"谁决定的"：**这一轮**由规则解析出的 pin 是指令
（用户指了某家，规则说了是哪家，后面的每一步都得停在它上面）；**继承自上一轮**的 pin
只是一个默认（线程在聊那家，但这条消息很可能已经换话题了）。如果把它当成指令讲给模型，
模型就会拿一个曼哈顿的餐厅去回答一个布鲁克林的追问——所以继承形态会说明它从哪来、
什么时候该丢。到底是不是 follow-up，正是**模型能判、规则判不了**的那件事。

配套还有一条清理：`dropStalePin`。一次新搜索替换了候选列表之后，上一轮的 pin
就不再关于任何"用户看得见的东西"了——继续带着它，会让下一轮的计划告诉模型去回答
一个**新结果里根本不提**的餐厅。但如果 id 仍然在新列表里，pin 就保留：这正是一次
"细化搜索"仍能停在同一个餐厅上的原因。

## 15.7 两类人机回环：缺槽位追问与同名消歧

到这一步，抽取器已经能说清"读懂了什么"。剩下的是两类**必须停下来问人**的情况。
它们由**两个不同的来源**触发，所以走两条不同的路：

### A. 缺槽位 → 追问（`missing_slots`）

抽取器判断"必填条件真的缺、检索跑不了"时，置 `MissingSlots` 与 `NeedClarification`。
图从 plan 出口转去 clarify 节点，问的是**槽位名本身**：

```text
我需要再确认一点信息才能继续：borough、cuisine。补充之后我再帮你查一次。
```

注意这里挂的是槽位名，**不是伪造一个工具名**——下一轮需要知道的是"补什么"，
而不是"假装谁问的"。clarify 节点因此区分两种挂起：有得选时挂具体的动作，
纯缺槽位时挂槽位列表。

### B. 同名歧义 → 候选卡片消歧（`resolve_restaurant`）

用户说一个名字（"帮我看看 Katz's"），这既不是条件也不是位置，交给 `resolve_restaurant`
工具走一次 `MatchByText`。它返回**三态**，而且这三种都是**正常结果，不是错误码**：

| 状态 | 含义 | 正确下一步 |
|---|---|---|
| `resolved` | 有唯一清晰的最佳匹配 | 拿 id 去取证据（`get_restaurant_evidence`）再答 |
| `ambiguous` | 前二太接近，分不出 | **停下问用户**，不要猜 |
| `not_found` | 没有够格的匹配 | 改用按需求检索，或让用户确认拼写 |

"没找到"也定义成正常结果，理由写在注释里："答一个错误的猜测，比什么都不答更糟。"

判定由两个阈值控制，它们都是环境变量旋钮（`AGENT_RESOLVE_*`）：

- `MinSimilarity = 0.55` —— **地板**。低于它就不算匹配。没有它，一个谁都没打过的名字
  会解析到 pg_trgm 三元组索引以为最近的那家。
- `AmbiguityGap = 0.10` —— **前二差距**。低于它就说"你说的是哪家"。这个间隙为 0，
  会让"两个店共享前缀"每次都触发提问；太大，又会在两个真正同名的店之间瞎猜一个。

**判定的顺序是承重的：先按 hints + 地板收窄，再判歧义。**

> 先判歧义，会把一个明明有赢家的结果说成歧义——因为一个被地板拒掉的"接近项"
> 还留在候选列表上，把前二差距撑得像是真的。

候选排序是**稳定**的：`按 score，再按 id`——两个一模一样的分数每次返回同一个顺序，
这是第 8 章"排序必须可复现"的纪律在工具层的延续。

当状态是 `ambiguous`，消歧问题（`buildClarificationQuestion`）用**人能区分的东西**列选项：

```text
按你说的名字，我找到了几家都对得上的餐厅，你说的是哪一家？
1. Katz's Delicatessen（manhattan，205 E Houston St，delicatessen，评分 4.5）
2. Katz's Deli（brooklyn，...）
回复序号或直接说出名称、地址都可以。
```

一条不可越界的规矩：**绝不用数据库 id 让人做选择。** 用户从没见过 id，"在 42 和 77
之间选一个"不是问题；街区、地址、菜系、评分才是人区分两家店用的东西。

最后是一条顺序纪律：**先存 checkpoint 和候选快照，再发 delta 和 `awaiting_input` 帧。**
客户端收到"该你了"会立刻回读线程，看到的必须正是它刚被告知的那个状态——先把状态落盘，
一次丢失的竞态才是廉价的。

## 15.8 防死循环：澄清上限与明示假设

如果每一轮都可能问，一个线程就能永远问下去。所以澄清次数有一个上限
（`AGENT_MAX_CLARIFICATIONS = 3`），而且它**存在 checkpoint 里、跨 turn**。

同线程连续问到上限之后，第 4 次**必须继续**。但它有**两种出路**，因为两类情况的
出路本来就不同：

```go
func (r *Runner) settleClarificationCap(st *TurnState) {
    if st.ClarificationCount < r.cfg.MaxClarifications {
        return
    }
    if len(st.ClarificationOptions) >= 2 {
        // 桌上有候选：按最相似的那家继续，但必须把假设说出来
        best := st.ClarificationOptions[0]
        st.SelectedRestaurantID = best.RestaurantID
        st.Plan.ReferenceNote = fmt.Sprintf("澄清次数已达上限，按最相似的「%s」继续", best.Name)
        st.Warnings = appendUnique(st.Warnings, "…回答中必须说明这一假设")
    }
    // 没有候选：缺的是用户从没给过的槽位，没有可以假设的对象
    st.ClarificationOptions = nil
    st.Plan.NeedClarification = false
    st.ClarificationAssumed = true
}
```

- **有候选** → 按最相似的店继续，但回答里**必须明示**"按最相似的 X 继续"。
  **静默假设正是这个上限要防的失败本身**：一个假装笃定、其实在猜的回答，比一次
  坦白"我不确定，先按这个答"的回答更糟。
- **没有候选**（缺的是用户从没给过的槽位）→ 停止追问，让 `answer` **如实报告缺口**，
  而不是再问一次。

处置完成后 `ClarificationAssumed = true`，于是 `needsClarification()` 永远返回 false：

```go
func (st *TurnState) needsClarification() bool {
    if st.ClarificationAssumed {
        // 上限到了，正在一个已声明的假设上继续；再问就是上限要打断的那个循环。
        return false
    }
    return len(st.ClarificationOptions) >= 2 || st.Plan.NeedClarification
}
```

## 15.9 取舍与边界

**为什么独立抽取器，而不是让规划模型顺手填。** 代价是多一次模型调用（可以用便宜的小模型，
`CHAT_MODEL_EXTRACT`）。换来的是一层**可审计、可降级、可离线测**的理解层。值得。
反过来说，什么规模可以不这么做：工具 schema 简单、条件两三个、漏了也不致命时，
让模型直接在参数里填是可以的——PlatePilot 不行，是因为"漏一个行政区"会让召回静默变宽。

**规则降级是官方形态，不是兜底。** 没有 chat provider 的部署照样能跑：意图和部分槽位
由规则词表给出，关键词通道仍然工作。这条取舍反过来有代价：**规则词表是产品决策、是封闭的。**
词表外的一切留在 `Query`（向量通道还能用），规则**漏认**比**误认**好——一个错误的
软条件会让回答断言一条用户从没问过的推断。

**没有 NER，只信引号。** 规则路径只把**加引号的**短语当店名（`scanQuotedNames`）。
猜一个大写短语是店名，会误解析普通词；**一个错的解析比不解析更糟**——它会去回答一个
用户根本没问的餐厅。抽取器认不出店名时，那句话落到 `Query` 兜底，模型（或整轮对话）
仍有机会处理。

**`resolve_restaurant` 的阈值是两个产品旋钮。** 门槛调高，`not_found` 变多、`resolved` 变少；
间隙调小，更多名字被判为歧义、追问变多。它们放在环境变量里，正说明这是**产品决策而非实现细节**：
调优不必重编译。

**澄清上限的代价是"第 4 次可能按错的假设作答"。** 这是刻意的取舍：无限追问会更糟。
上限用"明示假设"来补偿——一次坦白的猜测，胜过一句假装确认的独断。

**"附近"降级的代价是地理能力受限。** 没有地理编码器，"离我近"只能收窄到行政区/商圈，
且这条限制会**明确写进 warning**——一个要了"附近"却拿到全行政区答案的用户，理应知道为什么。

## 15.10 课后实验

**跑**

```bash
# 只探"理解层"，不起整轮对话：POST /v1/restaurants/interpret
curl -s localhost:8080/v1/restaurants/interpret \
  -H 'content-type: application/json' \
  -d '{"text":"曼哈顿中城 4 星以上、安静点的意大利菜，人均别超过 $$"}' | jq
```

看返回里的 `intent`、`hard_filters`、`soft_conditions`、`query`、`source` 各落在哪——
尤其注意"安静"必须出现在 `soft_conditions` 而**不**在 `hard_filters` 里。
再故意让 provider 不可用（或用超时），观察 `source` 变成 `"rules"`、`warnings` 多一条。

**改**

```bash
# 门槛调高 → resolve 的 not_found 变多、resolved 变少
AGENT_RESOLVE_MIN_SIMILARITY=0.75 make run-chat
# 间隙调小 → 更多名字被判为 ambiguous，追问变多
AGENT_RESOLVE_AMBIGUITY_GAP=0.03 make run-chat
# 澄清上限压到 1 → 第 2 次就必须"明示假设"继续
AGENT_MAX_CLARIFICATIONS=1 make run-chat
```

然后发一段对话试指代：先要一轮推荐，再发"第二家安静吗""那家安静的怎么样""帮我订那家"，
看 `reference_note` 怎么说明它把话读成了哪一家。

**想**

- 为什么软条件**绝不能**进硬过滤？如果硬把它塞进去，"安静"这种词在库里会变成什么？
- 把 `AmbiguityGap` 设成 `0`，会发生什么？设成 `0.5` 呢？
- 澄清上限到了、桌上又没有候选时，为什么"如实报告缺口"比"再问一次"对？
- 规则路径认不出没加引号的店名时，会发生什么？它为什么**不该**去猜？（提示：`Query` 兜底 + 误解析的代价。）
