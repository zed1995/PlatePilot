## 14.1 坏 case 开场：一个「合法」到足以通过校验的错误调用

先接回第 3 章那个假搜索函数。那时工具是代码里写死的，模型只能调它、不能选它。现在工具多了，
坏 case 也升级了——它不再表现为「函数返回空」，而是表现为**一次看起来完全合法的写操作**：

```text
① 用户：推荐一家安静的意大利餐厅
   plan → tools(search_restaurants) → plan → answer          （只读，正常）
   
② 用户：就第二家吧，帮我明晚 7 点订 4 个位
   模型这一轮返回两个 tool_call：
     call A: get_availability     {restaurant_id: 8842, date: "2026-10-18", party_size: 4}
     call B: request_reservation  {restaurant_id: 8842, slot_id: "slot-7pm", party_size: 4}
```

看着没问题，但仔细核对本轮的事实：**`8842` 从未出现在这家店的搜索结果里**。用户看到的
候选列表里是另外三个 id，模型自己拼了一个。此时：

- JSON Schema 校验会**通过**——`8842` 是一个合法的 integer，满足 `"type": "integer"`；
- 如果这一步直接执行，系统会去订一家用户在整段对话里从未见过的餐厅。

**schema 能证明「这是一个整数」，它证明不了「这个整数是用户看过的餐厅」。** 这就是工具系统
必须解决的第一类问题：把校验从「类型对不对」推进到「是不是本轮真正读到过的值」。
同一段场景还暴露另外三个问题：`get_availability` 和 `request_reservation` 能不能并发跑
（不能，后者依赖前者的返回）；写操作一旦成立，本轮剩下的调用怎么办；模型一路上会犯错
（工具名写错、参数不是 JSON、漏必填项），**这些错误该拖垮整个推理循环，还是回给模型让它改**。

本章按「工具怎么声明 → 参数谁校验 → 结果怎么回去 → 怎么调度」的顺序，把这四个问题逐个收掉。

## 14.2 六个工具：一张模型可见的能力表

PlatePilot 给模型的工具只有六个，全部是**确定性函数**——模型负责规划和措辞，计算在
store / retrieval 里完成。这一点值得先钉住，因为它是整章的地基：

> **模型不计算，模型只是选择调谁、填什么参数；真正的过滤、排序、查库、下单都在 Go 代码里。**

| 工具名 | 作用（一句话） | 只读 | 确认策略 | 落到哪个能力端口 |
|---|---|---|---|---|
| `search_restaurants` | 按自然语言需求 + 硬过滤检索餐厅，返回排序候选 | 是 | — | retrieval 检索服务 |
| `get_restaurant_evidence` | 为 1–5 家餐厅取可引用的证据文档 | 是 | — | retrieval 证据服务 |
| `resolve_restaurant` | 把用户说的名字解析成 `restaurant_id` | 是 | — | restaurant 仓储（`MatchByText`） |
| `get_availability` | 列出某餐厅某天可订时段 | 是 | — | reservation 服务 |
| `request_reservation` | 请求订座（**不直接下单**，先请用户确认） | 否 | `required` | reservation 服务 |
| `save_memory` | 记住关于用户的一件事 | 否 | `implicit` | memorywrite 服务 |

三个细节从这张表里就能读出来：

**① 工具即能力边界。** 模型做不到的事，就是它没有对应工具的事——没有 `request_reservation`
它就不能下单，没有 `save_memory` 它就记不住任何东西。所以「关掉一个能力」的正确做法是
**让工具干脆不注册**，而不是注册一个「永远回答不行」的工具。装配代码就是这么写的：
预约能力关闭时 `get_availability` / `request_reservation` 两个工具**根本不进注册表**
（[app.go](../../chat-service/internal/app/app.go#L177-L196) 的注释原话是
"removes the capability from the model's view instead of presenting a tool that can only say no"）；
`save_memory` 同样只在「有记忆存储 **且** 开关打开」时注册。

**② 只读是显式声明的，不是程序员心里的默认。** `ToolSpec.ReadOnly` 是一个字段，注册时会被
拿去和确认策略交叉校验（14.3）。只读工具想并发，写工具必须截停——调度纪律正是从这条声明
推出来的（14.7）。

**③ `resolve_restaurant` 走的是餐厅仓储而不是检索服务。** 它的活儿是「名字 → id」的一次
查库，把它塞进检索服务会让一次名字查找意外获得软通道的意见（相似度、语义排序）。工具的
依赖刻意收窄成 `RestaurantResolver` 一个接口，就是为了不让它「顺手」长出过滤能力。

## 14.3 说明书：一份 JSON Schema，声明一次，校验两次

模型看到的一个工具，是三个字段：**名字、描述、参数 schema**。

```go
Spec: domaintool.ToolSpec{
    Name:        ResolveRestaurantToolName, // "resolve_restaurant"
    Description: "Turn a restaurant name the user said into a restaurant_id ...",
    Parameters:  json.RawMessage(resolveRestaurantSchema), // JSON Schema
    ReadOnly:    true,
},
```

`Parameters` 就是一份 JSON Schema。注意一件与直觉可能相反的事实：**本项目的 schema 是手写的
常量字符串**，紧挨着对应的 Go 参数结构体：

```go
// schema（给模型看的）与 args struct（给代码用的）成对声明，必须手动保持同步
const resolveRestaurantSchema = `{
  "type": "object",
  "properties": {
    "name":   {"type": "string", "description": "The restaurant name the user said, verbatim"},
    "limit":  {"type": "integer", "description": "How many candidates to consider, 1..5"}
  },
  "required": ["name"],
  "additionalProperties": false
}`

type resolveRestaurantArgs struct {
    Name        string `json:"name"`
    AddressHint string `json:"address_hint"`
    Borough     string `json:"borough"`
    Limit       int    `json:"limit"`
}
```

很多框架用反射从 Go 结构体**自动生成** schema（省掉这份同步），本项目没走那条路，
取舍在第 [14.9](#149-取舍与边界) 节讲。这里先记住结论：**说明书是手写的一次声明，
但它会被校验两次，分别在两个不同的时刻、针对两类不同的错误。**

### 第一次校验：注册期（程序员错误，启动即失败）

`Register` 时 `parseSchema` 会把 JSON 解成内部结构，只认一个**刻意封闭的子集**：
`type`（object/array/string/number/integer/boolean/null）、`required`、`properties`、`items`、
`enum`、`additionalProperties:false`。子集之外的关键字（`description`、未来的注解）**被接受
并忽略**，而不是拒绝——这样给 schema 加说明文字永远不会让注册失败。

注册期的错误是**写代码的人的错**，所以它们最好在启动时就炸掉，而不是等第三次对话才暴露：
`Handler` 为 nil、工具名不合 `^[a-z][a-z0-9_]{1,63}$`、重名、schema 根不是 object、
确认策略与 `ReadOnly` 对不上、该有 `SummarizeApproval` 却没有（或反之）。任何一条不满足，
装配阶段直接返回错误，服务起不来。

其中**确认策略的交叉校验**最值得单独说，因为它是用一个「三值枚举」而非 bool 换来的安全：

```go
ConfirmationNone     = "none"      // 只读工具无副作用
ConfirmationRequired = "required"  // 写操作：挂起，等用户确认这次调用
ConfirmationImplicit = "implicit"  // 写操作：用户自己那条消息就是授权
```

用一个 bool `needsApproval` 会有一个致命的盲区：**「这个写工具需要用户确认」和「作者压根没想过
这件事」都是零值**，两者在注册时长得一模一样，而后者意味着一个无人授权的写操作悄悄上了线。
把它做成必须显式声明的字符串，**漏填就是空字符串，`Register` 可以直接拒绝**。
这张表也解释了两条配对规则：写工具没有策略 → 拒绝（这是它存在的原因）；只读工具却说
「需要确认」→ 也拒绝，因为那会把一次查库变成一道用户必须回答的问题。

### 第二次校验：调用期（模型错误，转成 tool message 回给模型）

运行时 `Invoke` 会再校验一次，针对的是**模型这次产出的参数**，顺序是：

1. 参数必须是合法 JSON；空参数视为 `{}`；
2. 顶层必须是 JSON **对象**（不是数组、字符串）；
3. 按 schema `validate`：必填、类型、`enum`、对象属性、数组元素逐个检查。

失败信息**带路径**（`limit must be integer (got string)`、`cuisine 不在枚举里` 这类），
因为这条信息的读者是模型——它得知道**哪个**参数错了才能改对。两次校验的分工可以一句话概括：

> 注册期问「这份说明书本身合法吗」，答案是程序员的事，错了就别启动；
> 调用期问「模型这次给的参数合法吗」，答案是运行时的事，错了就回一条 tool message 让它重来。

## 14.4 注册表：五种失败，一个永不 panic 的出口

所有工具调用都从**同一个函数** `Registry.Invoke` 进来。它有一条写在文档注释里的硬契约：

> **Invoke 永不 panic，永远返回一个 `ToolResult`。**

理由很实在：模型是在一个推理循环里调工具的，一次工具失败应该是**一轮对话里的一个事件**，
而不是把整张图掀翻的异常。于是五类失败被统一收进同一个 `ToolResult` 信封，各带一个稳定的
错误码：

| 失败 | 错误码 | 谁造成的 |
|---|---|---|
| 未知工具名 | `CodeNotFound` | 模型（写错了工具名） |
| 参数不是合法 JSON | `CodeValidationFailed` | 模型 |
| 参数不满足 schema | `CodeValidationFailed` | 模型 |
| 工具执行超时 | `CodeProviderTimeout` | 环境（库/上游慢） |
| handler panic | `CodeInternal` | 代码（被 `recover` 兜住） |

handler 自己返回的**领域错误会被原样保留**：如果 `request_reservation` 在没被批准时返回
`CodeAgentNoPendingAction`，`Invoke` 不会把它压成一个笼统的 internal，而是把这个码原封不动
送回去——因为下游要靠它做判断，模型也要读它。非领域错误（一个裸 `errors.New`）才被包成
`CodeInternal`。这条「领域错误保真、其余归一」的规则让错误码既是**给模型看的话**，
又是**审计能分类的标签**，一份数据两个用途。

`Invoke` 的顺序就是失败处理的优先级，骨架大致是（省略了部分分支）：

```go
func (r *Registry) Invoke(ctx context.Context, call domaintool.ToolCall) (result domaintool.ToolResult) {
    result = domaintool.ToolResult{CallID: call.ID, Name: call.Name, Status: domaintool.ToolStatusError}
    reg, found := r.entries[call.Name]                                  // ① 未知工具 → CodeNotFound
    if !found { result.Error = errs.Newf(errs.CodeNotFound, "unknown tool %q", call.Name); return }

    var decoded any                                                    // ② 参数校验
    if err := json.Unmarshal(call.Arguments, &decoded); err != nil {
        result.Error = errs.Wrap(errs.CodeValidationFailed, "...", err); return
    }
    obj, ok := decoded.(map[string]any)                                // 顶层必须是对象
    if !ok { result.Error = errs.Newf(errs.CodeValidationFailed, "..."); return }
    if err := reg.schema.validate(obj, "$"); err != nil {              // 按 schema 校验
        result.Error = errs.Newf(errs.CodeValidationFailed, "tool %q: %v", call.Name, err); return
    }

    callCtx, cancel := context.WithTimeout(ctx, reg.entry.Timeout)     // ③ 统一超时
    defer cancel()
    defer func() { if p := recover(); p != nil { /* panic → CodeInternal */ } }()

    out, err := reg.entry.Handler(callCtx, call.Arguments)
    // ④ callCtx.Err()==DeadlineExceeded → CodeProviderTimeout
    // ⑤ errs.As(err) 命中 → 域错误原样保留；否则包成 CodeInternal
    // ⑥ 补齐 CallID/Name，Status 为空则默认 ok
    return out
}
```

超时那一层有个容易被忽略的细节：`Invoke` 判的是 `callCtx.Err() == context.DeadlineExceeded`，
而不是笼统的「ctx 错了」。二者的区别很重要——**是工具自己超时了，还是整个请求被上游取消了**，
对应的是两种不同的处置（前者可以换参数重试，后者应该就此结束 turn）。超时的具体数值按
`Entry.Timeout > Spec.TimeoutMS > 默认 15s` 的优先级解析（`DefaultTimeout`）。

### 「给模型看的话」由工具产出，不靠通用渲染器

失败要能读懂，成功也要能读懂。每个工具的 handler 都配了一个 `renderXXX`，把结构化结果压成
一段**省 token 的中文摘要**：搜索没命中是「未找到符合条件的餐厅」而不是一个空 JSON 数组；
时段为空是「这天没有能坐下 N 人的时段」——**说成事实，不报成错误**，因为报错误会诱导模型
重试同一个问题。这些文案是**产物的一部分，不是装饰**：模型手里没有可读的解释，就会自己编
一段听起来合理的（第 3 章的老朋友）。

注册表还负责把工具的**依赖注入**和**能力开关**管住：`SummarizeApproval` 这个回调之所以由
工具自己提供而不是由一个通用渲染器统一生成，是因为**只有工具知道自己的参数是什么意思**——
「2 人 · Joe's Pizza · 2026-10-10 19:00（政策 mock-v1）」是一句关于预约的话，一个通用渲染器
只能把一个 JSON blob 丢给用户让他批准，那不叫「可批准的内容」（第 18 章细讲）。

## 14.5 结果的两种读者：Content 给模型，Data 给图

一个 `ToolResult` 同时携带两份东西：

```go
type ToolResult struct {
    CallID  string          // 归属哪次调用
    Name    string
    Status  ToolStatus      // "ok" / "error"
    Content string          // 模型读的自然语言摘要（省 token）
    Data    json.RawMessage // 结构化 DTO，给图更新 TurnState 用
    Error   *errs.Error     // 失败时的稳定错误码 + 文案
}
```

为什么要分两份，而不是只留一份？因为**它们有两个截然不同的读者**：

- `Content` 的读者是**模型**：它要能读懂、能引用、且要省 token。所以它是中文短句，
  带着「匹配原因」「数据时间」「降级提示」这些模型作答时用得上的东西。
- `Data` 的读者是**图**：它是原样的领域 DTO（`SearchResult` / `EvidenceResult` / `ResolveResult`…），
  图拿着它去更新候选、证据、值域，**不需要重新解析一遍文本**。

举三个来自真实工具的对照：

- `search_restaurants` 的 `Content` 每行带 `匹配原因` 和 `数据时间`。这不是凑字数——
  **一个模型解释不了的推荐，它会自己去编一个解释**。把 reasons 摆在它面前，它就能引用
  「究竟是哪个通道、什么条件命中的」，而不是凭空构造一段合理的说辞。
- `get_restaurant_evidence` 的 `Content` 里，每一条证据都保留 `evidence_id`。那是**唯一合法的
  引用键**（第 9、16 章），丢了它就等于让模型失去「能不能引」的依据。
- 空结果与降级也不回避：搜索无命中会附上 `检索说明`，证据无命中会附上 `降级提示`。
  注意渲染函数把这两类措辞分开，并且**不把一次成功跑过的通道叫「降级」**——
  那会教模型为一个其实完整的排序道歉。

## 14.6 只读工具的纪律：补齐不覆盖、拒绝空搜索、三态不是错误

三个只读工具各自都有一条「看起来更聪明、其实是错的」的诱惑，值得单独说清。

**`search_restaurants`：turn 的计划（plan）补齐模型漏掉的硬条件，但绝不覆盖它给过的值。**
第 13 章讲过 ingress 会产出本轮唯一的 `Plan`。这里就是它的消费点：`applyPlanDefaults` 把用户
在这句话里说过、而模型没塞进工具调用的条件（行政区、菜系、价格、评分、营业中、软条件）
补进去。方向是刻意单向的：

```go
// 补齐（plan 填模型漏掉的部分）……
if args.Borough == "" && filter.Borough != "" { args.Borough = filter.Borough }
// ……但不覆盖：模型给了值就尊重它，因为那可能是它有意放宽的一次重试
```

为什么要「只补不覆」？因为模型可能**故意**放宽——「没有 4 星的，那就看看 3 星」是一次合法的
重试，覆盖它会让这个重试永远做不到。plan 保证的是另一半：**用户说过的条件，不会因为模型
没在调用里重复一遍就消失**。这正是在第 3 章「模型漏一个菜系、召回就静默变宽」那个隐患的正面回应。
另外，**一次没有任何条件的搜索会被拒绝**（`hasCondition()` 为假就返回 `CodeInvalidArgument`）：
没有条件、没有文本的调用等于「把全库按分数倒出来当作是搜到的」，那是第 8 章明令拒绝的行为。

**`get_restaurant_evidence`：follow-up 轮用计划里 pin 住的餐厅补 `restaurant_ids`。**
用户问「第二家安静吗」，`restaurant_ids` 可能整个缺省——此时工具读 `plan.SelectedRestaurantID`
补上（第 13 章的指代 pin）。同样是「模型给的 id 原样用，只在其没给时才问计划」。它还硬性
限制**最多 5 家**、`doc_types` 只认白名单枚举，超限直接报错而不是悄悄截断。

**`resolve_restaurant`：三种状态都**不是**错误。** 名字解析只有三种正常结局，
每一种对应模型不同的下一步：

```go
resolved   // 唯一确定 → 下一步去取证据
ambiguous  // 两三家几近并列 → 必须先问用户选哪家，不要猜
not_found  // 没到相似度门槛 → 改用按需求搜索，或请用户核对名字
```

阈值是可配置的两个数：`min_similarity=0.55`（低于它就不算匹配）和 `ambiguity_gap=0.10`
（前两名差距小于它就判歧义、去问用户）。判定**顺序**也是承重的：先用提示（区、地址片段）
和相似度门槛筛，**再**判歧义——反过来会把一个清晰的赢家因为一个已被淘汰的近似项而误判成歧义。
排序按 `score → id` 稳定，同一个名字跑两次结果一致。最后一条最容易忘：**工具只把名字转成 id，
绝不跳过证据步骤**——resolved 只是一个 scope，不是答案，允许模型把二者当同一回事，
它就会对一家「只知道名字」的店写出一段无据的推荐。

## 14.7 写操作的纪律：值域校验、确认门、截停与保序

回到 14.1 的坏 case。防御分三层，全部在**工具系统这一侧**声明，图那一侧执行（执行细节在
第 13 章 §13.5，这里讲「为什么是这样」）。

**第一层：值域校验——把「类型对」推进到「本轮见过」。** 每个 turn 维护一个 `ValueDomain`：

```go
// 本轮真正读到过的餐厅 id（搜索返回或名字解析确定的）与时段 id
type ValueDomain struct {
    RestaurantIDs map[int64]struct{}
    SlotIDs       map[string]struct{}
}

// 写参数必须落在值域里；读参数不检查（查库查空是无害的，拦住它只会把问题变成错误）
func ValidateWriteArguments(name string, args json.RawMessage, domain ValueDomain) error { ... }
```

注释把这条规则的存在理由写得毫不含糊：JSON Schema 能证明 `restaurant_id` 是个整数，
**证明不了它是用户被展示过的某家店**。一个被注入的模型若能随手挑一个 id，就能下单到一家
从未在对话里出现过的餐厅——这正是 schema 排除不掉的「看起来合法的坏动作」。值域校验对
**空集也严格**：一个从没搜到过任何餐厅的 turn，不可能合法地订任何一家；把「什么都不知道」
当作「没有限制」恰恰是要堵的洞。这套校验**只对写工具做**，对读工具不做。

**第二层：确认门——写路径在推理循环里根本不可达。** `request_reservation` 声明了
`ConfirmationRequired`，所以模型**每轮工具执行**遇到它都会截停：不执行、把它记成本线程的
待批动作、生成人话摘要、挂起等用户确认（`SummarizeApproval`）。而第二道保险在工具自己身上：
handler 第一件事就是检查 context 里有没有用户的批准，**没有就返回 `CodeAgentNoPendingAction`**。
这个错误的重试面是零——模型无论传什么参数都满足不了那个检查，所以**它无法靠「说服」绕过确认门**。
（`save_memory` 走的是 `implicit`：用户自己那句「记住我不吃辣」就是授权。它的替代保险是
**必须逐字引用用户原话**，一个自作主张决定某条偏好值得保存的模型，手里没有可引用的原话。）

**第三层：截停与保序——同一轮里，写操作后面的调用直接丢弃。** 一次出现写操作的扫描会让
本轮到此为止，其后的调用**全部作废**，理由是「不许对着一个写操作尚未建立的状态继续执行」。
同时，同一轮的多个**只读**调用会并发（至多 3 个），但**上层完全无感**：结果按**调用顺序**
折叠（不能用完成顺序 append），转录、turn 状态、下一轮看到的世界都与串行**逐 bit 一致**。
并发只在两处可见——时钟，和审计行的**写入**顺序。为了让「调用顺序」这个事实不随时间戳漂移，
并发启动前在主 goroutine 上预分配递增的 `seq`，审计表按 `seq` 排序读回调用顺序。

> 一句话记忆：**只读工具可以乱序完成，但必须按序折叠；写工具必须立刻停下整轮，且只有
> 用户能把它重新打开。**

## 14.8 专题：为什么是 Tool Calling，而不是 MCP

这一段回答一个一定会被问到的问题：2026 年的工具生态里 MCP（Model Context Protocol）很热，
这个项目为什么没用它？

**先厘清两者不在同一层。** 这是全段的关键：

```text
Tool Calling      ：模型输出「想调谁、参数是什么」的协议  →  模型 ↔ 运行时的对话格式
MCP               ：工具从哪里来、怎么被发现的传输协议   →  运行时 ↔ 工具提供方
```

MCP **不替代** tool calling。一个 MCP server 提供的工具，走到模型面前时，仍然要以
function calling 的 JSON Schema 形式出现——**MCP 解决的是「工具从哪来」，不是「模型怎么调它」**。

**再看这个项目的工具是什么形态：** 进程内、直连 store 的**确定性函数**。只有一个 client
（本服务自己的那张图），没有跨语言、跨进程、跨第三方共享工具的需求；而预约的 hold + 幂等
还要和本地状态、事务紧耦合。在这个前提下，上 MCP 的**净代价**是：

- 多一条**进程边界**与一次序列化往返（延迟）；
- 丢掉**编译期类型安全**（工具签名从 Go 类型变成运行时的字符串约定）；
- 破坏**事务与一致性边界**（写操作要跨进程协调）；
- 离线**契约测试**要额外拉起一个 server 进程才能跑；
- 而换来的东西是——**没有**。没有第二个 client 要复用这些工具，没有第三方要提供工具。

**那什么时候才该上 MCP？** 当工具满足下面任一条时，MCP 才开始划算：工具由**第三方**提供；
**多个 agent / client** 要复用同一组工具；工具需要**独立部署与独立演进**。项目在技术选型
里为这条未来路径**预留**了官方 Go SDK（`modelcontextprotocol/go-sdk`），但**没有现在就用**——
预留选型不等于提前付成本。真上 MCP 时，它在架构里的准确位置是**接在 `toolreg` 之后**
（作为「工具来源」），而**不是替代 `toolreg`**：注册表仍然是那个把工具变成「模型能看见、
参数能被校验、失败能被读懂」的地方。这条延伸路线在收官章还会再出现。

## 14.9 取舍与边界

**① schema 手写而不是反射生成。** 反射生成能消除「schema 与 args struct 不同步」这个隐患，
代价是 schema 的措辞成了类型系统的副产品——而**给模型的 `description` 是产品文案，值得逐字
推敲**，不是能从字段名推出来的。本项目选了手写，把「给模型看的话」当成一等公民来写，
同时用**注册期校验**兜住 schema 本身的合法性。边界：工具数量涨到几十个、description 不再需要
逐字雕琢时，反射生成会重新变得划算。

**② 封闭的 schema 子集，而不是完整的 JSON Schema 校验器。** 只支持 7 种 type + required/
properties/items/enum/additionalProperties:false，其余关键字忽略。代价是表达力有限（比如
不支持 `oneOf`、数值区间只在 `description` 里口头约定）；收益是「为什么这条参数被拒」
永远只隔一个函数，不依赖第三方校验器的行为。边界：真需要复杂 schema 组合时再换完整校验器。

**③ 工具失败是「数据」不是「异常」。** 五类失败全部转成结构化 `ToolResult`，把带路径的错误
文案交回模型。收益是推理循环不会被工具失败掀翻，模型的犯错可以自我纠正；代价是**程序员的错
也可能被降级成「模型看起来在瞎试」**——一个 handler 内部 bug 变成 `CodeInternal` 回给模型，
模型可能会换着参数反复重试。因此服务器日志与审计必须留痕（第 20 章），不能让真实的代码 bug
消失在「模型又调错了」的表象里。

**④ 值域校验只覆盖写工具。** 读工具不校验值域，是因为「查库查空」是无害的，拦住它反而把
一次正常提问变成一次报错。代价是一个被注入的模型可以**用读工具反复打库**（浪费预算）；
这一层目前靠工具轮次上限（5）和单轮并发上限（3）兜，真要防滥用得在更外层的限流做。

**⑤ 确认策略是三值枚举，不是 bool。** 见 14.3：bool 会让「需要确认」和「没想过」混为一谈。
代价是每个写工具都必须显式选一个策略、且 `required` 策略必须提供 `SummarizeApproval`；
收益是「一个无人授权的写操作」在**注册期**就不可能悄悄上线。

## 14.10 课后实验

**跑（全离线）**

```bash
cd chat-service
# 注册表契约：五种失败各返回什么、确认策略配对如何被拒
go test ./internal/agent/toolreg/... -count=1 -v
# 工具行为：plan 补齐、无条件下拒绝、resolve 三态、值域校验
go test ./internal/agent/tools/... -count=1 -v
```

**改（环境变量，观察能力表怎么变）**

```bash
# 关掉记忆写入 → save_memory 从模型的工具表里消失（而不是变成一个只会说"不行"的工具）
AGENT_MEMORY_WRITE_ENABLED=false make run-chat

# 关掉预约能力 → get_availability / request_reservation 两个工具都不再注册
RESERVATION_ENABLED=false make run-chat

# 调高相似度门槛 → resolve_restaurant 的 not_found 变多、resolved 变少
AGENT_RESOLVE_MIN_SIMILARITY=0.75 make run-chat
```

  [search_restaurants.go](../../chat-service/internal/agent/tools/search_restaurants.go)、

- 14.1 里模型给了两个调用（availability + reservation）。如果把它们**并发**执行会发生什么？
  截停规则为什么必须先扫一遍、而不是「跑到写工具再停」？（提示：reservation 的 `slot_id`
