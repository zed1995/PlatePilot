# 第 24 章 收官：从 PlatePilot 出发的延伸路线

> 上一章：[第 23 章 韧性与工程纪律](23-韧性与工程纪律.md) ｜ 回到：[课程提纲](00-课程提纲.md)
>
> 二十几章走下来，PlatePilot 已经不是"一个能聊天的餐厅推荐器"。它是一条**可引用的检索链**、
> 一张**可回放的 Agent 图**、一套**会失败的验收门禁**。这一章不做新功能，只做三件事：
> 把整门课连成一条线，指出五条真实的延伸路线，再把那些"很有名但这里没用"的技术放回它们该在的位置。

---

## 24.1 回头看一眼：一条从"幻觉"长出来的链

第 1 章留下的问题是：**模型会编餐厅，怎么让它说的每句话都能指回一条真实评论？**
后面每一章，都是在回答这个问题路上撞到的一堵墙：

| 墙 | 章节 | 技术答案 | 一句话原则 |
|---|---|---|---|
| 模型会编 | 1、9、16 | 证据块 + `reasons` + 引用闭包 | 无来源的引用，比没有引用更糟 |
| 语料太大 | 5 | 流式导入、预过滤、暂存后 rename | 先让数据可复现，再谈智能 |
| 关键词搜不到 | 6、7 | embedding + pgvector HNSW | 硬过滤必须先于向量召回 |
| 单通道会翻车 | 8 | 多路召回 + 融合 + 池内精确重排 | 召回是投票，融合是规则 |
| 证据塞不下 | 9 | 两级检索 + 2000 token 预算 + 整块丢弃 | 超预算就整块丢，不许半句引用 |
| 改了不知道好不好 | 10、21 | 规则评测 + 四道门禁 | 不能回放的改进不算改进 |
| 循环会失控 | 11、12、13 | Eino 状态图 + 检查点 | 控制流归代码，模型只做判断 |
| 工具会乱调 | 14、15 | 工具注册表 + schema + 槽位校验 | 结构化输出只保证合法 JSON，不保证业务合法 |
| 模型会说错 | 16 | 引用校验 + 违规替换 | 先发布，也要能撤回 |
| 记不住用户 | 17 | 记忆检索 + 注入预算 | 记忆是证据，不是事实来源 |
| 会写错库 | 18 | HITL + 幂等 | 有后果的动作必须有人确认 |
| 过程是黑盒 | 19、20 | SSE + 三级审计 | 一轮对话要能被重放 |
| 不会算账 | 22 | p50/p95 + 成本归因 | 先测量，再归因，最后优化 |
| 一坏就崩 | 23 | 降级矩阵 + 契约测试 | 能答就答，不能答就说清楚 |

如果只用一句话概括这 24 章：

> **让模型负责理解、规划和措辞；让代码负责计算、校验和落库；让数据库负责给出可引用的证据。**

三个角色各司其职，系统才既有"通用"的体验，又有"可审计"的底线。

还有一个更抽象的形状：整门课其实只建了两个闭环。

- **引用闭环（往外）**：答案 → 证据块 → 餐厅/评论/文档 → 快照与来源。
- **校验闭环（往内）**：模型输出 → schema/槽位/引用/预算 → 不合格就重试、降级或拒绝。

后面所有的延伸，本质上都是在扩大其中一个闭环的覆盖范围。

## 24.2 五条延伸路线：现在到哪，下一步是什么

### 24.2.1 Rerank：从"精确 cosine"到真正的交叉编码器

**现在到哪：**

第 8 章做了两层排序：

1. 多路召回后用规则融合；
2. 对候选池用**精确 cosine** 重算 profile / digest 文档的相似度（`rescore.go`），
   纠正 ANN"没进这一页"和"不相关"的混淆。

这不是 rerank，只是**把近似分数换成精确分数**。真正的 rerank 端口已经留好了：

```go
// shared/rerank/rerank.go
type RerankProvider interface {
	ModelID() string
	Rerank(ctx context.Context, query string, candidates []search.RestaurantCandidate) ([]search.RestaurantCandidate, error)
}
```

`ApplyRerank` 的行为也已经定死：没配 provider 就用融合顺序；provider 失败、超时（默认 3 s）、
返回的排列不是输入候选的合法排列，都保留融合顺序并把原因写进 trace。**端口有，provider 没有。**

**下一步：**

实现一个交叉编码器 provider：把 `(query, 餐厅证据摘要)` 成对打分，按分数重排。
它比 cosine 贵得多，所以只对融合后的一个小候选池做，而不是全库。

**什么时候值得接：**

- 召回已经足够好（目标餐厅基本都在池子里），但**前 5 名的顺序**仍然经常不对；
- 你有可回放的评测集，能证明接上之后命中@5 真的提升；
- 你愿意为每轮多付一次模型调用和一段延迟。

如果这三个条件不成立，接 rerank 只是给系统加了一个更贵的随机数。

### 24.2.2 Digest 溯源：从"引用了哪几条"到"是否真被支撑"

**现在到哪：**

离线 digest 已经做了**来源白名单校验**（`ParseDigestOutput`）：

- `source_review_ids` 不能为空；
- 每个 id 必须是本轮 bundle 里**真的提供过**的评论；
- 重复 id 去重，最后按升序存储，保证 provenance 可复现；
- 引用了一个没见过的 id，整份输出被拒绝——注释说得很清楚：
  "provenance pointing at a review the model never saw is worse than no provenance"。

这挡住了"编造评论 id"，但挡不住更隐蔽的一种情况：**id 都是真的，结论却不是那些评论说的。**

**下一步：**

做**claim-level entailment**：把 digest 的每个结论句拆出来，逐句判断它是否被所引评论支撑；
不支撑的句子要么删掉，要么标记为"低置信"。这一步可以离线做（便宜、可回放），
也可以在线做（贵、但能覆盖新生成的回答）。

**什么时候值得做：**

- 你开始用 digest 做面向用户的结论，而不只是检索摘要；
- 你发现"引用真实但结论过度概括"的 bad case；
- 你有办法把"支撑/不支撑"变成一条可评测的断言。

### 24.2.3 MCP：接在 toolreg 之后，而不是替代它

**现在到哪：**

项目的工具都在进程内：`search_restaurants`、`get_restaurant_evidence`、`resolve_restaurant`、
`save_memory`、`get_availability`、`request_reservation`。它们由 `agent/toolreg` 注册，
schema 与执行都在同一进程里。

技术 PRD 把 MCP 列为"可选工具协议和外部工具接入"（`modelcontextprotocol/go-sdk`），
但没有把它放进当前架构。原因不是"MCP 不好"，而是**当前没有它要解决的问题**：

- 工具来源单一，全部由本项目实现；
- 没有第三方工具要接；
- 没有多客户端复用同一套工具的需求；
- 引入远程工具协议，会多一个可被利用的入口，而收益为零。

**下一步（真要接时）：**

在 `agent/toolreg` **之后**加一层 MCP 适配器：把远端工具发现、调用、超时、错误映射成
现有的 `tool.ToolSpec`，图本身不感知 MCP。**协议属于工具层，不属于编排层。**

**什么时候值得接：**

- 要接第三方工具（地图、订座、支付）；
- 要让多个客户端/Agent 复用同一套工具服务；
- 工具需要独立部署、独立扩缩容或独立权限。

### 24.2.4 多用户：`X-User-ID` 是起点，不是安全方案

**现在到哪：**

README 写得很直接（逐字）：

> **Identity is a request header, not authentication.** `/v1` trusts whatever `X-User-ID` the caller sends, and `/admin/v1` is gated only by a loopback check — there are no credentials anywhere. This is deliberate for a local, single-user demo ... and it is the first thing to replace before any multi-user or hosted deployment.

——**"身份是一个请求头，不是认证。`/v1` 信任调用方发来的任何 `X-User-ID`，
`/admin/v1` 只靠 loopback 检查——整个系统没有任何凭据。这对本地单用户 demo 是刻意的，
也是多用户或托管部署前第一个要替换的东西。"**

**下一步（按顺序）：**

1. **认证与授权**：把 `X-User-ID` 换成经过验证的身份，并给每个资源加所有权检查；
2. **租户隔离**：会话、记忆、预约、审计都要能按用户隔离，且删除/导出可审计；
3. **输入/输出护栏**：moderation、jailbreak 分类、输出 PII/毒性过滤；
4. **额度与限流**：每用户 token/轮次配额，防止一个用户把成本打满；
5. **数据生命周期**：账号删除、记忆导出、预约残留（README 已指出删除会话不会删预约行）。

**什么时候值得做：**

- 只要第二个人能用，第 1 步就必须做；其余步骤按开放程度逐步加。
- 单用户本地 demo 不需要为了"看起来安全"而提前加一层没有威胁模型的鉴权。

### 24.2.5 Fine-tune 与拆库：两个"涨一个数量级再说"的决定

**现在到哪：**

- 没有 fine-tune。第 1 章的取舍说得很清楚：不引入搜索引擎/专用向量库/消息队列，
  先用 Postgres 的 pgvector / PostGIS / pg_trgm 把闭环跑通。
- 单库同时承担结构化过滤、向量召回、模糊文本、运行时表。第 5 章解释过理由：
  如果过滤在 Postgres、向量在专用库，你就得先把过滤结果跨系统搬运，硬过滤先于向量召回的保证就断了。

**什么时候值得 fine-tune：**

- prompt 工程 + 检索质量 + 工具设计都已经到位，指标仍然平台化；
- 你有足够多**标注过的**（query → 正确餐厅/正确工具序列）数据；
- 领域语言有明显分布差异（本地化菜系、街区别名），通用模型反复误解；
- 你能承担重训、回归评测和版本管理的成本。

**什么时候值得拆专用检索/向量存储：**

- 语料再涨一个数量级（现在是约 27 万家 POI、3350 万条评论、2.9 GB 本地语料）；
- 单库的 HNSW 构建/更新窗口开始影响在线查询；
- 过滤与向量需要独立扩缩容，或者需要跨地域复制；
- 你能接受"硬过滤先于向量召回"这件事由两个系统共同保证——这会显著提高工程复杂度。

**顺序很重要：** 先 fine-tune 还是先拆库，取决于瓶颈是"模型不懂"还是"检索不够快/不够准"。
不要因为"大厂都这么做"而提前拆。

## 24.3 附：本项目没用到的常见 Agent 技术

下面这些技术在 Agent 开发里很常见，各自解决一个具体问题。这个产品形态不会遇到那个问题，
所以正文不展开。每条只讲三件事：**它解决什么、这里为什么用不上、什么时候该回来找它。**

### 24.3.1 规划范式：Plan-and-Execute、Reflection、ToT/LATS

- **解决什么**：让模型先出多步计划、对中间结果自我批判重来，或在多条推理分支里搜索。
- **这里为什么不用**：PlatePilot 的一轮是"检索 + 少量工具"的短流程，一步 ReAct + 状态图足够。
  加规划/反思/树搜索只会更贵、更不稳，还会把可回放的控制流重新交回给模型。
- **什么时候回来**：任务变成"多约束行程规划"、"跨天预订协调"这类步骤多、可试错、
  单步 ReAct 明显走不动的场景。

### 24.3.2 多 Agent 协作：supervisor/worker、handoff、debate、A2A

- **解决什么**：把任务拆给多个角色 agent 互相调用，适合职责差异大、需要对抗式校验的场景。
- **这里为什么不用**：单 agent，工具即能力边界。多 agent 会引入跨 agent 的状态、通信、
  权限与审计复杂度，而当前的职责并没有大到需要拆。
- **什么时候回来**：出现真正独立的角色（例如"检索员 + 预订员 + 审核员"）且它们需要独立部署、
  独立权限或独立模型时。

### 24.3.3 工具规模化：tool retrieval / 动态工具加载

- **解决什么**：工具有上百个时，先检索出"这轮该用哪几个"再喂给模型。
- **这里为什么不用**：只有 6 个固定工具，注册表全量声明即可，没有挑选成本。
- **什么时候回来**：工具数量增长到模型无法稳定选择，或大量工具来自不同团队/第三方时。

### 24.3.4 护栏框架：moderation、jailbreak 分类、输出 PII/毒性过滤

- **解决什么**：多用户线上产品的标配，防止滥用、注入和有害输出。
- **这里为什么不用**：本地单用户 demo，语料已脱敏；没有开放输入面。
- **什么时候回来**：对外开放的第一天。它和多用户认证是同一批工作，不是"以后再说"的优化项。

### 24.3.5 受约束解码 / 结构化输出：JSON mode、GBNF、Outlines

- **解决什么**：从解码层保证模型只能吐合法 JSON/枚举。
- **这里为什么用了一半**：API 层用了 `response_format=json_schema` 严格模式做槽位抽取；
  provider 不支持时降级 `json_object` 并重试一次（第 15 章）。
- **为什么从不信任它**：结构化输出只保证"合法 JSON"，保证不了业务合法——行政区真实存在吗？
  证据 ID 本轮真的有吗？语义校验仍在代码侧，不合格整体降级到规则抽取。
- **GBNF/Outlines 为什么没引入**：它们是本地解码层约束，需要自己托管模型；当前用 API 模型，
  这层控制不在手里。等自托管或本地小模型成为主路径时再考虑。

### 24.3.6 语义缓存 / prompt 缓存

- **解决什么**：对相同或相近的请求直接复用结果，省时省钱。
- **这里为什么不用**：语料小、问答长尾、命中率低；在线缓存会把"可复现"变成"看命中"。
  项目只在**离线 digest** 用了 bundle-hash 缓存——同样的输入 bundle 不重复花钱。
- **什么时候回来**：出现明显的重复查询分布（例如同一批热门餐厅被反复问），
  且你能接受缓存一致性/失效策略的复杂度。

### 24.3.7 上下文压缩 / 历史摘要

- **解决什么**：长对话把早期历史 summarize 成一段再注入，控制上下文长度。
- **这里为什么不用**：靠"记忆检索"控制注入窗口（第 17 章），只注入与本轮相关的记忆；
  还没到需要摘要的规模。
- **什么时候回来**：单用户对话长度或记忆条数增长到"扫描全部记忆"不再免费时。
  README 给过触发条件：`<1k memories/user` 是当前假设，超过后再改注入策略，而不是先换索引。

### 24.3.8 代码沙箱 / code interpreter、多模态

- **解决什么**：让 Agent 执行代码，或处理图像/音频。
- **这里为什么不用**：产品是"文本餐厅检索"，没有代码执行面，也没有多模态输入。
- **什么时候回来**：出现"帮我算一下这桌人均"之外的真正计算任务，或用户开始发菜单照片/语音时。
  注意：代码沙箱一旦引入，就是一个全新的安全边界，不能顺手加。

## 24.4 如果要把这个 demo 推上线：一张检查清单

这部分不是课程计划，只是一张把"演示"变成"产品"的清单。每一项都能在正文里找到对应的墙。

**身份与数据**

- [ ] 用真实认证替换 `X-User-ID`；所有资源加所有权检查（会话、记忆、预约、审计）。
- [ ] 给 admin 面加真正的鉴权，不再只依赖 loopback。
- [ ] 明确数据生命周期：账号删除、记忆导出、会话删除后的预约残留。

**安全与合规**

- [ ] 输入 moderation / jailbreak 防护；输出 PII、毒性过滤。
- [ ] 预约写操作的权限与审计：谁批准了什么，依据是哪一版 policy。
- [ ] 密钥只走环境变量/密钥管理，日志用 `Redacted()`。

**可靠性**

- [ ] 给 p95、错误率、降级率设 SLO 与告警（第 22、23 章）。
- [ ] 单 Postgres 的备份/恢复演练；迁移只在 pipeline 跑，服务启动只做 `VerifySchema`。
- [ ] 审计表按保留期归档；接受"审计写入不决定成败"的取舍，并监控缺行。

**成本与体验**

- [ ] 每用户配额与限流；模型路由（plan/answer/extract 分开）。
- [ ] 证据预算、工具轮次、澄清次数保持为可配置护栏，而不是散落的常量。
- [ ] 缓存策略只在有重复分布时引入，并明确失效规则。

**质量**

- [ ] 用真实流量扩充评测集；保持离线可跑、真库可门禁。
- [ ] 每次改检索/提示/工具，都过第 21 章的四道门禁，再看第 22 章的性能表。
- [ ] 把"降级可见"写进验收：trace 里缺一条 `ran:false`，也算回归。

## 24.5 留给你的三个练习

1. **接一个 rerank provider。**
   实现 `shared/rerank.RerankProvider`，在装配层注入 `deps.Rerank`，只对融合后的前 N 个候选打分。
   要求：不改图、不改工具；失败/超时/非法排列都必须保留融合顺序；在 trace 里能看到
   `ModelID` 与 note。做完后，用第 21 章的评测集回答一个问题：命中@5 真的提升了吗？

2. **给 digest 加一条 claim-level 校验。**
   在 `ParseDigestOutput` 的 id 白名单之后，再加一层"结论句是否被所引评论支撑"的检查。
   要求：不合格的句子被删掉或标低置信，而不是整份 digest 失败；检查过程可回放；
   在离线阶段跑，不增加在线延迟。做完后，找一个"引用真实但结论过度概括"的 bad case 验证它。

3. **把 `X-User-ID` 换成一个最小可用的认证。**
   要求：不改变 Agent 图；所有/v1 资源做所有权检查；admin 面加独立鉴权；
   现有测试仍能离线跑。做完后，写一条"越权访问别人的会话"的测试，并让它失败过一次——
   先证明旧代码真的会泄露，再证明新代码挡住了。

这三个练习分别对应三条延伸路线：**排序、溯源、多用户**。
它们都不需要重写课程里的任何一章，只需要在已经留好的端口上继续加。

---

## 24.6 结课：三条可以带走的判断

**1. 控制权放在代码里，能力放在模型里。**

模型擅长理解意图、选择工具、组织语言；它不擅长保证"行政区真实存在"、"证据 ID 本轮真的提供过"、
"这一轮最多调 5 次工具"。把这些交给代码，模型才可以被替换；把理解交给模型，系统才不需要穷举规则。
第 11–16 章做的全部事情，本质上都是在划这条边界。

**2. 两个闭环，缺一不可。**

引用闭环让答案能指回证据；校验闭环让证据能否掉答案。
只有引用没有校验，系统会自信地引用错东西；只有校验没有引用，系统会正确地拒绝回答一切。
PlatePilot 的可用性，来自两个闭环同时存在。

**3. 降级必须可见，验收必须可回放。**

第 21 章的四道门禁和第 23 章的降级矩阵，是同一件事的两面：
**正常路径要能被证明正确，异常路径要能被证明没有伪装成正常。**
一个系统如果做不到这两点，它仍然可以演示，但不能被运营。

如果只能记住一句话：

> **不要问"Agent 能不能做这件事"，要问"它做完之后，我们能不能证明它做对了、并知道它花了多少"。**

这句话能回答后面绝大多数技术选型。课程到这里结束，项目还在继续。
