## 23.1 坏 case 开场：两次"成功"的故障

先看两个都不报错、但都已经坏掉的场景。

**场景一：语义检索悄悄消失了。**

Ollama 没起来，embedding provider 构建失败。服务没有退出，检索仍然返回结果——
结构化过滤和关键词召回还在工作。用户看到一页餐厅，觉得"能用"。
但如果 `trace.channels` 里没有把向量通道标成"未运行"，也没有一句"已关闭"的说明，
那么所有人都会以为语义召回参与了排序。**结果变差了，而系统没有任何一处承认它变差了。**

**场景二：二进制比数据库新。**

服务升级了，迁移没跑。审计写入缺一列。审计钩子的设计是"写入失败不决定一轮的成败"，
于是错误被吞掉、只进日志；读路径拿到同样的缺列错误，却只能把它报成"上游不可用"。
一次 schema 落后，最后表现为**审计悄悄缺行 + 用户看到一次不明所以的 502**。

代码里对这件事写得很直白（逐字）：

> A service whose schema is behind its binary must not start. The alternative is not "it works anyway": the audit path swallows write errors by design, so a missing column costs the trail silently, and the read path reports it as an upstream outage. Failing here is the one place the fault is cheap to see.

——**"二进制比 schema 新时，服务不该启动。替代方案不是'照样能跑'：审计路径按设计吞掉写错误，
所以缺一列会让审计悄悄缺行，而读路径会把它报成上游故障。在这里失败，是唯一能让故障变便宜的地方。"**

这两个场景给出了本章的两条主线：

1. **能继续给出正确答案的，就降级，但必须让降级可见。**
2. **不能继续给出正确答案的，就在最便宜的地方失败，而不是把错误翻译成别的错误。**

## 23.2 概念与原理：降级是一张事先写好的矩阵

### 23.2.1 先分类：配置错误，还是运行时故障

处理故障的第一步不是"加重试"，而是判断它属于哪一类：

| 类别 | 例子 | 正确反应 |
|---|---|---|
| 配置错误 | 设置了 `CHAT_PROVIDER` 却没给 key；`RESERVATION_ENABLED=true` 却没有预约库 | 拒绝启动，点名缺什么 |
| 能力缺失 | 完全没配 chat provider；没配 embedding；没配 rerank | 把能力从模型/用户视图里拿掉，或明确报"不可用" |
| 运行时抖动 | 429、408、5xx、连接被重置、空 200 | 有界重试 + 退避 |
| 单次失败但可继续 | 审计写失败、池内重排失败、rerank 超时 | 继续这一轮，记录降级 |
| 结构性不一致 | schema 落后、迁移没跑 | 拒绝启动 |

这张分类决定了后面所有动作。**把配置错误当运行时抖动去重试，是最常见的一种浪费：
重试不会把一个空 key 变成有效 key。**

### 23.2.2 四种动作，一张矩阵

项目在装配层（`chat-service/internal/app/app.go`）把每个能力的状态写成了明确分支，
而不是散落在各个 handler 里。矩阵大致是这样：

| 能力 | 缺失/故障状态 | 行为 | 可见性 |
|---|---|---|---|
| Chat provider | 完全没配 | 搜索/证据/线程/记忆接口照常；发消息返回 `provider_unavailable` | 明确的错误码；不伪造一轮回答 |
| Chat provider | 配了但构建失败 | 拒绝启动 | 启动日志点名配置项 |
| Embedding | 构建失败 | 检索退回结构化 + 关键词 | 启动 warn；`trace.channels` 中向量通道 `ran=false` |
| 知识库 | 没配 | 语义通道关闭 | 启动 warn；trace 记录未运行 |
| Rerank | 没配/失败/超时/返回非法排列 | 保留融合顺序 | trace note；这一轮继续 |
| 池内重排 | 查询失败 | 保留召回分数 | `Rescore.Warnings` 进入 trace |
| 流式回答 | provider 不支持流 | 退回一次性生成 | warning："答案流式不可用，已退回一次性生成" |
| 上游 | 429 / 408 / 5xx / 连接失败 / 空 200 | 有界重试（默认 2 次，指数退避，尊重 `Retry-After`） | 只有重试耗尽才把这轮判失败 |
| 工具参数 | 模型返回畸形 JSON | 不重试 | 按不可重试的上游响应处理 |
| 审计 | 没配 run 仓库 | 这一轮照常跑 | 启动 warn："agent turns run without audit trail" |
| 审计 | 写失败 | 这一轮照常跑 | 服务端日志；审计行缺失 |
| Schema | 落后于二进制 | 拒绝启动 | 启动错误点名迁移 |
| 预约 | 开关开着但没有预约库 | 拒绝启动 | 启动错误点名开关 |
| 预约 | 有库但没有会话库 | 降级为"只能查可用性" | 启动 warn：booking 无法在会话里确认 |
| 记忆写入 | 开关开着但没有记忆库 | 不注册 `save_memory` | 启动 warn：工具不会出现 |

**矩阵的价值不在表格本身，而在"每一格都有人事先决定过"。** 没决定的格子，上线后就会由
某个 handler 临时决定，通常表现为一句含糊的 500。

### 23.2.3 为什么"chat 没配"不等于"拒绝启动"

一个很自然但错误的规则是：既然 M4 之后模型是主路径，那没有 chat provider 就该拒绝启动。

项目的实际选择更细（`app.go` 注释，逐字）：

> The agent runner is assembled only when a chat provider was supplied. Without one the HTTP search/evidence API still runs; the conversational turn path simply stays unwired, mirroring the embedding degradation.

——**"只有提供了 chat provider 才装配 Agent runner。没有它时，HTTP 搜索/证据 API 照常运行；
对话 turn 路径只是没有接线，和 embedding 的降级方式是同构的。"**

于是行为被拆成两种，而不是一刀切：

- **完全没配**：搜索能用，线程和记忆接口能用，发消息得到 `provider_unavailable`
  （`chatService` 里就是 `if s.runner == nil { return CodeProviderUnavailable }`）。
- **配了但配错**（缺 base URL、key、model）：`config.Validate()` 直接拒绝启动。

这个区别很重要：**"没有这个能力"和"这个能力配坏了"是两种不同的事实**，前者可以降级，
后者必须修配置。把它们混成一种，要么让可用的搜索被无谓地拖死，要么让一个空 key 的服务假装能聊天。

### 23.2.4 为什么 schema 落后必须拒绝启动

这是少数**不能降级**的地方。原因是降级会同时污染两条路径：

- 审计写入失败是"按设计吞掉"的，缺列不会让这一轮失败，只会让记录悄悄少掉；
- 读路径拿到同一个错误，却只能翻译成"上游不可用"。

两种表现都不是事实本身。启动时 `VerifySchema` 只做只读检查，失败就退出，并点名缺哪一版迁移——
**这是整条链路里唯一能便宜看到这个故障的地方。** 迁移的应用仍然只归 `data-pipeline`，
服务启动时绝不自动改 schema（见根 `AGENTS.md` 的硬规则）。

### 23.2.5 重试只属于"临时问题"

项目的 chat 客户端只对一部分失败重试：

- HTTP **429**（限流）、**408**（请求超时）、**5xx**（上游故障）；
- 连接层错误；
- **200 但 choices 为空**——注释说得很清楚，这是"过载路由上的瞬时丢包，不是 provider 拒绝了请求"；
- 200 但 body 里带 error 且其 code 可重试。

不重试的包括：

- **400**：请求本身有问题；
- **401/403**：认证/权限问题；
- **402/404**：额度用完、模型 id 没有 endpoint——都是配置错误；
- **模型返回畸形 tool arguments**：这是坏响应，盲目重试只会得到同样的坏响应。

重试本身也有边界：默认 `CHAT_MAX_RETRIES=2`，指数退避，上游给了 `Retry-After` 就按它等
（包括 `0` 表示立即重试）。**重试不是"更努力"，它是在花更多钱买同一个不确定性。**

### 23.2.6 降级必须可见：三个出口

一条降级如果没人看见，等于没降级。项目把"可见"分成三个出口：

1. **用户能读到的 `warnings`**：例如"答案流式不可用，已退回一次性生成"。
   面向用户的解释性文案是中文。
2. **`trace.channels`**：每个通道都有 `ran` 和 `note`；被关掉的向量通道必须记录为
   **未运行**，note 里要出现"已关闭"。测试 `TestDisabledVectorChannelIsRecordedNotRun`
   就是为这一条存在的。
3. **服务端日志**：审计写失败、记忆写开关没有库、预约没有会话库——这些不影响用户答案，
   但运维必须能查到。

这三者的分工是：**用户需要知道"这次的答案少了什么"，运维需要知道"系统哪里在带病运行"。**

## 23.3 承载思路的最小示例：一个降级单元的形状

下面是一个通用的降级单元骨架，和项目里的 `Rescore`、`ApplyRerank`、审计钩子共享同一种形状：

```go
// Outcome 表示"一次可选增强的结果"。
// Value 永远可用；Applied 区分"没配/没跑"与"跑了但失败"；
// Note 是一句能进 trace 或 warnings 的中文说明。
type Outcome[T any] struct {
	Value   T
	Applied bool
	Note    string
}

func withFallback[T any](
	ctx context.Context,
	name string,
	run func(context.Context) (T, error),
	fallback T,
) Outcome[T] {
	value, err := run(ctx)
	if err != nil {
		// 关键：不把错误变成这一轮的失败，但也不假装增强发生过
		return Outcome[T]{
			Value:   fallback,
			Applied: false,
			Note:    name + "未生效，已使用基础结果",
		}
	}
	return Outcome[T]{Value: value, Applied: true}
}
```

三个字段各有职责：

- `Value` 保证调用方**永远拿到一个能用的结果**——降级不是返回零值让上层崩。
- `Applied` 让上层能区分"从未配置"和"配置了但这次失败"，这两件事在运维上完全不同。
- `Note` 保证降级**有地方被看见**；没有 note 的 `Applied=false` 仍然是一次静默降级。

项目里的实现比这个骨架多两件事：**超时**（`ApplyRerank` 默认 3 s）和**结果合法性校验**
（rerank 返回的排列必须恰好覆盖输入候选，少了、重了、多了都算失败）。这两件事都属于
"运行时故障"的判断，不是业务逻辑。

## 23.4 一套契约，两个实现

韧性不只体现在降级，还体现在**你怎么证明两个实现真的做同一件事**。

`shared/store/contract` 定义了三套行为契约：

- `contract.Run`：写侧与内容仓储（餐馆、评论、知识文档，以及会话、记忆、预约、run 审计）；
- `contract.RunRead`：读侧仓储（餐厅检索、详情）；
- `contract.RunKnowledgeRead`：知识文档读取。

然后两个适配器跑**同一套断言**：

| 适配器 | 跑在哪 | 没数据库时 | 证明什么 |
|---|---|---|---|
| `shared/store/memory` | `make test`，完全离线 | —— | 行为契约本身；单元测试可以默认离线 |
| `shared/store/postgres` | `make test-postgres` | skip，不 fail | pgvector / PostGIS / pg_trgm 真的在干活 |

为什么不能只测内存实现？因为 Postgres 适配器的价值恰恰在那些**double 伪造不了**的地方：
HNSW 的排序、partial index 的命中、`pg_trgm` 的相似度、PostGIS 的距离。一个内存 map
可以通过所有断言，却完全不能说明真实 SQL 是对的。

为什么又要默认离线？因为大部分逻辑（分页、所有权、幂等、状态机）不需要数据库。于是规则是：

- **默认离线可跑**：`make test` 不依赖外部服务；
- **需要真库的测试在没有库时响亮地 skip**，而不是 fail；
- **需要当门禁时，用环境变量把 skip 变成 fail**：`PLATEPILOT_REQUIRE_DB=1`、
  `PLATEPILOT_REQUIRE_VECTOR=1`。

这套设计承认了一个矛盾：**离线套件方便，但会和真库漂移；真库套件可信，但不能每次提交都跑。**
契约测试是两者之间的桥：同一套断言，两种执行环境，漂移会在 `make test-postgres` 里暴露。

`shared/store/memory/store_contract_test.go` 里的
`TestMemoryStoresSatisfyContract`、`store_read_contract_test.go` 里的
`TestMemoryReadStoresSatisfyContract`、`postgres/contract_test.go` 里的
`TestRestaurantStoreContract`，名字不同，跑的是同一份 `contract.Run` / `RunRead`。

## 23.5 可复现与架构边界：把纪律写成会失败的测试

### 23.5.1 确定性：同样的输入，同样的输出

检索是一门"看起来有很多随机"的工程：ANN 近似、多路融合、浮点分数。项目的要求是
**可复现排序**：同样输入必须返回同样结果。做法不是祈祷，而是给排序写死决胜规则。

融合层在分数相同时按餐厅 id 决胜，注释（逐字）：

> A scoring model that rewards the id is false precision dressed as arithmetic; a stable tie-break is what makes the ranking reproducible.

——**"把 id 当成评分是在给假精确披上算术的外衣；稳定的决胜规则才是让排序可复现的东西。"**

同理，第 21 章的回放测试要求两遍逐 bit 一致。**只要排序里出现 map 遍历顺序、当前时间、
随机数，这个测试就会红。** 这不是"测试太严"，这是把"可复现"从一个愿望变成一条会失败的断言。

### 23.5.2 依赖方向：三条会失败的边界

仓库的架构约束不是文档里的箭头图，而是 AST 测试：

- `shared/domain/architecture_test.go`：领域层不许出现 `postgres` / `postgis` / `pgvector` / `sql`
  这些词——**源码和注释都算**。领域类型不知道存储引擎。
- `chat-service/internal/agent/architecture_test.go`：Eino 类型只准出现在
  `internal/agent` 与 `internal/app`（仅装配模型实例）；
  `agent` 与 `app` 之外的包不许出现 Eino。
- `chat-service/internal/admin/architecture_test.go`：`admin` 不许 import 具体的 store 适配器，
  只能面向端口。

还有一条跨模块的：`chat-service` 与 `data-pipeline` **绝不互相 import**，要共用就下沉到
`shared/`。这些测试红了的正确反应是**想是不是分层放错了**，而不是改测试放宽它。

### 23.5.3 表集与响应契约

两个服务都写库，但表集不重叠：`data-pipeline` 写内容表（餐馆、评论、知识文档），
`chat-service` 写运行时表（会话、run 审计、记忆、预约）。schema 只有 `data-pipeline migrate` 能改。

`/v1` 下的响应体是客户端契约：`reasons`、`trace.channels` 会被 UI 直接读，
字段变更属于破坏性变更。**这条纪律和降级是同一件事的两面**：
你承诺了 trace 里有什么，就不能在降级时悄悄少给。

## 23.6 取舍与边界

**1. 吞掉审计错误，是用可观测性换可用性。**

`audit/hooks.go` 开头写得很清楚：审计写入从不决定一轮的成败，每个方法都吞掉仓储错误并记录日志。
这个取舍在"审计库短暂不可用"时是对的：用户不该因为一条日志写不进去就丢掉回答。
但它也带来一个后果：**审计表不是完整档案**。所以 schema 检查必须在启动时把它们挡在门外，
否则你会在一个本来就"允许缺行"的表上，叠加一次"悄悄缺列"。

**2. 降级太多，会变成能力悄悄消失。**

每个降级都必须有 `warnings`、trace note 或启动 warn。没有出口的降级不是韧性，是隐瞒。
判断标准很简单：**如果运维不看代码，能不能从输出里知道这次答案少了什么？**

**3. 重试会放大拥塞。**

上游已经 429 了，所有客户端一起重试只会更糟。项目的边界是：最多 2 次、指数退避、
尊重 `Retry-After`、流式请求在首字节前失败才重试（没发布过内容，调用方看不出重试）。
写操作能安全重试的前提是第 18 章的幂等设计，不是"重试本身很安全"。

**4. 离线测试会漂移。**

内存实现能证明契约，不能证明 SQL。承认这一点，才会有 `make test-postgres` 和契约套件。
**不要因为"内存测试绿了"就认为真库没问题。**

**5. 不要给降级加降级。**

一个能力失败后，应该回到"基础结果"，而不是再调用另一个可选能力去救。
矩阵的每一格都应该是**一步到位**的：rerank 失败就保留融合顺序，不再去调池内重排；
语义通道失败就用结构化+关键词，不再去猜一个替代模型。多层 fallback 会把延迟和故障面一起放大。

**6. 矩阵应该只有一个所有者。**

这些判断集中在装配层，而不是散落在 handler、tool、store 里。原因很实际：
**同一个能力在两处被判断，就会出现两种降级行为。** 装配层是唯一同时看得见所有依赖的地方，
也应该是唯一决定"缺了它怎么办"的地方。

## 23.7 课后实验

**跑：**

1. **离线全套**：

   ```bash
   make test
   ```

   确认没有数据库也能全绿。这是第 6 节测试约定的第一条：默认离线可跑。

2. **真库契约套件**：

   ```bash
   make pg-up
   make test-postgres
   ```

   再跑一次 `PLATEPILOT_REQUIRE_DB=1 make test-postgres`。第二次即使你把数据库停掉，
   也不该"安静地绿"——它应该 fail，因为门禁模式把 skip 变成了失败。

3. **观察 embedding 降级**：先确保 Ollama 没在运行（或把 `EMBEDDING_PROVIDER` 设为空），
   然后：

   ```bash
   make run-chat-admin
   curl -s 'localhost:8080/v1/search?q=安静的意大利餐厅&borough=Brooklyn' | jq '.trace.channels'
   ```

   找到向量通道，确认 `ran=false` 且 note 说明它被关闭。**如果结果仍然正确但没有这条记录，
   就是一次静默降级——这正是本章要消灭的东西。**

4. **观察 chat 缺失的两种表现**：

   ```bash
   # 完全没配：搜索照常，发消息应得到 provider_unavailable
   # 配了但缺 CHAT_BASE_URL：Validate 应在启动时就拒绝
   ```

   先不配 provider 启动，`curl` 搜索接口；再向 `/v1/conversations/:id/messages` 发一条消息，
   读错误码。然后把 `CHAT_PROVIDER` 设成一个值但不给 `CHAT_BASE_URL`，重启，
   确认它**不进入服务循环**，而是在启动时报配置错误。

5. **schema 落后的实验（只在 scratch 库做）**：在一个一次性数据库里跑完迁移，
   删掉 `schema_migrations` 的最后一行，再启动服务。预期是启动失败并点名缺哪一版，
   而不是"服务起来了、审计少几行、读接口报上游错误"。
