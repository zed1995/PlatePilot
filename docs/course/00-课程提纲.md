# 《动手做一个"有据可依"的 AI Agent》课程提纲

> Go + Eino + RAG 从入门到实战
> 基于 PlatePilot 真实仓库（M0–M6 全部落地）梳理，版本日期：2026-10-11

---

## 一、课程定位

我们手里有一份真实的大数据：Google Local 纽约市 **27 万家 POI、3350 万条评论**（gzip JSONL，2.5 GB）。
要做的产品是一个餐厅发现 Agent——用户用自然语言提问，它负责搜索、推荐、解释、追问，
甚至走到预约确认；而它最硬的一条约束是：

> **用户看到的每一个结论，都必须能指回一条真实评论。**

这条约束的起点是**幻觉**：模型不是"不知道就不说话"——没有餐厅数据时，它会一本正经地编出店名、
评分和"这家很安静"这类体验判断；而把数据塞进上下文之后，它照样会编。**"不要编"这种提示词
永远治不好它，因为模型无法验证自己没编**——所以"引用闭环"只能是架构级约束，不是提示词工程。

顺着它往下走，会一路逼出本课程的全部技术点：流式数据处理、embedding、向量索引、多路召回融合、
证据组装、工具调用、图编排、人工确认门、长期记忆、SSE 流式协议、运行审计、Agent 评测门禁与性能核算。

> **第二条闭环——校验闭环**：模型吐出来的每一件结构化产物（工具参数、槽位、引用的证据 ID、
> digest 的来源 ID），在没有被代码校验过之前都不可信。两条闭环一进一出——引用闭环管"给用户看的"，
> 校验闭环管"模型给的"——会贯穿后面很多章。

课程不按技术点的教科书顺序讲，而是按**一个 Agent 长出来的真实顺序**讲：先写一个最丑但能跑的
for 循环，再带着它一次次撞墙，每面墙对应一个真实技术与项目里的真实取舍。

### 叙事主线

```text
一个 40 行的 for 循环 Agent
  → 它不知道餐厅数据，就一本正经地编  → 撞上第一面墙：模型幻觉
  → 给了数据它还会编（prompt 治不好）  → 数据工程 + RAG + 向量检索
  → 单通道检索频频翻车                → 多路召回 + 融合 + 证据闭环
  → 循环里长出状态/追问/写操作         → 手写循环失控 → Eino 图编排
  → 工具写死、模型不听话              → 工具注册表 + 槽位抽取 + HITL 确认门
  → "看起来能用"但无法证明对          → 审计 + SSE + 评测门禁 + 性能与韧性
```

这条线与项目真实的里程碑 M0→M6 重合，但教学顺序不照抄里程碑。

## 二、受众与学习方式

- **受众**：有任意语言工程经验、没做过 LLM 应用的工程师。**不教语言语法**（Go 的接口、
  并发等只作为架构思想出现，不解释语法细节）。
- **产出形式**：纯 Markdown 文档。不新增可运行代码、不新建教学项目；每章只内嵌少量
  承载思路的精简片段（通常 10–40 行）；仓库真实实现不逐行走读，而是作为佐证收进
  每章末的「参考代码与目录」。
- **课后动作**统一为三类：**读**（按章末「参考代码与目录」按图索骥）、**跑**现成命令
  （`curl`、`make eval-*`、`EXPLAIN`）、**改**环境变量观察行为变化。
- **原理深度约定**：所有原理（HNSW、图调度、embedding、SSE 等）讲到**核心思想与关键过程**
  为止，能解释"为什么这样设计、不这样会怎样"即可，不逐行抠源码、不推导公式。
- **环境**：Go 1.26+、Docker（本地 Postgres，自带 pgvector + PostGIS）、Node 18+（前端）、
  Ollama（本地 embedding）。准备步骤见开篇词。

### 每章统一结构

1. **坏 case / 真实需求开场**：一个不解决就过不去的问题。
2. **概念与原理（正文主线）**：把这一类问题的通用知识与思路讲清楚，配图或表格，
   不堆术语。这是正文主体——读者**不看代码也应当读得懂**。
3. **承载思路的最小示例**：文档内一段 10–40 行的精简片段，只为说明思路，
   不是仓库源码的搬运。
4. **取舍与边界**：为什么这么做、什么场景要重新考虑、代价是什么。
5. **课后实验**：跑现成命令、改环境变量观察行为（「读」由章末参考目录引导）。
6. **参考代码与目录**：本章涉及的仓库真实文件、函数与实测数字集中在**章末**，
   供想深入实现的读者按图索骥。正文不逐行走读代码。

> 注：开篇词（第 0 章）与收官（第 24 章）不套此结构，按各自文体组织；第 1–23 章统一遵循。

### 第一篇 Agent 入门——从一个 for 循环开始

#### 第 1 章 需求与数据：我们到底在解决什么问题

- 数据盘点：Meta 原始 schema（name/category/avg_rating/price/hours/MISC…）与 Review schema；
  272k 行 meta、33.5M 条评论里**只有 12.7% 可导入**，这个数字如何决定后续所有设计。
- 需求拆解：自然语言搜索、推荐、体验类问答、追问、可选 mock 预约；中英文。
- 核心产品原则："**模型负责理解、规划和表达；数据库与领域服务负责确定性查询和写入**"。
- 先立问题再立方案：模型在没有语料时会**幻觉**——编店名、编评分、编主题观点，而且把语料
  放进上下文也治不好；「不要编」这类提示词为什么不成立（模型无法自证没编）。
- 为什么"证据可溯源"因此是架构级约束而不是提示词：它决定了召回分两级、证据有预算、
  回答要重新校验、digest 永不可引用。
- 锚点：`docs/platepilot-technical-prd.md` §1–2、`data/demo/demo_restaurants.json`、`README.md`。

#### 第 2 章 概念速成：聊天模型、Embedding、Tool Calling、RAG、Agent

一张概念地图讲完入门术语，每个都配一句"在 PlatePilot 里它对应什么"：

- token 与 chat completion；system / user / assistant / tool 四类消息。
- embedding：把文本变成向量，向量距离 ≈ 语义相似；为什么中英文混用语料也要本地模型。
- tool calling（function calling）：模型不执行函数，只输出"想调谁、参数是什么"的结构化请求。
- RAG：检索增强生成的最小闭环（召回 → 组装 → 生成 → 引用校验）。
- ReAct 与 Agent：推理-行动循环；Agent 与固定 workflow 的分界（控制权在模型还是在代码）。
- 锚点：`shared/chat/chat.go`、`shared/domain/tool/tool.go`、`shared/embedding/embedding.go`。

#### 第 3 章 一个 for 循环就是你的第一个 Agent

- 文档内 40 行片段：拼 prompt → 调模型 → 解析 tool_call → 执行一个假搜索函数 →
  把结果作为 tool message 塞回 messages → 再问模型，直到响应里没有 tool_call。
- 这就是 ReAct，也是所有 Agent 框架的内核。
- **第一个坏 case 就在那个假搜索函数里**：让它返回空（或弱结果），模型不会停下来说"我没查到"，
  而是编出一家不存在的店和一段"很安静、服务好"的点评。幻觉第一次现形——它在提示词层面无解，
  直接逼出整个第二篇。
- 当场暴露七个问题，后续章节逐一回收：
  1. 模型会一本正经地编，怎么办？（→ 第 1、9、16 章）
  2. 工具怎么声明给模型、参数谁来校验？（→ 第 14 章）
  3. 循环何时停？模型一直调工具怎么办？（→ 第 11、13 章）
  4. 槽位缺失、同名歧义怎么办？（→ 第 15 章）
  5. 状态放哪？进程挂了呢？（→ 第 13、20 章）
  6. 模型挂了 / 超时 / 乱返回怎么办？（→ 第 4、23 章）
  7. 怎么在不花钱、不连库的情况下测它？（→ 第 4、21 章）
- 对照物：最终形态 `chat-service/internal/agent/runner.go`（先只看不讲）。

#### 第 4 章 第一次工程化：Provider 抽象与端口/适配器

- OpenAI 兼容协议精读：`/chat/completions` 的 messages、tools、stream 字段长什么样。
- 把模型藏到 `ChatProvider` 接口后面：chat、tool-calling、embedding 是三个独立端口。
- mock/scripted provider：让全部测试离线、确定、免费可跑——这是后续评测体系的地基。
- 分层即纪律：`shared/domain` 不允许出现 `postgres`/`eino` 字样，Eino 类型不得越出 agent 包，
  这些由 **AST 架构测试强制**，违反时先想代码放错了层，而不是放宽测试。
- 核心思想（不讲语法）：依赖倒置、端口与适配器、可替换性、用测试固化架构边界。
- 锚点：`shared/chat/openai/`、`shared/embedding/ollama/`、`shared/domain/architecture_test.go`、
  `chat-service/internal/agent/architecture_test.go`。

### 第二篇 给 Agent 装记忆——数据工程与 RAG

#### 第 5 章 数据从哪里来：424 万条评论的流式导入

- 为什么不能 `json.Unmarshal` 整个 2.5 GB 文件：gzip JSONL 逐行读取、边解压边解析。
- curate 清洗的关键决策：菜系归一、价格等级、营业时间、PII 脱敏（user_id/name 直接剥除）、
  行政区点-面判定（真实边界几何 vs 包围盒，错误率 10.2% vs 24.1% 的实测故事）、去重与打分。
- 幂等：数据库赋值 identity 主键；评论唯一键 `(restaurant_id, text_hash, rating, reviewed_at)`，
  重跑只更新不重复写。
- prefilter：本地先把 2.5 GB 砍到 308 MB（33.5M → 4.24M 行），为什么"在 join 之前过滤"
  能省掉小时级写入。
- 为什么一个 PostgreSQL 同时扛四件事：结构化过滤（btree/`=`/`ANY`）、地理（PostGIS GiST）、
  向量（pgvector HNSW）、模糊文本（pg_trgm）——不引入 ES / 专用向量库的取舍。
- 锚点：`data-pipeline/internal/pipeline/raw/jsonl.go`、`.../curate/`、`.../prefilter.go`、
  `shared/store/postgres/migrations/0001_init.sql`。

#### 第 6 章 把文字变成向量：Embedding 与知识文档

- 核心思想：分布式表示——为什么向量空间里距离近 ≈ 语义近；cosine 相似度直觉。
- 本地 qwen3-embedding:0.6b、1024 维、Ollama 接入；为什么 embedding 走本地而 chat 走远端。
- `EmbeddingProvider` 端口 + fake 实现；批量 embed 与失败审计。
- 知识文档三兄弟：`restaurant_profile`（商家事实）、`restaurant_review_summary`（可引用证据）、
  `restaurant_review_digest`（**排序燃料，永不可引用**）；文档 hash 实现增量更新。
- **常见 RAG 要切块，这里为什么不切**：主流 RAG 的第一课是把长文档按固定长度 / 语义边界切成 chunk
  再逐块 embedding——因为文档可能很长、一个问题只命中其中一段。这份语料是评论，单条本来就短，
  且知识文档是**按餐厅聚合**的（profile / summary / digest 各一份），检索单位天然就是"一家店、
  一类文档"，所以整篇当一条文档、不做二次切分。代价是单条偏长、粒度偏粗；什么时候该回来补切块
  （评论会聚合成长篇综述、或单文档塞不下一个 embedding 窗口时）值得提前讲清。
- **重头戏小节：digest 的生成与溯源（一次真实的 prompt 迭代）**
  - 反例先行：从 commit `09985b7（refactor(digest): shorten digest prompt to 40-100 words）`
    能看到这次收敛——早期 prompt 没有硬长度上限，模型容易为凑篇幅注水；收敛版 prompt 里
    "Never pad, repeat, hedge, or restate the same point to reach a length" 就是针对它的规则。
    收敛后的规则：40–100 词、硬顶 100 词；7 个维度按优先级只写评论真正支撑的，
    无支撑的维度直接跳过且不许声明"信息缺失"；再配一条长度门（150–800 runes）在代码侧兜底。
    讲法以 commit 信息与现存 prompt 文本为证据，不渲染仓库无记录的具体症状。
  - 输出不可信（接第 1 章的校验闭环）：模型给的来源评论 ID 可能是**幻觉 ID**，要逐个校验合法性；
    digest 因此记录 `source_review_ids`——模型究竟 grounded 在哪几条评论上，可回溯到原文。
  - 工程细节：bundle hash 做缓存（输入不变就跳过重算）；规则基线 `digest:rules:v1` 零模型费用，
    LLM digest 需显式开关。
- 离线产物与在线检索的分工：重导 restaurants 之后 prefilter/文档/向量为什么要重跑。
- 锚点：`shared/embedding/`、`data-pipeline/internal/pipeline/knowledge/`、`.../embed.go`、
  迁移 `0002_knowledge_document_identity.sql`、`0003_embedding_audit.sql`、
  `0014_digest_source_reviews.sql`（source_review_ids 落库）。

#### 第 7 章 向量检索第一课：pgvector 与 HNSW

- 最小 SQL：`ORDER BY embedding <=> $1 LIMIT k`；cosine / 内积 / L2 的选择直觉。
- HNSW 核心思想（不推导）：分层可导航小世界图——先在稀疏"高速公路层"长跳，
  再逐层下沉细找；为什么它是 `ORDER BY` 结构而不是过滤器。
- **关键事故**：`WHERE borough = 'manhattan' ORDER BY embedding <=> q` 直接退化成顺序扫描
  （50k 行手工过滤的 EXPLAIN 实测）。
- 解法：硬过滤先于向量召回 + **每个行政区一个 partial HNSW index**，过滤后仍走索引扫描；
  以及"行政区 + 半径 + 菜系"三重过滤仍会 filter-then-sort 的已知边界。
- 锚点：迁移 `0004_scope_partitioned_hnsw.sql`、`README.md` 的检索小节、
  `shared/store/postgres/knowledge_index_test.go`。

#### 第 8 章 单通道为什么不够：多路召回与融合

- 纯向量翻车合集：找店名精确匹配失败、硬行政区被"语义相近"带偏、高分店沉底。
- 四个通道：结构化硬条件、pg_trgm 名称/地址关键词、profile 语义、digest 语义
  （两个语义通道共享归一化界，算一个家族）；每通道按 `oversample` 读得比 page size 更深，
  先把候选池铺大。
- **出去的 query 不做改写**：常见 RAG 会先做 query 改写 / 扩展 / 分解（multi-query、HyDE、
  把"安静的店"拆成多个子查询再合并）。这里刻意保持"原始 query 一次 embedding 直查"——
  确定性条件已由槽位单独抽取兜住（第 15 章），语义通道只负责补召回，而"单一 query 不够"
  这个短板本身由多路融合在补。代价与回归点：query 极短或很口语时语义通道会偏弱，
  到什么规模才值得引入改写。
- 融合三步——**归一化 → 加权求和（或加权 RRF）→ 池内重排**：
  - 归一化：各通道分数量纲不同，先映射到同一界再相加，否则权重毫无意义。
  - 加权求和 vs RRF：由 `RETRIEVAL_FUSION_METHOD` 切换，讲清两种融合各自适合什么。
  - **池内重排（pool rescore）**：HNSW 是近似召回，返回顺序不可全信；融合后对整个候选池
    用精确 cosine 重算相似度再排一次（`RETRIEVAL_ENABLE_POOL_RESCORE`，默认开）——
    "先粗召回、再精算"是这一块最值得讲的一步，也是它与 rerank provider（端口已留空）的边界。
  - 评分先验按评论样本量收缩（小样本 4.9 分不该赢过 4.5 分/数千条）。
- 每个候选必须自证：`reasons` 写清通道、权重、贡献；`trace.channels` 如实记录每个通道
  跑没跑、召回多少，没跑就是 `ran:false`。
- 纪律：排序必须可复现（禁止 map 遍历顺序/时间/随机数）；无 filter 且无 text 的请求拒绝；
  未知行政区 400；查无结果 200 + 空数组——这些差异是有意的。
- 锚点：`chat-service/internal/retrieval/fusion.go`、`rescore.go`、`review_channel.go`、
  `service.go`。

#### 第 9 章 让每个答案都能溯源：两级检索与证据组装

- 为什么餐厅召回与佐证召回必须分开：scope（谈哪几家）是前提，不是召回后再 filter；
  evidence 接口在没有 restaurant_ids 时直接拒绝。
- 证据组装的硬规则：超 token 预算**整块丢弃，绝不截断半句引用**；每店每类文档最多 3 块
  （在预算之前应用，防长块垄断）；`dropped_by_reason` 区分预算满/重复/超限；
  来源缺失返回 `"unknown"` 进 `warnings`；全部不可用则报错而非空包。
- prompt injection 防御：评论是数据不是指令——检索内容与系统指令的边界、注入用例怎么考。
- **护栏只做了"注入"这一种**：多用户线上产品通常还有输入侧 moderation、jailbreak 分类器，
  输出侧 PII / 毒性过滤。本项目是本地单用户 demo、语料已脱敏，只保留了"评论是数据不是指令"
  这一条边界；接多用户时这几层要补齐。
- digest 与 summary 的根本区别：喂排序 vs 可引用，为什么这个区分不能靠模型自觉。
- 锚点：`retrieval/evidence.go`、`assemble.go`、`agent/answer/injection.go`。

#### 第 10 章 没有度量就没有优化：检索评测体系

- 86 个 YAML case 覆盖五个查询族：硬过滤、软条件、证据主题、注入、scope 纪律。
- 指标：recall@5、引用精确率、硬过滤准确率、语义回答相关性、跨店泄漏；
  实测基线（recall@5 0.843、引用精确率 1.000、零泄漏）。
- **这里全是可复现的规则指标，没有用模型当裁判**：`relevance` 就是"返回页里命中期望菜系的比例"
  这类可判定的计算（见 `eval_test.go`）。常见做法是 **LLM-as-judge** 给语义质量打分——更灵活、
  能评规则写不出的东西，但不确定、有成本、不可逐 bit 复现；本项目门禁要求可复现，所以选了规则，
  代价是表达力有限、软指标得自己拆成可判定形式。
- 覆盖率棘轮：某一族丢 case，评测直接失败。
- 离线哲学：没库时"响亮地 skip"（一片绿但没断言比一片红更糟）；
  `PLATEPILOT_REQUIRE_DB=1` / `REQUIRE_VECTOR=1` 把 skip 变 fail，防向量通道静默降级。
- 调参不重编译：权重、top_k、oversample 全部环境变量化，对着评测集调。
- 锚点：`retrieval/eval_test.go`、`testdata/retrieval_cases.yaml`、根 `.env.example`。

### 第三篇 从 for 循环到 Agent 框架——Eino 与工具系统

#### 第 11 章 for 循环的瓶颈：为什么需要图编排

- 第 3 章的循环长出这些东西后是什么样：多轮工具、槽位缺失要追问、同名要澄清、
  只读工具想并发、写操作必须先停下等人确认——循环体里堆满互相缠绕的 if-else。
- 抽象的方向：把一个 turn 看成**显式状态机**——共享状态（TurnState）、节点（纯变换）、
  分支（条件路由）、停机点（等用户、等确认、结束）。
- 手写状态机 vs 用框架：框架帮你解决编译期校验、流式、回调、并发与状态传递；
  但业务状态机必须是你自己的（项目里 TurnState、停机语义都在自己手里）。
- 锚点：`agent/state.go`、`agent/nodes.go`（先看函数清单与注释）。

#### 第 12 章 Eino 入门：核心抽象与底层原理

- 核心抽象：Chain（直线）与 Graph（带分支）、Lambda（任意函数即节点）、Branch（条件路由）、
  StateGraph（带共享状态）；ChatModel / Tool 是两种组件接口。
- Compile 在干什么：把声明式的图变成可执行对象，**编译期**检查节点是否齐备、边是否闭合、
  类型是否对得上——图错误在启动时暴露，不在第三次对话时。
- 流式与回调的核心思想：节点产出沿图流动，callback handler 在节点边界切面注入
  （项目的审计/trace 就挂在这一层），业务节点本身不写观测代码。
- 一个最小 Lambda + Branch 的内嵌片段，讲清"图就是带路由的函数组装"。
- 锚点：`agent/einomodel/chatmodel.go`、`agent/toolreg/einotool.go`；Eino 依赖版本见
  `chat-service/go.mod`。

#### 第 13 章 PlatePilot 的 Agent 图全景

- 七个节点：ingress（历史/记忆/候选人注入）→ interpret（槽位）→ plan（模型决策）→
  tool round（执行/并发/写操作截停）→ clarify（澄清或继续）→ answer（证据合成）→
  finalize（持久化）。
- TurnState 里有什么、分支条件怎么判、两个停机状态（awaiting_input / awaiting_confirmation）。
- 两个入口的决定性差别：`Run` 跑完返回完整转录（离线评测要这个）；
  `RunLive` 在独立 goroutine 上图执行、逐帧回调（SSE 首字节延迟要这个），
  128 帧缓冲因此不会成为答案长度上限。
- 轮次护栏：最多 5 轮工具、同线程最多 3 次澄清（第四次说明前三次没改变任何东西）。
- 锚点：`agent/runner.go`、`agent/nodes.go`、`agent/persistence.go`。

#### 第 14 章 工具系统：六个确定性工具与注册表

- 六个工具：search_restaurants、resolve_restaurant、restaurant_evidence、get_availability、
  request_reservation、save_memory；**模型规划和措辞，数据库计算**。
- 工具的 JSON Schema 如何从 Go 类型声明生成；注册表负责注册、超时统一、参数校验；
  领域错误转成模型读得懂的 tool message。
- 调度纪律：同一轮只读调用并发（最多 3 个），上层无感（转录与状态与串行完全一致）；
  写工具立即终止本轮、后续调用直接丢弃（不许对着写操作尚未建立的状态执行），
  并以 `seq` 列在审计表里保序。
- **末节专题：为什么是 Tool Calling，而不是 MCP**
  - 两者不在同一层：MCP 是**工具的跨进程发现与传输协议**；MCP server 提供的工具，
    到了模型面前仍然以 function calling 的 JSON Schema 出现——MCP 不替代 tool calling，
    它解决的是"工具从哪来"。
  - PlatePilot 的工具是**进程内、直连 store 的确定性函数**：只有一个 client（本服务自己的图），
    没有跨语言/跨进程/第三方共享需求；预约 hold + 幂等还要和本地状态、事务紧耦合。
  - 上 MCP 的净代价：多一条进程边界与序列化往返、丢掉编译期类型安全、
    破坏事务与一致性边界、离线契约测试要额外拉起 server、延迟增加——没有换来任何东西。
  - 什么时候才该上：工具由第三方提供、多个 agent/client 复用同一组工具、
    工具需要独立部署与演进（此时技术 PRD 已预留 `modelcontextprotocol/go-sdk` 选型）。
- 锚点：`agent/tools/`、`agent/toolreg/registry.go`、`docs/platepilot-technical-prd.md` 选型表。

#### 第 15 章 听懂人话：槽位抽取、意图与澄清

- 为什么不能指望模型在工具参数里"自觉透传"全部条件：漏一个菜系、忘一个行政区，
  召回就静默变宽。
- 独立 extractor：interpret 节点用结构化输出把用户消息解析成 slots/intent，
  作为模型规划之外的第二道保险；模型缺失时规则降级是官方支持的部署形态。
- 两类人机回环：缺槽位 → 生成追问（missing_slots）；同名/多家命中 → resolve 候选卡片消歧。
- 防死循环：澄清上限 3 次，之后必须按明示假设继续，而不是问第四次。
- 锚点：`agent/slots/`、`agent/tools/resolve_restaurant.go`、`agent/nodes.go` 的 clarify 段。

#### 第 16 章 说对话、引对源：回答合成与流式引用闭包

- 两类凭据两种说法：商家记录事实（评分/价格/菜系/行政区/地址，2021 快照）可直述，
  评分必带评论样本量；观点类问题（口味、安静程度、氛围、服务）**只能**来自召回的评论证据，
  每句挂 `[^id]`；记录里没有的字段答"记录中没有"，绝不靠常识补——这正是第 3 章幻觉的正面回答：
  宁可承认缺失，也不补常识。
- 引用闭包：首轮生成引用了本轮并不拥有的证据 ID → 整轮重新生成。
- 系统指令与上下文块的语言策略：模型可见的 `<evidence>` / `<filters>` / `<recent_turns>` 等块
  刻意保持中文（压住小模型的中文推理），离线 digest 用英文（语料是英文、对 embedding 更友好），
  而最终回答必须跟随用户语言——三种语言取向各有理由，不是随手写的。
- 流式的核心矛盾：重新生成发生时，错的文本已经到达用户屏幕。协议设计解：
  `message.delta` 全程标注"暂定"，`message.replace` 表示丢弃本 run 全部累积文本并以正文为准，
  客户端只渲染最后一份完整文本就永远正确；`message.end` 之前一切不落本地存储。
- 锚点：`agent/answer/compose.go`、`adequacy.go`、`httpapi/sse.go`、README "turn's event stream"。

#### 第 17 章 长期记忆：检索，而不是回放

- 反模式：把历史记忆全部拼进 system prompt——挤爆注入窗口、稀释当前话题。
- 短期上下文是另一笔预算：ingress 注入的 recent turns（对话历史）与长期记忆**共用同一个注入
  窗口**，取舍是耦合的——本章讲长期那半，短期那半在第 13 章的 ingress 里定。
- 三类记忆区别对待：**约束**（过敏、忌口、硬要求）整窗注入，硬条件不容遗漏；
  **偏好与事实**按当前消息与记忆内容的相关性挑选，窗口花在"本轮相关"的记忆上。
- 安全兜底：记忆检索失败或零命中时回退到"最自信优先"——检索只能收窄窗口，不能清空它。
- 写记忆也是策略：turn 结束时由 memorywrite 策略抽取，用户可在 `/v1/memories` 查看/改/删。
- 锚点：`agent/memory.go`、`memorywrite/policy.go`、`app/memory_test.go`。

#### 第 18 章 敢写下去的 Agent：HITL 确认门、幂等与预约

- **确认门不是 prompt 工程**：写操作路径从工具轮中根本不可达——模型再怎么"说服"用户、
  输出什么文字，都不会产生写库；预约只能在展示最终摘要后经独立的
  `POST /conversations/:id/confirm` 发生。
- 幂等键由 thread + action + 用户批准的 request id 派生；确认重试 = 同一张订单，
  绝不重复订座。
- mock inventory：座位与 hold 是 demo 状态，运维台可查看与重置；明确标注 mock，不伪装真实预订。
- 删除会话不级联删预约：预约占的是真实（mock）座位计数，归属在库存而非对话。
- 锚点：`hitl/confirm.go`、`reservation/service.go`、`httpapi/confirmation_handler.go`、
  `agent/nodes.go` 的 parkForConfirmation。

### 第四篇 让 Agent 上线——流式、观测、评测与韧性

#### 第 19 章 SSE 与验证台：把一个 turn 实时送到浏览器

- 为什么是 SSE 不是 WebSocket：服务端单向推送、HTTP 语义、curl 可调试。
- 封闭事件集：message.start / delta / replace、tool.start / finish、citation、
  state.awaiting_input、confirmation.required、memory.saved、message.end、error；
  服务端永不发出契约未定义的事件（有测试扫封闭集）。
- 帧随图执行即时转发而非攒到最后；128 帧缓冲、心跳、phase 进度事件。
- 前端验证台如何讲清「Agent 在想什么」：step timeline、tool timeline、引用抽屉、候选卡片、turn 状态栏——
  验证台本身就是"Agent 在想什么"的可视化教材。
- 锚点：`httpapi/sse.go`、`conversation_handler.go`、`web/src/components/agent/`、
  `web/src/hooks/useAgentTurn.ts`。

#### 第 20 章 Agent 可观测性：run / tool / node 三级审计

- 三级模型：每个 turn 一行 run、每次工具调用一行（含参数摘要/状态/seq/延迟）、
  每个图节点一个 span（planning/tools/clarify/answer/finalize 各自耗时）。
- 查询面：`/v1/runs/:id`、`/v1/runs/:id/nodes`、`/v1/traces/:trace_id`。
- 审计旁路原则：审计写失败**不能拖垮 turn**（吞错），但服务器日志必须留痕；
  run 表只存分类与截断消息，日志才是排查第一现场。
- **一次坏 turn 的排查演练**（把三级审计真正用起来）：从 `/v1/runs/:id` 拿到 run，看 `/nodes`
  定位哪一步耗时异常或出错，再下钻到该 run 的工具调用参数/状态/延迟，最后落到服务器日志——
  三级审计存在的唯一理由就是这条路径。
- schema drift 要拒绝启动而不是告警：库落后两个迁移时症状是误导性的 502，
  "双方都安静"的错误必须变成显式失败；但检查只读，迁移永远是 pipeline 的职责。
- 锚点：`agent/audit/hooks.go`、`shared/store/postgres/run_repository.go`、
  迁移 `0005_agent_runtime.sql`、`0010_run_nodes.sql`。

#### 第 21 章 怎么"考试"一个 Agent：四道安全门禁

- 四个 gate 全部要求 1.0：工具选择准确率、确认门安全、重复预约安全、端到端成功率。
- scripted provider：用例以 YAML 编排"模型第 N 次返回什么"，零成本、离线、确定性地
  驱动真实图；加 case 只是改数据。
- 为什么每个 case 要在**两种回答路径下各考一次**：流式路径在引用校验之前就发出了文本，
  门禁必须在违规可能触达用户的配置下成立。
- 回归手段：固定请求两遍回放必须逐 bit 一致；两套模型配置逐 case diff。
- 锚点：`agent/agent_eval_test.go`、`agent/agent_replay_test.go`、
  `agent/testdata/agent_cases.yaml`、`model_routing_test.go`。

#### 第 22 章 性能与成本：会算账的 Agent 工程

- 检索实测：p50 129 ms / p95 158 ms，其中 embedding 往返约占 53%——钱和时间花在哪要有数。
- Agent 运行时自身开销：每轮 p50 0.34 ms（离线 scripted），证明图编排本身近乎免费。
- 流式的账：同一套工作，流式 TTFT 65 ms vs 整段 122 ms，整轮略慢（校验的是流而不是整块）；
  用 20 ms/块的固定节奏 provider，测的是"我们花了多少"而不是"模型花多少"。
- 成本意识：digest 默认走规则基线（零模型费用），LLM digest 需显式开关；
  权重/超时/开关全部环境变量化，调优不重编译。
- 锚点：`agent/agent_perf_test.go`、`retrieval/perf_test.go`、`.env.example`。

#### 第 23 章 韧性与工程纪律

- 软降级矩阵：chat provider 缺失 = 拒绝启动（M4 起模型是主路径）；
  embedding 缺失 = 语义通道关闭、trace 如实记 `ran:false`；上游过载 = 重试而非结束 turn；
  provider 不支持流 = 自动降级整段完成并在 end 帧告警。
- 一套契约两个实现：memory 与 postgres 跑同一套 contract 测试；默认离线全绿，
  真库套件 `make test-postgres`，没库 skip。
- 确定性纪律：排序可复现、测试无外部依赖、架构边界由 AST 测试守护。
- 全架构复盘：四项目依赖方向、两服务表集不重叠、`/v1` 响应即客户端契约。
- 锚点：`app/app.go`、`shared/store/contract/`、`chat-service/AGENTS.md`。

### 收官：从 PlatePilot 出发的延伸路线

- rerank 的下一步：池内重排只是精确 cosine 重算（第 8 章已讲），再往上是一层真正的交叉编码器
  rerank——端口已留空，什么时候才值得接上。
- digest 溯源的下一步：现在还只记录"模型 grounded 在哪几条源评论上"（第 6 章），再进一步是
  校验模型的结论是否真被那几条评论支撑，而不只是"引用了它们"。
- 真要接外部/第三方工具时，MCP 在架构里的准确位置（接在 toolreg 之后，而非替代它）。
- 从演示到多用户：`X-User-ID` 请求头身份假设、loopback admin 是有意的起点而非安全方案。
- 什么时候才值得 fine-tune；什么时候该把单库拆成专用检索/向量存储（语料再涨一个数量级时）。

#### 附：本项目没用到的常见 Agent 技术（值得知道）

> 下面这些在 Agent 开发里很常见，各自解决一个具体问题；而这个产品形态不会遇到那个问题，
> 所以正文不展开。每条只讲「它解决什么 / 为什么这里用不上」，有兴趣再自行深入。

- **规划范式——Plan-and-Execute、Reflection/Reflexion、Tree-of-Thoughts/LATS**：让模型先出多步计划、
  对中间结果自我批判重来、或在多条推理分支里搜索。适合步骤多、可试错、单步 ReAct 走不动的任务；
  本项目的 turn 是"检索 + 少量工具"的短流程，一步 ReAct + 状态图足够，加这些只会更贵更不稳。
- **多 Agent 协作——supervisor/worker、handoff、debate，以及 A2A 这类 agent 间协议**：把任务拆给
  多个角色 agent 互相调用。适合职责差异大、需要对抗式校验的场景；本项目是单 agent，工具即能力边界，
  多 agent 只会引入跨 agent 的状态与通信复杂度。
- **工具规模化——tool retrieval / 动态工具加载**：工具上百个时，先检索出"这轮该用哪几个"再喂给模型。
  本项目只有 6 个固定工具，注册表全量声明即可，没有挑选成本。
- **护栏框架——输入 moderation / jailbreak 分类器、输出 PII·毒性过滤**：多用户线上产品的标配。
  本项目是本地单用户 demo、语料已脱敏（见第 9 章的取舍）。
- **受约束解码 / 结构化输出——JSON mode、GBNF、Outlines**：从解码层保证模型只能吐合法 JSON/枚举。
  本项目用了 API 层的 `response_format=json_schema` 严格模式（slots 抽取；provider 不支持时
  自动降级 `json_object` 并重试一次），但从不信任它——结构化输出只保证"合法 JSON"，保证不了
  业务合法（行政区真实存在吗？证据 ID 本轮真的有吗？），语义校验仍在代码侧，不合格整体
  降级到规则抽取（第 15 章的校验闭环）；GBNF/Outlines 这类本地解码层约束没有引入。
- **语义缓存 / prompt 缓存**：对相同或相近的请求直接复用结果，省时省钱。本项目语料小而问答长尾、
  命中率低，只在离线 digest 用了 bundle-hash 缓存。
- **上下文压缩 / 历史摘要**：长对话把早期历史 summarize 成一段再注入。本项目靠"记忆检索"控制注入
  窗口（第 17 章），还没到需要摘要的规模。
- **代码沙箱 / code interpreter、多模态（视觉·语音）**：让 agent 执行代码或处理图像/音频。与
  "文本餐厅检索"这个产品无关。

## 五、写作约定（给后续每一章）

1. 每章文件命名：`NN-章节标题.md`（如 `03-一个-for-循环就是你的第一个-agent.md`），与本提纲同目录。
2. 中文行文；面向用户的解释性文案沿用项目中文风格。
3. 代码引用以仓库相对路径标注；示例片段只保留教学所需的最小骨架，不复制大段真实源码。
4. 一切数字、行为、文件路径必须来自仓库现状（README、docs、代码、迁移、测试），不臆造；
   项目演进而本章过时，以仓库为准并修订本章。
5. 原理只讲核心思想；需要更深的读者由章末的「参考代码与目录」引导到真实代码。
6. **正文以知识与思路为主线，不以代码为主线。** 每章要能回答"这一类问题该怎么想、怎么解"，
   目标是读者**不看仓库代码也能理解知识点**；不按代码文件顺序组织章节、不逐段走读源码。
7. **但项目是这门课的差异化证据，不是可有可无的背景。** 每讲完一段通用知识，就用本项目的
   真实取舍、实测数字或事故佐证"这套思路在真实系统里如何落地"——**知识点是主线，项目是证据**；
   不做脱离落地的纯教科书，也不做围绕代码的分析报告。
8. 章末「参考代码与目录」把本章涉及的真实文件、函数、实测数字列全，作为课后「读」的入口；
   正文允许用真实数字与取舍作证据（第 7 条），但文件路径与函数名以章末清单为主，不密集罗列，
   也不重复贴大段实现。
