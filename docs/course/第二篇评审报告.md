## 总体结论

**六章仍然守住了「教学文档，不是代码分析」的主线，这一点没有退步。** 正文按「问题 → 概念 →
取舍」组织，真实源码集中在 §X.6，坏 case、最小示例、课后实验三件套齐全；第二篇依旧是全课程
证据密度最高的一段。

但本轮逐条对源码复核后，发现上一版报告漏掉了两类更要紧的问题，它们不在文风层面，而在
**因果解释与契约表述**：

1. **🔴 第 9 章把「两级检索」说成防止错配引用的充分必要条件，因果链反了。** 证据行本身带
   `RestaurantID`，一次全库召回后按餐厅集合过滤也不会自动错配；错配发生在生成阶段，要靠
   引用校验兜底。scope 仍然是正确的接口前置条件，但理由需要重写。
2. **🔴 第 10 章把检索证据评测说成了「答案级引用能力」评测。** `citation_precision` 实际检查
   来源、快照、scope 三项；`evidence_grounded_rate` 实际是「该 case 返回的证据是否全部可核对」。
   二者都没有检查模型最终答案里的逐句引用。`citation precision = 1.000` 不能推出「回答里的引用
   100% 正确」。
3. **🔴 第 8 章上一轮的核心混淆仍未关闭**：review 通道用 digest 排餐厅，但正文仍把它描述成
   回答「等位久吗／服务好吗」的证据来源，且没有一句「digest 永不可引用」。
4. **🔴 第 8 章的请求契约写错了一句会误导实现的话**：正文说「没有 filter 也没有 text 的搜索要
   拒绝」，实际规则是 `text`、`query`、`filter`、`soft_conditions` 四者全空才拒绝；只有 `query`
   的请求是合法主路径，正文自己的 §8.5 示例就在这样调用。

结论：**不需要重写六章，但必须先修 4 条红色因果/契约问题，再处理 9 条黄色补强。**
「有没有写成代码分析」的专门结论仍然是：**没有**。

## 二、重点问题详解

### 重点一（🔴 必修）第 9 章：两级检索的因果链讲反了

**原文**（§9.2.1）：

> 如果证据召回可以自己扩大范围，它就可能返回语料里离查询最近的那条评论——然后把它归到一家
> 根本不相干的店头上。而「这条评论其实不是这家的」这件事，下游任何环节都无法检测。

**仓库事实**：

- 每条证据 DTO 都带 `RestaurantID`（`shared/domain/evidence/evidence.go:60-70`），召回条件也按
  `restaurant_id` 过滤；一次全库向量召回后按 `restaurant_ids` 过滤，返回的仍是带正确归属的行，
  不会因为 SQL 是一次还是两次就自动变成另一家店的话。
- 评测还专门统计 `cross_restaurant_leak`，并用 `inScope(item.RestaurantID, tc.RestaurantIDs)`
  逐条检查（`chat-service/internal/retrieval/eval_test.go:426-431`）——若「下游无法检测」，这个
  断言本身就不成立。

**为什么必须改**：这段把「两级 API」说成了引用正确性的唯一机制，学生会记住一个错误的因果模型；
真正防错配的是**生成阶段只允许引用本轮 scope 内的证据 ID + 引用闭包校验**（第 16 章）。scope 的
价值仍然成立，但它是接口契约与召回范围问题，不是「不分两级就必然错店」。

**建议改写**：

> 证据召回把「哪几家店」作为**调用前置条件**，而不是召回后再筛的一个可选过滤条件。理由是引用
> 在语义上永远是「X 家的 Y 说了 Z」：没有 scope 的接口无法表达这条断言，调用方也无从判断返回的
> 证据属于谁。scope 同时让两级使用不同的文档集（restaurant / evidence），避免一级的排序燃料混入
> 二级引用。**但 scope 不是防错配的唯一防线**——证据行带 `RestaurantID`、生成侧还有引用闭包，
> 三者共同保证「话」不会被安到别的店头上。

---

### 重点二（🔴 必修）第 10 章：检索证据评测被写成了答案级评测

**原文**（§10.2.6）：

> `citation_precision`：返回的逐条引用里，有多少条是「可核对」的……
> `evidence_grounded_rate`：有多少个可回答的问题，是整题由可核对引用答出的。

**仓库事实**：

- `checkCitation` 只检查 `Source != ""`、`SnapshotAt` 非零、`trace.ScopeSize != 0`
  （`eval_test.go:466-475`），**没有检查引用内容是否切题，也没有检查生成答案里的句子**。
- `groundedPassed` 的判定是「该 case 返回的 evidence bundle 非空且每一条都通过 `checkCitation`」
  （`eval_test.go:433-450`），不是「模型答案的每一句都有引用」。
- 评测入口只构造 `retrieval.Service`（`eval_test.go:214-255`），没有走 answer/compose 链路，
  因此这套指标无法证明「最终回答的引用正确率为 1.000」。

**为什么必须改**：这是全章最容易被误读成「我们的答案 100% 可信」的一句话。实际契约只到
「交给答案合成器的证据是可核对的」；答案句级引用由第 16 章的引用闭包与第 21 章的 Agent 门禁负责。

**建议改写**：

> 本章评测的是**检索层交出的证据**，不是模型最终回答的逐句引用：
> `citation_precision` = 返回证据中同时具备来源、快照时间、正确 scope 的比例；
> `evidence_grounded_rate` = 在期望有答案的 case 中，返回证据全部可核对的比例。
> 「回答里的每句话是否都有引用」属于 answer/compose 与 Agent 门禁，不在这套 fixture 的测量范围。

同时把「precision」在正文里显式解释为**可核对率**，避免读者按信息检索的 precision 定义理解。

### 重点三（🔴 必修）第 8 章：review 通道仍被写成「证据通道」

**原文**（§8.2.1 表）：

> `review` ｜ review digest 的语义 ｜ `query` + `soft_conditions` ｜ 「等位久吗／服务好吗」

**问题**：review 通道召回的是 `restaurant_review_digest`，它属于 `restaurant` scope，是排序
燃料，**永不可引用**（`shared/domain/evidence/evidence.go:24-30`）。但表中「回答哪类问题」直接
写成「等位久吗／服务好吗」，读者自然会认为回答里那句「等位久」来自 review 通道。ch9 虽然讲清了
digest 与 summary 的区别，但两章之间没有桥。

**建议**：在 §8.2.1 表下加一句（并在 §8.4 重申）：

> 四个通道全部是 **restaurant scope 的一级召回**，只决定「谈哪几家」；review 通道用 digest
> 做餐厅级语义排序，**digest 不进入任何引用**。真正被引用的 summary/attributes/hours 来自
> 第 9 章的 evidence scope 二级召回。

### 重点四（🔴 必修）第 8 章：「空请求」契约写错，且与本章示例自相矛盾

**原文**（§8.2.7）：

> 没有 filter 也没有 text 的搜索要拒绝（`CodeRetrievalEmptyQuery`），不要退化成
> 「按分数返回全库」。

**仓库事实**（`chat-service/internal/retrieval/service.go:212-217`）：

```go
if text == "" && query == "" && req.Filter.IsEmpty() && !req.HasSoftConditions() {
    return ..., CodeRetrievalEmptyQuery
}
```

即 `text`、`query`、`filter`、`soft_conditions` **四者全空**才拒绝；只有 `query` 的语义检索是
主路径。§8.5 的第一个 curl 正是 `{"query":"quiet italian place for a date", ...}`，按正文这句
规则反而应该被拒绝。

**建议**：改为「没有任何可用信号（`text`、`query`、`filter`、`soft_conditions` 全空）的请求
要拒绝」，并补一句「只有 query 是合法的语义检索；只有 filter 是合法的结构化浏览」。

### 重点五（🟡 建议）第 9 章：支撑下限的例子与真实文档结构不符

**原文**（§9.2.3 第 ④ 趟）：

> 想象结果里剩了三条同一家店的 review summary：它们是同一句话的三次转述。

**仓库事实**：`restaurant_review_summary` 是**按话题一文档**
（`data-pipeline/internal/pipeline/knowledge/summary.go:102-127`）：food、service、ambience、
value、wait 等各一份，内容分别统计该话题的评论数与正面占比，不是同一句话的三次转述。真正的
风险不是「重复」，而是**整包只剩同一类“印象型”文档**，无法与 profile/hours 这类“记录型事实”
区分。

**建议**：把例子换成「三条不同话题的 review summary」，并说明 support floor 换入的是
`restaurant_profile` / `restaurant_hours` / `restaurant_attributes` 中的一种；规则本身不变。

### 附带发现（代码侧，未改动）

逐行核对 `newEvalService` 时发现：它的 `ServiceConfig` 只显式设了 `Weights`、
`Oversample`、`TopK`、`EnableStructured/Keyword/Vector`，**没有设 `EnableReview`、
`EnablePoolRescore`、`ReviewMinSim`、`FusionMethod`**；而 `NewService` 只兜底
`Oversample/TopK/EmbeddingTimeout/ReviewOverread`。后果是评测跑的是「三通道 + 无池内
重排」，与 `DefaultServiceConfig`（四通道 + rescore）不一致。

这可能是有意为之（评测只锁前三路），也可能是 review 通道加入后测试配置没跟上。**它不
影响本章任何一句结论**（正文只声称「同一份通道与融合代码」，未声称同一套开关），但会
影响「评测分数能否代表线上」这个更强的主张，建议作为独立问题确认：要么在评测里显式
打开这两个开关并重跑基线，要么在 `newEvalService` 上写清为什么关掉。
